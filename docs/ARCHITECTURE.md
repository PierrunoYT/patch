# Architecture

Patch is an Electron app written in TypeScript and built with electron-vite. All logic that touches the file system, the network, API keys or child processes runs in the **main process**. The **renderer** is a sandboxed page without Node.js access that talks to the main process only through a typed IPC contract.

```
┌──────────────────────── main process (Node) ─────────────────────────┐
│ index.ts          wiring, IPC handlers                                │
│ settings.ts       settings, keys, ChatGPT session (safeStorage)       │
│ projects.ts       recent projects, per-project instructions           │
│ chat_manager.ts   active chat, autosave  ──▶ chat_store.ts            │
│ agent/            agent loop, chat session, system prompt             │
│ llm/              Anthropic + OpenAI conversations, small-model calls │
│ tools/            read/edit/write/grep/list, run_command, web, browser│
│ search/           embeddings index for search_code                    │
│ panels/           terminal (node-pty), git (simple-git), browser      │
└───────────────▲──────────────────────────────────────────────────────┘
                │ typed IPC (src/shared/ipc.ts)
┌───────────────┴── preload (sandboxed) ──┐   ┌── <webview> guest ──────┐
│ window.api.invoke / window.api.on,       │   │ pages opened in the     │
│ allow-listed channels only               │   │ browser panel; no Node, │
└───────────────▲──────────────────────────┘   │ no preload             │
┌───────────────┴── renderer (no Node) ────┐   └─────────────────────────┘
│ app.ts, views/ (transcript, composer,     │
│ sidebar, dialogs, panels), markdown.ts    │
│ (DOMPurify)                               │
└──────────────────────────────────────────┘
```

## IPC contract

`src/shared/ipc.ts` declares every channel:

- `InvokeApi` — renderer → main request/response (`window.api.invoke('settings:get')`).
- `EventMap` — main → renderer pushes (`window.api.on('chat:event', …)`).

Handlers (`src/main/ipc.ts`, `handle` / `send`) and the preload bridge are typed from these maps, so a renamed channel or changed payload fails to compile. The preload forwards only channels listed in `INVOKE` / `EVENTS`; those lists are `Record<Channel, true>` so forgetting a new channel is also a compile error.

## Chats and the agent loop

1. The renderer calls `chat:send`. `ChatManager` creates a `ChatSession` on the first message, fixing the chat's project, model and system prompt, and returns as soon as the session starts. Setup errors (no project, missing key) come back immediately.
2. `Agent.send` (`src/main/agent/agent.ts`) adds the user message and runs turns:
   - The tool list is rebuilt at the start of every turn (`ChatManager` passes `tools: () => …`), so a tool that becomes available while a chat is open, such as `search_code` after an OpenRouter key is saved, is offered from the next turn on. The system prompt is not rebuilt; it stays byte-identical for prompt caching and tells the model to use optional tools only when currently offered. When the chat starts, `agent/agent_file.ts` reads `AGENTS.md` (else `CLAUDE.md`, capped at 20,000 characters) from the project root into the prompt, before the per-project instructions. `ChatSnapshot.agentFile` carries its name so the status bar can show that it is loaded; a saved chat keeps the file it started with.
   - `conversation.runTurn` streams the model's answer (text and summarized thinking are forwarded as `chat:event`s).
   - A request that fails for a reason that usually passes is repeated by the agent loop (`runTurnWithRetries`), not by the provider SDKs: their clients are created with `maxRetries: 0` for conversations (the small-model clients for titles and compaction summaries get 3 silent SDK retries, `BACKGROUND_RETRIES`). `agent/retry.ts` decides from the error's shape, so it covers Anthropic, OpenAI and compatible endpoints: HTTP 408, 429 and 5xx (including Anthropic's 529), errors sent inside a stream after a 200 response (`overloaded_error`, `api_error`, `rate_limit_error`, `server_error`, read from the most specific type or code the SDK puts on the error, since the outer type is just `error`) and connection problems (`ECONNRESET`, timeouts, DNS failures, SDK connection errors). Not retried: 501 and 505, other 4xx, an out-of-quota 429, a refused connection (nothing is listening, e.g. Ollama not started), aborts and anything else. Up to 4 retries wait about 2, 4, 8 and 16 seconds (±25%), or the provider's `Retry-After` / `retry-after-ms` when given; a request to wait more than 60 seconds is not retried. Each retry adds a notice to the chat ("Rate limited (429). Retrying in 2 s (retry 1 of 4)…"), discards the text the failed attempt had streamed, and can be stopped during the wait. A conversation only records a turn once it has succeeded, so repeating a request cannot duplicate history; the last error is shown as before once the retries are used up.
   - For each tool call: validate the input against the tool's Zod schema (a failure names the missing fields and the fields received, and is returned to the model as an error result) → ask the permission rules (`decidePermission`, `agent/permissions.ts`; `reject` answers the model without running, `allow` skips the card, `ask` forces it) → build a preview (diff, command, or URL) → if the tool needs approval (`alwaysAsk`, `mustAsk` for this call, or `requiresApproval` in **Ask** mode when the call is not pre-approved and no rule decided), wait for `chat:decide` → run it. Consecutive calls to `parallelSafe` tools run with `Promise.all`; every other call runs alone after them, and results keep the order of the calls. The result text, summary and errors pass through `redactSecrets` (`tools/redact.ts`) before they are returned to the model or emitted. The `isPreApproved` callback that `ChatManager` passes to each session checks shell commands against `allowedCommands` (the global list in Settings plus the chat's project's own list from `projects.json`, `mergeAllowLists`, both read on every call so changes apply to open chats) (whole-word prefix match; never for a command containing `; & | < >`, a backtick, `$`, `(`, `)`, `{`, `}` or a line break, because PowerShell runs `(...)` and `{...}` even inside a program's arguments), fetch/browser hostnames against `allowedNetworkHosts` (global plus project, the same way), and local browser files against workspace confinement. File edits always ask in Ask mode.
   - All results of a turn go back to the model together, then the next turn starts. The loop ends when the model answers without tool calls (or after 200 turns).
3. Declining **with** feedback sends the feedback to the model as the tool result and continues; declining **without** feedback stops the task. Stopping (`chat:stop`) aborts the request and running commands. Every tool call always gets a result, even when skipped or stopped, or when it came with a refusal, so the history stays valid for the API. Tool calls from a response cut off by the output limit or by a full context window are not run, since their input may be cut off too.
4. Every event goes through `applyChatEvent` (`src/shared/chat.ts`) in both processes: the main process keeps the transcript for saving, the renderer for display. Streaming deltas are applied in batches once per animation frame. `TranscriptView` re-renders only items whose object changed and updates their element in place, moving keyboard focus back to the same control (`data-focus-key`); items are grouped in chunks of 50 (`CHUNK_SIZE`), and off-screen chunks and items skip layout (`content-visibility: auto`), so a frame at the bottom of a long chat lays out a few dozen chunks rather than every item; finished tool cards and Thinking build their body when first expanded (measurements in `docs/PERFORMANCE.md`). Because off-screen items count at a placeholder height until laid out, the view jumps to the bottom again for a few frames after a chat is opened or an item is added, and stays at the bottom when the scroll area shrinks; the user's own scrolling ends this. The reducer also caps what a tool card keeps (`TRANSCRIPT_LIMITS`): the last 20,000 characters of output (`outputOmittedChars` counts what was left out, over all streamed chunks), the first 2,000 lines and at most 200,000 characters of a diff (`diffOmittedLines`), the first 20,000 characters of a command (`commandOmittedChars`), and the first 20,000 characters of a plan (`textOmittedChars`). The card says what was left out; on an approval card that is a warning that approving applies the whole change. This limits only what is shown and saved in the chat; the tools' results for the model and the change that is applied are not affected, and exports say where content was left out.
5. The chat is saved (debounced 500 ms, immediately after every tool-result batch, and when a task finishes) to `userData/chats/<id>.json`, including the provider-native conversation, so reopened chats continue exactly where they stopped.
6. A short title is generated by the small model after the first message.
7. **Compact chat** (`chat:compact`, `ChatSession.compact`) shortens what is sent without touching what is stored, so the history stays append-only. `conversation.planCompaction()` picks a cut (`llm/compaction.ts`): the latest place that still leaves about 40k characters after it and where the history may start without separating a tool call from its result, which is provider-specific (Anthropic: before an assistant message or a user message that is not a tool result; Chat Completions: anywhere but before a `tool` message; Responses: before a message or a reasoning item, never before a function call or its output, and never right after a reasoning item, whose message or call would otherwise be sent without it). The text before the cut (tool results cut to 1,500 characters, inputs to 600, at most 300k characters in all) goes to the small model, which returns a summary. `applyCompaction(summary, keepFrom)` then stores a `CompactionState { summary, keepFrom }` next to the messages in the saved conversation. From then on each request is built from the summary followed by the messages from `keepFrom`: a separate user message in front of an assistant message, or joined to the first block of a user message (a copy; stored messages are never edited). The Responses path always sends it as a separate user item. A later compaction starts at the previous `keepFrom` and hands the previous summary to the summarizer. `UsageTotals.contextTokens` (input plus cache reads and writes of the last request) drives the status-bar hint; `COMPACT_SUGGESTED_TOKENS` in `src/shared/models.ts` sets when it turns into a suggestion. This is separate from the server-side compaction Claude models do on their own (`compact-2026-01-12`), which the API applies to the request and returns as blocks in the history.

A crash mid-run is survivable the same way. A run saves the chat immediately when it starts (with its new user message) and after each tool batch, and while a run is in progress the saved `resumable` flag is true, so a chat reopened after a crash offers Resume wherever the crash happened: during a model request, while tools ran, or in the 500 ms save debounce before the latest tool calls were written. The save after a tool batch is a checkpoint: it writes only the chat file, not the chat index, and sends no `history:changed`, unless the chat is not in the index yet. The history list (title, time, cost) catches up with the next regular save, at the latest when the run ends. The flag is cleared by the save when the run ends, unless the user stopped it. A conversation that ends with unanswered tool calls is also marked resumable; resuming appends a synthetic failed result for each of them, saying the action may or may not have run, since a result is only recorded once the whole batch finishes and earlier calls in that batch may already have taken effect. Loading also closes tool rows left running or awaiting approval, and stops the typing indicator on an assistant row saved mid-stream. Stopping a run marks it resumable only after its abort handling settles and tool results are paired. `chat:resume` appends a continuation instruction to the model history (not a duplicate visible user request), warning the model to inspect state before retrying interrupted side effects. The `resumable` flag is saved and restored; declining an approval without feedback does not set it. This continues the task from conversation history, not from an exact execution checkpoint, and cannot guarantee that the model never repeats an action.

`ProjectStore.opened()` tracks tabs separately from recent projects. `ChatManager` retains each inactive project's idle session, workspace and shell runner; switching back restores its chat, including stopped-run state. The renderer keeps unsent text and attachments per project in memory and drops them when a tab closes. Switching or closing projects and starting another chat requires the current run to settle first, preventing approvals from crossing workspaces. The interactive terminal restarts on switches. Agent-started background commands survive normal turn completion and project switching, but Stop cancels the active project's background jobs as well as its current foreground command; closing their chat/tab also stops them. Other projects' jobs and the interactive terminal are not cancelled by Stop. Tabs and drafts are not restored after app restart; saved chats remain accessible through history. `project:opened` and `project:close` are part of the typed IPC contract.

## Model providers (`src/main/llm/`)

`Conversation` is the provider-neutral interface: `addUserMessage`, `addToolResults`, `runTurn`, `serialize`. Each implementation stores history in its API's native format, and only records an assistant turn once the request has succeeded, which is what makes it safe for the agent loop to repeat a failed request.

The SDK clients for conversations are created with `maxRetries: 0` (`createAnthropicClient` / `createOpenAIClient`); retries of transient errors are done by the agent loop so they can be shown in the chat (see [Chats and the agent loop](#chats-and-the-agent-loop)). Clients for the small model (chat titles, compaction summaries) are created with 3 silent SDK retries (`BACKGROUND_RETRIES`).

**Anthropic** (`anthropic.ts`, official SDK, `client.beta.messages.stream`):

- History is **append-only**: assistant turns are stored exactly as returned, including thinking, compaction and fallback blocks, because current Claude models reject or ignore edited history.
- Server-side `pause_turn` and `compaction` responses are staged within `runTurn` and included in continuation requests, but not in serialized history until `runTurn` returns successfully. A failed or aborted continuation discards the staged messages, so an agent retry starts from the original history. Successful responses are appended together without rewriting their blocks; the existing five-continuation limit still applies.
- Billable usage accumulates across successful continuation requests, but the reported context size comes only from the final request. A server compaction can therefore reduce the displayed context without subtracting previously billed tokens.
- Features are enabled per model (`claudeCapabilities` in `src/shared/models.ts`) because unsupported parameters are rejected:
  - Opus 5.5 / Sonnet 5.5 (and other current models): adaptive thinking with summarized display, `output_config.effort` (Settings → Effort, default `high`), server-side compaction (`compact-2026-01-12`).
  - Opus 5.5 / Sonnet 5.5: refusal fallback (`fallbacks: "default"`, `server-side-fallback-2026-07-01`).
  - Haiku 4.5 and unknown ids: a plain request.
  - Image input (`images`): Opus 5.5, Sonnet 5.5, Haiku 4.5 and the other known current ids; not unknown ids, since an image the model cannot take is a 400. `acceptsImages(model)` applies it (and allows every OpenAI or compatible id, as before). `ChatManager.send` refuses a message with images for a chat whose model does not accept them, before a chat is created or anything is sent; the composer disables the paperclip and paste with the same message (`imagesNotSupportedMessage`). Images in tool results (browser screenshots) are not gated.
- Prompt caching via top-level `cache_control`, plus an ephemeral breakpoint on the system text and on the last tool, so that prefix can stay cached while the conversation tail moves. The system prompt is built once per chat and includes a project map two levels deep (file counts per folder, and entry points from `package.json`, `pyproject.toml`, `Cargo.toml`, and `go.mod`), capped at 2,500 characters. It is built on the main process, so the walk that counts files below the two shown levels stops after 20,000 entries and shows the counts as lower bounds (`(19028+ files)`); a home folder or a folder of many repositories then takes about 0.2 s instead of minutes. Each completed Anthropic turn appends one local log line (`llm` / `anthropic request`) with cache reads, cache writes, token counts, tool count, system length, and whether the tool-name hash or the system hash changed. Extra tools are sorted by name so MCP tools do not shuffle the prefix. With Settings → Prompt cache on, an idle Claude chat re-sends its last request about every 4 minutes for up to an hour (`ChatSession.scheduleKeepAlive`, `AnthropicConversation.keepCacheWarm`): `max_tokens: 0`, not streamed, the same tools, system, thinking, effort and betas, a placeholder user message at the end (the API rejects a request that ends with the assistant's reply) and the breakpoint on the reply's last block instead of the top-level automatic one. It only reads the cache, which refreshes the entry's 5-minute timer; the next real request then reads it. Its usage is added to the chat, and it stops on the next run, compaction, dispose or a failure.
- Tools are sent with `eager_input_streaming`, so large inputs (file contents) stream as generated. The API then no longer validates them, which is why the agent validates every input itself. A turn whose streamed tool input cannot be parsed is re-issued (up to twice).
- No `temperature` and no forced `tool_choice` (both rejected by current models).

**OpenAI** (`openai_responses.ts`, used when no custom base URL is set and no ChatGPT session is the credential): the Responses API, because GPT-6 models only support function calling in Chat Completions with reasoning turned off (and GPT-6 Astra cannot turn it off). Requests are stateless (`store: false`); reasoning items come back encrypted (`include: ['reasoning.encrypted_content']`) and are sent back unchanged so the model keeps its reasoning across tool calls. The output items are stored as the API returned them, minus the fields the SDK's stream helper adds (`parsed_arguments` on function calls, `parsed` on message text): the API rejects those as input (`toInputItem`, applied when a turn is stored and again when history is sent, so older saved chats are repaired). Reasoning effort follows Settings → Effort, reasoning summaries are shown as "Thinking", and `truncation: 'auto'` drops the oldest items when the context fills up.

**Sign in with ChatGPT** (`codex_auth.ts`, `openai_route.ts`): Settings can sign in with a ChatGPT account for official models. `chatgpt:sign-in` opens `https://auth.openai.com/oauth/authorize` with the public PKCE client and the loopback redirect `http://localhost:1455/auth/callback`. The code is exchanged only when the callback `state` matches that login. A callback with a different state is answered and ignored, so the login keeps waiting. A timeout, a sign-in replaced by a newer attempt, or a failure to bind port 1455 stores nothing. The access token, refresh token, and ChatGPT account id are stored on `settings.json` under `chatgpt`. The two tokens use the same `safeStorage` sealing as API keys. `chatgpt:sign-out` removes the session. The renderer receives `{ signedIn, accountLabel }` and never the tokens.

With no custom base URL, `chooseOpenAIRoute` sends an official chat to the Codex responses backend (`https://chatgpt.com/backend-api/codex`) when the session has an access token and an account id. That includes the case where an API key is also stored. The request sends `Authorization: Bearer` from the session and a `ChatGPT-Account-ID` header. `CodexAuthedConversation` refreshes an access token that expires within 60 seconds, once, before the turn. Turns that need a refresh of the same token share that request. The new tokens are stored only if that refresh token is still the one saved, and a permanent failure clears the session only in that same case. `invalid_grant` and the other permanent refresh failures then fail the turn with `ChatGptSignInRequiredError`. The agent loop does not retry that error. With no session, an API key still uses the Responses API. A non-empty OpenAI-compatible base URL still uses that URL, the API key, and Chat Completions, and does not send the ChatGPT session. Embeddings and the small model (titles, compaction, commit messages) still require the OpenAI API key. A Codex request that the backend rejects is shown as that error. The app does not fall back to the API key for the same turn.

**OpenAI-compatible endpoints** (`openai.ts`, used when Settings → _OpenAI-compatible base URL_ is set, e.g. Ollama, OpenRouter, LM Studio): Chat Completions streaming with function tools, since most compatible servers only implement that API. With no server-side compaction, the oldest turns are left out of each request once the history passes ~100k tokens (estimated from the text, with images at a small fixed size rather than their base64 length); the first user message (the task) and the step in progress (the last assistant message with its tool results) are always kept, and a tool result is never sent without the call it answers (`trimHistory`). Only the copy that is sent is shortened, the stored history is not (chats saved by older versions were shortened when they were saved). Use **Compact chat** to keep the earlier work as a summary instead of losing it.

In both OpenAI paths, tool screenshots are sent as a follow-up user message because tool results cannot carry images. Saved chats record which API their history belongs to (`api: 'responses' | 'chat'`).

**Summary/title model** (`CompletionClient`): selected for the chat's pinned provider, not the current global model selection. Standard provider chats use Claude Haiku 4.5 or GPT-6 Luna according to available keys. Custom Chat Completions chats use their own pinned model on the configured compatible endpoint, rather than assuming it serves GPT-6 Luna. Titles and Compact chat summaries require structured outputs (`output_config.format` / `response_format`) validated by Zod; compatible endpoints must support JSON-schema output. An unsupported summary request reports an error and leaves compaction state unchanged.

A chat keeps its model. The model picker in the composer (or Settings) sets the model for new chats through `settings:update`; it is locked once the chat has started.

MCP servers are configured in Settings as JSON (`mcpServers`). The `McpHub` connects in the background (stdio child processes or Streamable HTTP), caches each server's tools for the synchronous per-turn tool callback, reconnects when the setting changes, and reports per-server status via `mcp:status` for the settings dialog. Names are namespaced and sanitized (`mcp_<server>_<tool>`) so servers cannot collide or forge the name of a built-in tool; a failed server shows its error and the rest keep working.

Project skills are markdown files in `.patch/skills/` (`tools/skills.ts`). When a chat starts, `listSkills` reads the first 4 KB of each (up to 20; the prompt says how many more there are) and the system prompt lists their names and first non-heading lines. The skill list is frozen with the prompt: `load_skill` is offered exactly when the chat's prompt lists skills (`promptListsSkills`), so skills added or removed mid-chat change neither the prompt nor the tools, and the prompt cache stays warm. The model loads the text (up to 20,000 characters, `MAX_SKILL_CHARS`) on demand. The folder goes through `Workspace.resolve`, so a skills folder linked outside the project is ignored, linked files inside it are skipped, and skill names are restricted to file-name characters. The `task` subagent may load skills too.

Rules enforced in code, not only in the prompt:

- `Workspace.resolve` confines every path to the project root. Links are resolved first, also for a path that does not exist yet: its deepest existing part is resolved and the rest appended, so `link/new.txt` through a folder link to somewhere else is refused rather than created outside the project. A link that leads nowhere is refused. `.gitignore` and `.ccignore` are resolved through the same confinement check; external or dangling ignore-file links are ignored rather than read.
- Existing files must be read in the current chat before `edit_file` or `write_file` may change them. The check runs both in `preview` (so an unread file is rejected before the user is asked to approve) and in `run`.
- **Undo.** `edit_file` and `write_file` return `ToolOutput.undo` (`EditUndo`): the project-relative path, the exact previous bytes (`null` when the tool created the file) and the SHA-256 of what was written. It is never shown to the model. `Agent` passes it to `onEditApplied(toolId, edit)`, which `ChatManager` connects to `EditBackups.record` (`tools/edit_backups.ts`, one JSON file per edit in `userData/edit-backups/<chat id>/`, named by a hash of the application-generated tool-card id, newest 50 per chat, deleted with the chat). If that succeeds the `tool-end` event carries `undoable: true` and the card gets `undo: 'available'`. `edit:undo` (`ChatManager.undoEdit`) works only when the chat is idle and the card is `available`; `EditBackups.undo` resolves the path through `Workspace.resolve`, refuses unless the file's current bytes hash to `afterHash` (so later changes are never lost, and edits to one file are undone newest first), writes the bytes back or deletes the created file, and uses the backup up. `ChatSession.editUndone` then emits `tool-undone` (card `undo: 'undone'`), removes the file from `readFiles` so the model has to read it again, and queues a note that is put in front of the next message (or the resume instruction) sent to the model, so the conversation itself stays append-only. The note is saved with the chat until it is sent.
- **Protected files.** `isGuardedPath` (`tools/guard.ts`) lists paths whose edits always need approval (credentials and keys, `.git`, editor/agent folders, shell start-up files, databases, system folders; `.env.example`-style files are exempt). `write_file`, `edit_file` and `apply_patch` declare it with the optional `mustAsk(input, context)` of `AgentTool`, which asks in Auto mode too. A check that throws counts as "no".
- **Secret redaction.** `redactSecrets` (`tools/redact.ts`) replaces private keys, AWS/GitHub/Slack/Anthropic-style tokens, JWTs, quoted credential values and `.env`-style secret lines with `[REDACTED:_____]` in every tool result, summary and error. The file tools refuse input containing the placeholder, so a redacted value is never written back.
- **Permission rules.** `Settings.permissionRules` (`PermissionRule` in `src/shared/settings.ts`, validated by `parsePermissionRules`, edited as JSON in the dialog) are evaluated by `decidePermission` (`agent/permissions.ts`): the first rule whose `context`, `tool` glob and `matches` globs fit wins. `delegate` spawns the named program without a shell, sends `{tool,input,context}` on stdin and takes `allow`/`reject`/`ask` from stdout (15 s; any failure rejects). `ChatManager` passes the `thread` evaluator to the session and the `subagent` one to the subagent tools. `changesToConfirm` asks the user (native dialog) before an `allow` or `delegate` rule is saved.
- Command output is capped (start and end kept); commands are killed with their whole process tree on stop or timeout.

To add a tool: create it with `defineTool` (name, description, Zod schema, `requiresApproval`, optional `preview`, `run`) and add it to `registry.ts` (`CORE_TOOLS`, or a configuration-gated entry in `availableTools`). Tools that need per-chat state (`search_code`, `task`, MCP tools) are passed to the agent as `extra` from `ChatManager`.

## Code search (`src/main/search/`)

`CodeIndex` walks the project (respecting ignore rules, up to _Maximum files to index_), splits text files into overlapping 60-line chunks, embeds them with Voyage `voyage-code-4` through OpenRouter's embeddings endpoint (`openRouterEmbedder`: `input_type` `document` for chunks and `query` for the search text, as Voyage recommends for retrieval; 1024 dimensions, the model's default) and stores Float32 vectors in `userData/indexes/<sha1 of path>.json`. Updates re-embed only files whose size or modification time changed. The index is built on the first `search_code` call, never in the background. Search ranks by cosine similarity, at most two snippets per file. The best 30 of those go to Voyage `rerank-3` through OpenRouter's rerank endpoint (`openRouterReranker`, same key), which picks the final results; if reranking fails (anything but a stop), the results stay in embedding order and the tool output says why. Changing `INDEX_VERSION` or the embedding model rebuilds indexes. Settings shows the current project's index status (`index:status`: files and chunks, or why it is unavailable) and a Reindex button (`index:rebuild`, `CodeIndex.rebuild()`), which clears the index and embeds everything again.

## Chat list (`src/renderer/src/views/sidebar.ts`)

`Sidebar` lists the saved chats from `history:list`, newest first, grouped by day (Today, Yesterday, Previous 7 days, Older), and stays current through the `history:changed` push. `App` adds project navigation above it; New Chat sits above Sessions, and a header button collapses the sidebar with `aria-expanded`. Its footer sums the chats' `ChatSummary.tokens` and `cost`. Its filter narrows by title and project at once (`filterChats`) and then, after a short pause, shows `history:search` results, which also match message text. Deleting and clearing chats stay in the history dialog behind the header's history button. Its foot shows the open chat's `agentFile` and the code index state (`indexStatusLabel`, `src/shared/index_status.ts`), which `App` polls through `index:status` while an index is being built.

The main window follows an OpenCode Desktop-inspired layout: neutral theme tokens, a 48px header with session breadcrumbs, sidebar project navigation, a centered 768px conversation, and model/approval/plan controls mounted into `Composer.controls`. Inter, JetBrains Mono and Material Symbols are bundled with the app (`@fontsource-variable/*`, imported in `main.ts`), since the page's CSP loads nothing remote. `sym()` in `dom.ts` makes a Material Symbols icon, hidden from assistive technology. In the transcript every item is a row with an avatar column; the assistant's avatar is drawn on the first item of its turn (`leads` in `TranscriptView.render`). Tool rows show the tool name, a target and a result chip parsed from the summary (`toolLabel`), and `durationMs`, which `Agent.runTool` measures from the start of the tool's run (after approval) and sends with `tool-end`. The composer turns `@` into a file picker over `files:list` (`Workspace.listFiles`, ignore rules applied, at most 20,000 files) and sends mentions as `@path` at the start of the message (`messageWithMentions`). The status bar's context meter divides the last prompt size by the model's `contextWindow` (`src/shared/models.ts`; none for custom ids).

## Panels (`src/main/panels/`, `src/renderer/src/views/panels.ts`)

- **Terminal**: one interactive shell per project (`node-pty`), rendered with xterm.js. Separate from the agent's commands. The renderer starts it only when a project is open; without one the panel just says "Open a project to use the terminal." The main process still rejects `terminal:start` without a project as a safety net.
- **Browser**: a `<webview>` in the renderer (partition `persist:browser`). When it attaches, the main process receives its `webContents`; `BrowserService` implements the `browser` tool on it (load, console capture, `capturePage` scaled to ≤1280 px).
- **Git**: `simple-git` — status, diff (untracked files shown as additions), commit all, push, discard, discard all, init. `GitService.status` adds per-file line counts (`git diff --numstat --no-renames` against `HEAD`, or the index and working tree before the first commit, parsed by `parseNumstat` in `src/shared/panels.ts`; new files are counted by reading them, up to 2 MB, binary files not), the upstream with ahead/behind counts, and `canPush` (an upstream, or a remote named `origin`). `push` pushes to the upstream or runs `push --set-upstream origin <branch>`; it uses the user's git credentials and runs pre-push hooks, and since the app has no terminal git cannot prompt for a password. `git:suggest-message` sends the diff (cut at 30,000 characters, `MAX_COMMIT_DIFF_CHARS`) and the file list to the small model (`LlmService.smallModelForSettings`, preferring the provider of the model in Settings) and returns a Conventional Commit message (`panels/commit_message.ts`). The renderer shows one hunk of the diff at a time (`diffHunks`). Before the first commit, diffs include staged additions followed by any working-tree patches. Discarding a staged rename restores the original committed file and removes the renamed destination, including staged and unstaged edits to it. While the Git tab is open, it refreshes after each tool call and after an Undo. The status bar shows the current branch from `git:status` (with `*` when files changed) and the Git tab a badge with the number of changed files, refreshed when the project changes, after each run and whenever the Git tab reads a new status. A repository whose root is the home folder or a folder above it counts only when the project is that root (`isRepoAboveHome`); otherwise `git status` would scan the whole user profile.

## Accessibility

- The transcript is re-rendered per streamed chunk, so it is not an `aria-live` region. `TranscriptView.announcer` is a hidden `role="status"` region fed by `newAnnouncements` (`src/shared/announce.ts`): a finished answer (first 300 characters), an approval request, a failed tool, an error or a notice, each once. Opening a saved chat announces nothing.
- Anything that carries meaning only through an icon or color needs a text alternative (`visually-hidden` text or `aria-label`). `h()` gives icon-only buttons their `title` as `aria-label`.
- Colors come from the `--patch-*` tokens at the top of `src/renderer/src/styles.css`, one set per theme; Bootstrap's `--bs-*` variables and button variables point at them. Change the palette there, not in individual rules. Keep `--patch-accent-rgb` comma-separated (Bootstrap uses it in `rgba(var(...), a)`).
- Use Bootstrap's `*-text-emphasis` colors for colored text, not the plain `--bs-info`/`--bs-warning`, which are too light on white.

## Security model

- **Renderer isolation**: `contextIsolation`, `sandbox`, no `nodeIntegration`. Strict CSP (`script-src 'self'`, no remote images or connections).
- **Preload**: exposes only `invoke`/`on` for allow-listed channels.
- **Setting changes that run programs**: before `settings:update` applies a switch to Auto mode (once per app session), a changed `editorCommand`, or a new or changed stdio MCP server (command, arguments, `cwd`, or a new `env` value), the main process shows a native confirmation (`changesToConfirm` in `settings_confirm.ts`). A compromised renderer therefore can't make these changes silently. The dialog names `env` keys, never their values. Removing a server, HTTP servers and switching back to Ask mode don't ask.
- **IPC sender**: every handler (`handle` in `ipc.ts`) answers only calls from the app page's top frame: the built `renderer/index.html` from disk, or the dev server during development (`isAppPageUrl`). Calls from any other frame are refused and logged by channel name.
- **Navigation**: the app window cannot navigate; `http(s)` links and `window.open` go to the system browser. The app page always comes from the built files on disk in a packaged app: the dev server URL (`ELECTRON_RENDERER_URL`, set by `npm run dev`) is only used when the app is not packaged (`renderer_url.ts`).
- **Browser panel**: guests get no preload, no Node, sandboxed, in the `persist:browser` session partition; `will-attach-webview` rejects omitted or different partitions in the main process, so the renderer cannot attach a guest to the app's default session (#34). Popups are denied. A guest can only be attached to `about:blank` or an `http(s)` URL. Every permission request (camera, microphone, location, notifications) is denied. Browser-tool top-level redirects and later page navigation stay on the approved hostname; cross-host destinations need a new tool call. Project `file://` URLs are preapproved only after `confineFileUrl` checks confinement. Once the agent has opened a page, the `persist:browser` session's request filter (`BrowserService.allowsRequest`) also checks every `file://` request, frames and sub-resources included, which never fire `will-navigate`: a project page cannot show a file from outside the project in an `<iframe>` for a screenshot to pass on (#63).
- **Model output**: rendered markdown and diffs pass through DOMPurify; images, embeds, forms and styles are removed from model output (an image URL is a common data-exfiltration channel for prompt injection). Generated UI never uses inline handlers.
- **Secrets**: keys are encrypted at rest when system encryption is available and never sent to the renderer. Plaintext fallback and failed migration are flagged in Settings.
- **Agent**: path confinement, read-before-write, approval for edits and commands by default. Commands still run with the user's permissions; **Auto** mode trusts the model with your shell. Commands on the "allowed without asking" list skip approval only when they contain no shell operator and nothing PowerShell would evaluate (`$`, parentheses, braces). Tools marked `alwaysAsk` (MCP tools and `propose_plan`) and edits to protected files (`mustAsk`) ask even in Auto mode and are never covered by an allow-list; only an explicit `allow` permission rule overrides that. Tool results are redacted before the model sees them (best effort: known token formats and credential-named values).
- **MCP servers**: stdio servers are started with `cross-spawn` (no shell string) and `getDefaultEnvironment()` plus the server's own `env`, so the app's API keys are not passed on. A server's `env` values and HTTP `headers` are encrypted like API keys and only their names reach the renderer. A failed connection, a removed server and quitting close the client and kill the server's process tree (`taskkill /T` on Windows). Tool names are namespaced (`mcp_<server>_<tool>`) so a server cannot claim a built-in tool's name, and results are cut like other tool output.
- **Subagents (`task`, `finder`, `oracle`)**: can only run an allow-list of read-only tools (`read_file`, `list_directory`, `glob`, `grep`, `search_code`, `load_skill`), so they cannot edit, run commands, use the network, call MCP tools, propose a plan or start another subagent. A subagent on the chat's own model is sent the chat's exact system prompt and tool list, so its requests read the prefix the chat already cached instead of writing a new one (#77); its role goes into its first message, and every tool outside the allow-list is a stand-in with the same name, description and schema that only returns an error, so the real tool is never reachable. On another model it gets only the allow-listed tools and its role in the system prompt. Its reads go into its own set, so they do not satisfy the parent's read-before-edit check.
- **Project skills**: the `.patch/skills` folder is resolved through `Workspace.resolve`; a folder linked outside the project is ignored and linked files inside it are skipped. Skill text is prompt text, like `AGENTS.md`.
- **Electron fuses** (`build.electronFuses` in `package.json`, applied when packaging): the packaged app ignores `ELECTRON_RUN_AS_NODE`, `NODE_OPTIONS` and `--inspect` flags, so it can't be turned into a Node runtime or have code injected through them, and it only loads its code from `app.asar`, whose integrity is checked: a changed header stops the app at start, and a changed file stops it when that file is read. Cookies of the browser panel are encrypted on disk. `GrantFileProtocolExtraPrivileges` stays on, because the UI loads ES-module scripts from `file://`.
- **API endpoints** (`src/main/llm/endpoints.ts`, #64): keys and ChatGPT tokens only go to the official endpoints or the base URL set in Settings. The clients always get an explicit base URL (Settings → Claude base URL or OpenAI-compatible base URL, else the official one; the Anthropic client gets no `authToken`), so `ANTHROPIC_BASE_URL`, `OPENAI_BASE_URL`, `ANTHROPIC_AUTH_TOKEN` or an `ant auth login` profile cannot redirect them or add a credential. The `PATCH_TEST_*` hooks the tests use to reach local stand-ins only work in development builds: the main process calls `setPackagedBuild(app.isPackaged)` at start, and until it does the hooks are off, so a missed call fails closed. The same rule covers `ELECTRON_RENDERER_URL` (`renderer_url.ts`, #27). Setting or changing the Claude base URL needs a native confirmation (`settings_confirm.ts`), since the Anthropic key goes there; it must be an http(s) URL, and a bad saved value falls back to the official API.
- **macOS hardened runtime**: the app and helper entitlement files grant only `allow-jit` for V8, not DYLD environment-variable injection or unsigned executable memory. A signed packaged launch on Intel and Apple Silicon remains to be verified (#22, #28).
- **Git panel**: a repository's own `.git/config` can name commands git runs by itself. `GitService` (`panels/git.ts`) runs every call with `core.fsmonitor=false` and neutralizes the clean, smudge and process commands of the filter drivers the repository defines in its local config (`hardenedConfig`), and diffs use `--no-ext-diff --no-textconv`. Filters the user configured globally (such as git-lfs) keep working. Covered by the hostile-repository tests in `panels/git.test.ts`.

### Known limits (reviewed 2026-10-01)

These are accepted limits of the unreleased Patch baseline; each is a trade-off, not an oversight.

- **Network approvals are not a sandbox.** In Ask mode, `fetch_url` and `browser` require approval unless the exact URL hostname matches `allowedNetworkHosts` (empty by default, all ports, subdomains listed separately). Auto mode skips approvals. Fetch and browser top-level cross-host redirects are blocked even in Auto mode; the model must request the destination separately. Before the agent opens a page, and for addresses typed in the panel's address bar, browser navigation is not filtered; after the agent opens a page, link clicks and redirects in the panel stay on that page's host. Browser subresources and Google `web_search` are not filtered by this policy. Approved hosts and search queries can still receive private data. Keep projects with secrets out of chats that read untrusted pages.
- **Editor command.** `editorCommand` is run through a shell with the file path quoted. File names with a double quote or line break are refused, and on macOS and Linux also names with `$`, a backtick or a backslash, which `sh` would still expand inside the quotes. The command itself is the user's own setting; changing it needs a native confirmation, though a compromised renderer can already write to the terminal panel.
- **Tool card ids are the app's own.** `Agent.runTool` gives every tool call a fresh UUID for its card, approval and edit backup. The provider's tool-call id is used only to pair the call with its result in the API request, since some OpenAI-compatible servers reuse ids across turns.
- **Undo is locked against sending.** `ChatManager.undoEdit` counts as busy until the file is restored and the note for the model is queued and saved, so a message, resume, compact or chat/project switch cannot start in between. The pending note is saved with the chat (`SavedChat.pendingNotes`) and survives a restart; it is sent, and cleared, with the next message or resume.
- **Log redaction is pattern-based.** Recognized `sk-`, `gsk_`, `xai-` and `AIza` keys, bearer tokens and named API-key/authorization fields are redacted; unrecognized secret formats can still appear in error messages. Review logs before sharing.
- **IPC handlers trust the renderer's arguments.** The renderer is sandboxed, has a strict CSP and only shows sanitized model output, and pages in the browser panel have no preload, so they cannot call IPC. Handlers that take paths (`git:*`, file tools) still confine them to the project with `Workspace.resolve`. The renderer's IPC surface is powerful by design: the terminal panel types into a real shell, so a compromised renderer still amounts to code execution. Settings that choose MCP commands, the editor command and Auto mode need a native confirmation (see Security model), and handlers only answer the app page's top frame; runtime payload validation (#32) is open.
- **Retries repeat the whole request.** A failure in the middle of a long answer discards the streamed text and asks again, so the tokens of the failed attempt may be billed. On the Anthropic path, this also repeats any server-side compaction or `pause_turn` continuations from the failed attempt; their responses are not left in saved model history. Only errors that usually pass are retried; a wrongly classified error costs at most 4 extra requests (about 30 seconds) before it is shown.
- **A compaction is a lossy summary written by the small model.** Details can be missed or wrong, and the model then works from the summary as if it were what happened; the unedited history stays in the chat file but is no longer sent. The summarizing request is not included in the token and cost totals (`CompletionClient` reports no usage). The first request after a compaction misses the prompt cache. Context size is only known after a request, and the 150k suggestion is one value for every model, not a limit of the model in use (custom endpoints can have far smaller windows).
- **Undo covers the edit tools only.** Changes made by commands the assistant ran, or by anything else, have no backup. A backup is a plaintext copy of the file on disk in the app's data folder (until the chat is deleted or 50 newer edits push it out), which matters for projects with secrets. The pending model notification is saved with the chat and delivered on the next Send or Resume, including after a restart.
- **Local logs can name paths.** `logs/app.log.jsonl` never holds chat history or API keys (keys and tokens are redacted), but error messages such as "Folder not found: …" can contain file paths. The files stay on the machine and rotate at 512 KB; nothing is sent anywhere.
- **Project instructions, `AGENTS.md` and project skills** are prompt text, not trusted configuration: they are added to the system prompt (skills when loaded), so a malicious repository can steer the model. Approvals still apply to edits and commands.
- **MCP servers run with the user's permissions.** A stdio server is a program the user configured; approval covers each tool call, not what the server does on its own. Stdio servers start in the project that was open when they connected and are not restarted on a project switch. Renaming a server in Settings drops its stored secrets (#23).
- **Git panel commits and pushes run the repository's hooks.** Viewing status and diffs or discarding a file runs nothing the repository's config names, but **Commit** runs its commit hooks and **Push** its pre-push hook (including a local `core.hooksPath`), as any git client does; tools like husky depend on that. A push goes to whatever URL the repository's `origin` or upstream names, with the user's credentials. **Generate** sends the uncommitted diff to the configured model provider, like a chat would. A repository whose filter drivers are defined in its local config (for example `git lfs install --local`) is shown and committed without those filters in the Git panel.
- **Release signing**: Windows releases require signing credentials and valid Authenticode signatures on both the app and installer before publishing; checksums accompany the installer. Local development builds may remain unsigned. Signing credentials have not been provisioned, so releases are blocked (#26); macOS entitlement changes still need signed packaged testing (#28, #22).

## Tests

- `npm run test:unit` — Vitest unit tests next to the code (`*.test.ts`). The provider tests run the real SDKs against a local mock HTTP server (`llm/test_server.ts`).
- `npm run test:e2e` — builds the app and drives it with Playwright's Electron support, using a throwaway profile and mock APIs: Claude (`tests/e2e/mock_claude.ts`, enabled by `PATCH_TEST_ANTHROPIC_URL`) and OpenAI (`tests/e2e/mock_openai.ts`, enabled by `PATCH_TEST_OPENAI_URL`, used only when no custom base URL is set so the Responses API path runs). These hooks, and `PATCH_TEST_CODEX_URL` / `PATCH_TEST_CODEX_TOKEN_URL` for ChatGPT sign-in, only work when the app is not packaged; unit tests that use them call `setPackagedBuild(false)`. Covers window security, settings, a full tool-using chat with approval on both providers (including the encrypted reasoning round trip), the UI, the panels, retries of rate limits and overloads (the Claude mock can script failures with `Retry-After`), the local error log and Help menu, stopping and resuming long runs (the mock can hold an answer open until Stop, and `launchApp({}, { userData })` restarts on the same profile), killing the app mid-run and resuming from whatever it had saved (`RunningApp.kill()` ends the whole process tree, as a crash would), switching between open projects, very large tool results, the transcript view (opening a long chat at its end, a tall approval card staying in view, focus after Undo), undoing approved edits, Compact chat, image attachments, MCP tools, plan mode, per-project allow-lists, project skills, the `task` subagent, the single-instance lock, the terminal without a project, and the documentation screenshots with text contrast checks. The chat list, the header model picker and the status-bar branch have no e2e tests yet. Closing the app or a mock server fails with a clear error after 20 s and 5 s instead of hanging until the hook timeout. The harness also captures the main process's stderr, so tests can assert that no IPC handler errors were logged.

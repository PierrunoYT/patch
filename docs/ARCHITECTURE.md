# Architecture

Patch is an Electron app written in TypeScript and built with electron-vite. All logic that touches the file system, the network, API keys or child processes runs in the **main process**. The **renderer** is a sandboxed page without Node.js access that talks to the main process only through a typed IPC contract.

```
┌──────────────────────── main process (Node) ─────────────────────────┐
│ index.ts          wiring, IPC handlers                                │
│ settings.ts       settings, keys, ChatGPT session (safeStorage)       │
│ projects.ts       recent projects, per-project instructions           │
│ chat_manager.ts   active chat, autosave  ──▶ chat_store.ts            │
│ agent/            agent loop, chat session, system prompt             │
│ llm/              Anthropic + OpenAI conversations, small-model calls │
│ tools/            read/edit/write/grep/list, run_command, web, browser│
│ search/           embeddings index for search_code                    │
│ panels/           terminal (node-pty), git (simple-git), browser      │
└───────────────▲──────────────────────────────────────────────────────┘
                │ typed IPC (src/shared/ipc.ts)
┌───────────────┴── preload (sandboxed) ──┐   ┌── <webview> guest ──────┐
│ window.api.invoke / window.api.on,       │   │ pages opened in the     │
│ allow-listed channels only               │   │ browser panel; no Node, │
└───────────────▲──────────────────────────┘   │ no preload             │
┌───────────────┴── renderer (no Node) ────┐   └─────────────────────────┘
│ app.ts, views/ (transcript, composer,     │
│ sidebar, dialogs, panels), markdown.ts    │
│ (DOMPurify)                               │
└──────────────────────────────────────────┘
```

## IPC contract

`src/shared/ipc.ts` declares every channel:

- `InvokeApi` — renderer → main request/response (`window.api.invoke('settings:get')`). The renderer's arguments arrive as untyped data, so `handle()` (`src/main/ipc.ts`) parses them with the channel's zod schema from `src/main/ipc_schemas.ts` before the handler runs: argument count, types, enums (image types, secret names), numeric ranges (terminal size) and size caps are checked, `chat:decide` needs a real boolean `approved`, and a refused call names the channel and the first problem, never the value (#32).
- `EventMap` — main → renderer pushes (`window.api.on('chat:event', …)`). Every `chat:event` carries an increasing `seq`, and each snapshot the main process sends or returns carries the `seq` of the last event it already includes. The renderer registers its chat listeners before its start-up requests, keeps what arrives meanwhile, uses the newer of the requested and any pushed snapshot (`newerSnapshot`) and applies only events newer than it (`chatEventApplies`), because Electron drops messages that arrive while no listener exists (#192).

Handlers (`src/main/ipc.ts`, `handle` / `send`) and the preload bridge are typed from these maps, so a renamed channel or changed payload fails to compile. The preload forwards only channels listed in `INVOKE` / `EVENTS`; those lists are `Record<Channel, true>` so forgetting a new channel is also a compile error.

## Chats and the agent loop

1. The renderer calls `chat:send`. `ChatManager` creates a `ChatSession` on the first message, fixing the chat's project, model and system prompt, and returns as soon as the session starts. Setup errors (no project, missing key) come back immediately.
2. `Agent.send` (`src/main/agent/agent.ts`) adds the user message and runs turns:
   - The tool list is rebuilt at the start of every turn (`ChatManager` passes `tools: () => …`), so a tool that becomes available while a chat is open, such as `search_code` after an OpenRouter key is saved, is offered from the next turn on. The system prompt is not rebuilt; it stays byte-identical for prompt caching and tells the model to use optional tools only when currently offered. When the chat starts, `agent/agent_file.ts` reads `AGENTS.md` (else `CLAUDE.md`, capped at 20,000 characters) from the project root into the prompt, before the per-project instructions. `ChatSnapshot.agentFile` carries its name so the status bar can show that it is loaded; a saved chat keeps the file it started with.
   - `conversation.runTurn` streams the model's answer (text and summarized thinking are forwarded as `chat:event`s).
   - A request that fails for a reason that usually passes is repeated by the agent loop (`runTurnWithRetries`), not by the provider SDKs: their clients are created with `maxRetries: 0` for conversations (the small-model clients for titles and compaction summaries get 3 silent SDK retries, `BACKGROUND_RETRIES`). `agent/retry.ts` decides from the error's shape, so it covers Anthropic, OpenAI and compatible endpoints: HTTP 408, 429 and 5xx (including Anthropic's 529), errors sent inside a stream after a 200 response (`overloaded_error`, `api_error`, `rate_limit_error`, `server_error`, read from the most specific type or code the SDK puts on the error, since the outer type is just `error`) and connection problems (`ECONNRESET`, timeouts, DNS failures, SDK connection errors). Not retried: 501 and 505, other 4xx, an out-of-quota 429, a refused connection (nothing is listening, e.g. Ollama not started), aborts and anything else. Up to 4 retries wait about 2, 4, 8 and 16 seconds (±25%), or the provider's `Retry-After` / `retry-after-ms` when given, but never less than a second (#247); a request to wait more than 60 seconds is not retried, and the chat is left resumable (`isTransientError`). Each retry adds a notice to the chat ("Rate limited (429). Retrying in 2 s (retry 1 of 4)…"), discards the text the failed attempt had streamed, and can be stopped during the wait. A conversation only records a turn once it has succeeded, so repeating a request cannot duplicate history; the last error is shown as before once the retries are used up.
   - For each tool call: validate the input against the tool's Zod schema (a failure names the missing fields and the fields received, and is returned to the model as an error result) → ask the permission rules (`decidePermission`, `agent/permissions.ts`; `reject` answers the model without running, `allow` skips ordinary approval but not a per-call `mustAsk` safety check, `ask` forces approval) → build a preview (diff, command, URL, or an MCP call's arguments as JSON) → if the tool needs approval (`mustAsk` for this call, which may be asynchronous because `fetch_url` and `browser` resolve the host first, or, absent a rule, `alwaysAsk` or `requiresApproval` in **Ask** mode when the call is not pre-approved), wait for `chat:decide` → run it. Consecutive calls to `parallelSafe` tools run with `Promise.all`; every other call runs alone after them, and results keep the order of the calls. The result text, summary and errors pass through `redactSecrets` (`tools/redact.ts`) before they are returned to the model or emitted. The `isPreApproved` callback that `ChatManager` passes to each session checks shell commands against `allowedCommands` (the global list in Settings plus the chat's project's own list from `projects.json`, `mergeAllowLists`, both read on every call so changes apply to open chats) (whole-word prefix match; never for a command containing `; & | < >`, a backtick, `$`, `(`, `)`, `{`, `}` or a line break, because PowerShell runs `(...)` and `{...}` even inside a program's arguments) and never when an argument writes a file or runs a program (`--output`, `-o`/`-O`, `--exec`, `find -exec`/`-delete` and similar, `RISKY_ARGUMENTS` in `agent/allowed_commands.ts`, #233), fetch/browser hostnames against `allowedNetworkHosts` (global plus project, the same way), and local browser files against workspace confinement. File edits always ask in Ask mode.
   - All results of a turn go back to the model together, then the next turn starts. The loop ends when the model answers without tool calls (or after 200 turns).
3. Declining **with** feedback sends the feedback to the model as the tool result and continues; declining **without** feedback stops the task. Stopping (`chat:stop`) aborts the request and running commands. Every tool call always gets a result, even when skipped or stopped, or when it came with a refusal, so the history stays valid for the API. Tool calls from a response cut off by the output limit or by a full context window are not run, since their input may be cut off too.
4. Every event goes through `applyChatEvent` (`src/shared/chat.ts`) in both processes: the main process keeps the transcript for saving, the renderer for display. Streaming deltas are applied in batches once per animation frame. `TranscriptView` re-renders only items whose object changed and updates their element in place, moving keyboard focus back to the same control (`data-focus-key`); items are grouped in chunks of 50 (`CHUNK_SIZE`), and off-screen chunks and items skip layout (`content-visibility: auto`), so a frame at the bottom of a long chat lays out a few dozen chunks rather than every item; finished tool cards and Thinking build their body when first expanded (measurements in `docs/PERFORMANCE.md`). Because off-screen items count at a placeholder height until laid out, the view jumps to the bottom again for a few frames after a chat is opened or an item is added, and stays at the bottom when the scroll area shrinks; the user's own scrolling ends this. The reducer also caps what a tool card keeps (`TRANSCRIPT_LIMITS`): the last 20,000 characters of output (`outputOmittedChars` counts what was left out, over all streamed chunks), the first 2,000 lines and at most 200,000 characters of a diff (`diffOmittedLines`), the first 20,000 characters of a command (`commandOmittedChars`), and the first 20,000 characters of a plan (`textOmittedChars`). The card says what was left out; on an approval card that is a warning that approving applies the whole change. This limits only what is shown and saved in the chat; the tools' results for the model and the change that is applied are not affected, and exports say where content was left out.
5. The chat is saved (debounced 500 ms, immediately after every tool-result batch, and when a task finishes) to `userData/chats/<id>.json`, including the provider-native conversation, so reopened chats continue exactly where they stopped.
6. A short title is generated by the small model after the first message.
7. **Compact chat** (`chat:compact`, `ChatSession.compact`) shortens what is sent without touching what is stored, so the history stays append-only. `conversation.planCompaction()` picks a cut (`llm/compaction.ts`): the latest place that still leaves about 40k characters after it and where the history may start without separating a tool call from its result, which is provider-specific (Anthropic: before an assistant message or a user message that is not a tool result; Chat Completions: anywhere but before a `tool` message; Responses: before a message or a reasoning item, never before a function call or its output, and never right after a reasoning item, whose message or call would otherwise be sent without it). The text before the cut (tool results cut to 1,500 characters, inputs to 600, at most 300k characters in all) goes to the small model, which returns a summary. `applyCompaction(summary, keepFrom)` then stores a `CompactionState { summary, keepFrom }` next to the messages in the saved conversation. From then on each request is built from the summary followed by the messages from `keepFrom`: a separate user message in front of an assistant message, or joined to the first block of a user message (a copy; stored messages are never edited). The Responses path always sends it as a separate user item. A later compaction starts at the previous `keepFrom` and hands the previous summary to the summarizer. `UsageTotals.contextTokens` (input plus cache reads and writes of the last request) drives the status-bar hint; `COMPACT_SUGGESTED_TOKENS` in `src/shared/models.ts` sets when it turns into a suggestion. This is separate from the server-side compaction Claude models do on their own (`compact-2026-01-12`), which the API applies to the request and returns as blocks in the history.

A crash mid-run is survivable the same way. A run saves the chat immediately when it starts (with its new user message) and after each tool batch, and while a run is in progress the saved `resumable` flag is true, so a chat reopened after a crash offers Resume wherever the crash happened: during a model request, while tools ran, or in the 500 ms save debounce before the latest tool calls were written. The save after a tool batch is a checkpoint: it writes only the chat file, not the chat index, and sends no `history:changed`, unless the chat is not in the index yet. A checkpoint serializes the chat at once and writes the file in the background (`writeJsonLater` in `storage/json_file.ts`: one write per chat at a time, in order, through a temporary file and a rename); the regular saves are synchronous and replace a checkpoint that has not landed. A crash in the few milliseconds before a checkpoint lands resumes from the save before it. The history list (title, time, cost) catches up with the next regular save, at the latest when the run ends. The flag is cleared by the save when the run ends, unless the user stopped it. A conversation that ends with unanswered tool calls is also marked resumable; resuming appends a synthetic failed result for each of them, saying the action may or may not have run, since a result is only recorded once the whole batch finishes and earlier calls in that batch may already have taken effect. Loading also closes tool rows left running or awaiting approval, and stops the typing indicator on an assistant row saved mid-stream. Stopping a run marks it resumable only after its abort handling settles and tool results are paired. `chat:resume` appends a continuation instruction to the model history (not a duplicate visible user request), warning the model to inspect state before retrying interrupted side effects. The `resumable` flag is saved and restored; declining an approval without feedback does not set it. This continues the task from conversation history, not from an exact execution checkpoint, and cannot guarantee that the model never repeats an action.

`ProjectStore.opened()` tracks tabs separately from recent projects. `ChatManager` retains each inactive project's idle session, workspace and shell runner; switching back restores its chat, including stopped-run state. The renderer keeps unsent text and attachments per project in memory and drops them when a tab closes. Switching or closing projects and starting another chat requires the current run to settle first, preventing approvals from crossing workspaces. The interactive terminal restarts on switches. Agent-started background commands survive normal turn completion and project switching, but Stop cancels the active project's background jobs as well as its current foreground command; closing their chat/tab also stops them. Other projects' jobs and the interactive terminal are not cancelled by Stop. A command's leftovers (`npm run dev &`) are killed too: a foreground command's once it finishes, a background command's when it is stopped. On POSIX that signals the command's process group; Windows has no groups, and `taskkill /T` cannot walk the tree of a shell that has exited, so `tools/shell_leftovers.ts` lists the processes and kills those whose parent chain leads to the shell's pid, created while the shell lived (a pid reused later is not touched). A foreground command does this without delaying its result. These kills, container `rm -f` and `taskkill` run asynchronously so they never block the main process; quitting waits for them (`commandStopsSettled`, #112). On Windows a stop counts as settled only once the stopped shell has exited (at most 5 s), because its folder stays busy until then, and a shell killed before its `spawn` event gets a leftover sweep too, since it may already have started a program that holds its pipes (#50). Tabs and drafts are not restored after app restart; saved chats remain accessible through history. `project:opened` and `project:close` are part of the typed IPC contract.

Project-change side effects compare the stored active paths before and after opening, closing or removing a project. The main process stops the interactive terminal only when that path changes; the renderer likewise resets terminal/Git state only on a real project change. `ChatManager.projectChanged` does not republish an unchanged project's snapshot, so clicking the active tab, reopening its current chat, or closing another tab preserves expanded transcript sections and scroll position. Opening a different chat within that project changes the transcript but keeps the terminal and commit draft. Closing the last project publishes the empty snapshot after its session is discarded.

`ChatManager.open` resolves the saved chat's target workspace and prepares its provider conversation, session and workspace-bound shell without changing the active or parked state. Existing retained sessions are reused; newly restored sessions enter `liveSessions` only after they are installed. A missing provider key or a session-construction error therefore leaves the current project and chat untouched. Session factories accept explicit target resources so restoring a different project's chat cannot accidentally bind its tools to the current project's workspace. The `history:open` handler sends the current project in `finally`. If the active project actually changed, it runs `projectSwitched` like opening, closing and removing a project do: MCP servers that use `${project}` reconnect for the new project, and the terminal and the agent's browser reset (#241).

## Claude Code chats (`src/main/agent/claude_code*.ts`)

A chat on a `claude-code/…` model is answered by the user's installed Claude Code, not by Patch's loop. The SDK decisions below follow the official [TypeScript SDK](https://code.claude.com/docs/en/agent-sdk/typescript), [permissions](https://code.claude.com/docs/en/agent-sdk/permissions), [hooks](https://code.claude.com/docs/en/hooks) and [sandboxing](https://code.claude.com/docs/en/sandboxing) documentation. It plugs in through the `createAgent` seam of `ChatSession` (`session.ts`): `ClaudeCodeAgent` gets the chat's hooks (`requestApproval`, `emit`, `onCheckpoint`) and implements the same `ChatAgent` surface (`send`, `resume`, `compact`, `totals`). `ClaudeCodeConversation` stores only the Claude Code `sessionId` and the session's last usage totals; its messages stay empty and the transcript is the saved chat.

- The SDK is imported from `@anthropic-ai/claude-agent-sdk/core` (types and `query`), loaded with a dynamic import on the first Claude Code message. It is a dev dependency that electron-vite bundles, while the Claude Code program is not bundled: `findClaudeCode` (`claude_code_launch.ts`) runs the path from Settings (absolute, else refused), else `claude.exe` (Windows) or `claude` from `PATH` or the install folder. Nothing runs through a shell.
- Each message is one `query()` with `resume` set to the saved session. The SDK prompt is a single user message (text, plus images as base64). `pathToClaudeCodeExecutable` and `env` come from `claudeCodeLaunch` (`ChatManager`), read on every message. The environment turns off Claude Code's non-essential traffic; an API key is forwarded to `ANTHROPIC_API_KEY` with `ANTHROPIC_BASE_URL` set to the chat's base URL, never an inherited one.
- `ClaudeCodeAgent.run` owns the query: the query and its listeners are cleaned up in `finally`, and a stop (the abort signal) interrupts the run, aborts the SDK's controller and closes the query. A run that ends without a result, or whose result is an error, throws; a missing session (the file was deleted, or the chat came from another computer) clears the session and its usage and reports an error that asks the user to send again, without retrying. A `conversation_reset` (from `/clear`) switches to the new session id.
- Permissions: a `PreToolUse` hook returns `ask` for MCP tools, `ExitPlanMode` and a Bash call with `dangerouslyDisableSandbox`, and `canUseTool` shows the approval card for those and for every call Claude Code asks about. In Auto mode `canUseTool` allows the rest, but not while the chat is in plan mode before an approved `ExitPlanMode`, whose session-scoped mode change is the only suggestion returned. Declining with no feedback interrupts the turn; a pending approval resolves as declined when its signal aborts (`ChatSession.waitForApproval`).
- Transcript: `TurnView` turns stream events, complete assistant and user messages, and subagent (`parent_tool_use_id`) messages into the usual chat events. Tool cards are shown once and closed when the query ends; a streamed answer is replaced by its complete text; thinking that did not stream is shown from the complete message.
- Usage: a result reports the session's totals so far, cumulative across resumed runs and subagents, so `addUsage` adds the growth since the last report to the chat's totals, counts a new session (or a lower total) in full, and skips an error result with zero usage so the baseline is kept. Requests are counted once per assistant message id.
- Compaction is Claude Code's own (`/compact` in the resumed session); Patch's summarizer does not run for these chats. Retries are Claude Code's: its `api_retry` messages are shown as notices, and Patch does not repeat a run.

## Model providers (`src/main/llm/`)

`Conversation` is the provider-neutral interface: `addUserMessage`, `discardLastUserMessage`, `addToolResults`, `runTurn`, `serialize`. Each implementation stores history in its API's native format, and only records an assistant turn once the request has succeeded, which is what makes it safe for the agent loop to repeat a failed request. The one exception to append-only is a user message the API never accepted: when the first request of a send fails with 400 or 413, `Agent.send` calls `discardLastUserMessage()` so the refused message (an image the model cannot take, a request over the size limit) is not sent again with every later request (#240). To keep such refusals rare, `ChatManager.send` runs the attached images through `checkUserImages` (`llm/images.ts`: media type from the first bytes, about 18 MB in all), and `Agent` passes tool-result images through `withoutImages` for a model where `acceptsImages` is false.

The SDK clients for conversations are created with `maxRetries: 0` (`createAnthropicClient` / `createOpenAIClient`); retries of transient errors are done by the agent loop so they can be shown in the chat (see [Chats and the agent loop](#chats-and-the-agent-loop)). Clients for the small model (chat titles, compaction summaries) are created with 3 silent SDK retries (`BACKGROUND_RETRIES`).

The built-in catalog gives Claude Haiku 5.5 and Claude Fable 5.1 1M-token context windows and GPT-6.1 Sol a 1.05M-token context window. Legacy Claude Haiku 4.5 and GPT-6 Sol remain recognized so existing settings and saved chats continue to work.

**Anthropic** (`anthropic.ts`, official SDK, `client.beta.messages.stream`):

- History is **append-only**: assistant turns are stored exactly as returned, including thinking, compaction and fallback blocks, because current Claude models reject or ignore edited history.
- Server-side `pause_turn` and `compaction` responses are staged within `runTurn` and included in continuation requests, but not in serialized history until `runTurn` returns successfully. A failed or aborted continuation discards the staged messages, so an agent retry starts from the original history. Successful responses are appended together without rewriting their blocks; the existing five-continuation limit still applies. A turn still paused after the fifth continuation returns stop reason `paused`: the agent shows "The model paused its turn too many times" and records the outcome `paused`, which a subagent reports as unfinished instead of as its answer (#180).
- Billable usage accumulates across successful continuation requests, but the reported context size comes only from the final request. A server compaction can therefore reduce the displayed context without subtracting previously billed tokens.
- Features are enabled per model (`claudeCapabilities` in `src/shared/models.ts`) because unsupported parameters are rejected:
  - Fable 5.1, Opus 5.5, Sonnet 5.5 and Haiku 5.5: adaptive thinking with summarized display, `output_config.effort` (Settings → Effort) and server-side threshold compaction (`compact-2026-01-12`). Anthropic's compatibility list explicitly includes Haiku 5.5.
  - Fable 5.1, Opus 5.5 and Sonnet 5.5: refusal fallback (`fallbacks: "default"`, `server-side-fallback-2026-07-01`). Haiku 5.5 does not enable refusal fallback.
  - Haiku 4.5 and unknown ids: a plain request.
  - Image input (`images`): Fable 5.1, Opus 5.5, Sonnet 5.5, Haiku 5.5, Haiku 4.5 and the other known current ids; not unknown ids, since an image the model cannot take is a 400. `acceptsImages(model)` applies it (and allows every OpenAI or compatible id, as before). `ChatManager.send` refuses a message with images for a chat whose model does not accept them, before a chat is created or anything is sent; the composer disables the paperclip and paste with the same message (`imagesNotSupportedMessage`). Images in tool results (browser screenshots) are not gated.
- Prompt caching via top-level `cache_control`, plus an ephemeral breakpoint on the system text and on the last tool, so that prefix can stay cached while the conversation tail moves. The system prompt is built once per chat and includes a project map two levels deep (file counts per folder, and entry points from `package.json`, `pyproject.toml`, `Cargo.toml`, and `go.mod`), capped at 2,500 characters. It is built on the main process, so the walk that counts files below the two shown levels stops after 20,000 entries and shows the counts as lower bounds (`(19028+ files)`); a home folder or a folder of many repositories then takes about 0.2 s instead of minutes. Each completed Anthropic turn appends one local log line (`llm` / `anthropic request`) with cache reads, cache writes, token counts, tool count, system length, and whether the tool-name hash or the system hash changed. Extra tools are sorted by name so MCP tools do not shuffle the prefix. With Settings → Prompt cache on, an idle Claude chat re-sends its last request about every 4 minutes for up to an hour (`ChatSession.scheduleKeepAlive`, `AnthropicConversation.keepCacheWarm`): `max_tokens: 0`, not streamed, the same tools, system, thinking, effort and betas, a placeholder user message at the end (the API rejects a request that ends with the assistant's reply) and the breakpoint on the reply's last block instead of the top-level automatic one. It only reads the cache, which refreshes the entry's 5-minute timer; the next real request then reads it. Its usage is added to the chat, and it stops on the next run, compaction, dispose or a failure.
- `edit_file` opts into `strictInput`: for Claude models with `claudeCapabilities.strictTools` (Fable 5.1, Opus 5.5, Sonnet 5.5, Haiku 5.5, the other known current generation and Haiku 4.5), its definition uses `strict: true` and omits `eager_input_streaming`. The API enforces required fields and types, including in batched calls, without forcing tool use or disabling parallel calls. The SDK's `zodOutputFormat` schema transformation moves unsupported constraints such as `minLength` into descriptions; the agent still validates the original Zod schema before preview or execution. Same-model subagent stand-ins retain the flag to keep the tool prefix identical. MCP JSON Schemas never opt in. See [strict tool use](https://platform.claude.com/docs/en/agents-and-tools/tool-use/strict-tool-use) and [schema limitations](https://platform.claude.com/docs/en/build-with-claude/structured-outputs#json-schema-limitations).
- Other tools and unknown Claude ids keep `eager_input_streaming`, so large inputs (file contents) stream as generated without API validation. The agent validates every input itself, regardless of provider strict mode. A turn whose streamed tool input cannot be parsed is re-issued at once (up to twice). Only that case: a connection dropped mid-stream goes to the agent loop's retry, which waits and shows the retry in the chat (#173).
- No `temperature` and no forced `tool_choice` (both rejected by current models).

**OpenAI** (`openai_responses.ts`, used when no custom base URL is set and no ChatGPT session is the credential): the Responses API, because GPT-6 models only support function calling in Chat Completions with reasoning turned off (and GPT-6 Astra cannot turn it off); GPT-6.1 Sol likewise uses Responses for tool calling. Requests are stateless (`store: false`); reasoning items come back encrypted (`include: ['reasoning.encrypted_content']`) and are sent back unchanged so the model keeps its reasoning across tool calls. The output items are stored as the API returned them, minus the fields the SDK's stream helper adds (`parsed_arguments` on function calls, `parsed` on message text): the API rejects those as input (`toInputItem`, applied when a turn is stored and again when history is sent, so older saved chats are repaired). Reasoning effort follows Settings → Effort, reasoning summaries are shown as "Thinking", and `truncation: 'auto'` drops the oldest items when the context fills up.

**Sign in with ChatGPT** (`codex_auth.ts`, `openai_route.ts`): Settings can sign in with a ChatGPT account for official models. `chatgpt:sign-in` opens `https://auth.openai.com/oauth/authorize` with the public PKCE client and the loopback redirect `http://localhost:1455/auth/callback`. The code is exchanged only when the callback `state` matches that login. A callback with a different state is answered and ignored, so the login keeps waiting. A timeout, a sign-in replaced by a newer attempt, or a failure to bind port 1455 (on 127.0.0.1 and, where available, ::1, so `localhost` reaches the server either way) stores nothing. The access token, refresh token, and ChatGPT account id are stored on `settings.json` under `chatgpt`. The two tokens use the same `safeStorage` sealing as API keys. `chatgpt:sign-out` removes the session. The renderer receives `{ signedIn, accountLabel }` and never the tokens.

With no custom base URL, `chooseOpenAIRoute` sends an official chat to the Codex responses backend (`https://chatgpt.com/backend-api/codex`) when the session has an access token and an account id. That includes the case where an API key is also stored. The request sends `Authorization: Bearer` from the session and a `ChatGPT-Account-ID` header. `CodexAuthedConversation` refreshes an access token that expires within 60 seconds, once, before the turn. Turns that need a refresh of the same token share that request. The new tokens are stored only if that refresh token is still the one saved, and a permanent failure clears the session only in that same case. `invalid_grant` and the other permanent refresh failures then fail the turn with `ChatGptSignInRequiredError`. The agent loop does not retry that error. With no session, an API key still uses the Responses API. A non-empty OpenAI-compatible base URL still uses that URL, the API key, and Chat Completions, and does not send the ChatGPT session. Embeddings and the small model (titles, compaction, commit messages) still require the OpenAI API key. A Codex request that the backend rejects is shown as that error. The app does not fall back to the API key for the same turn.

`LlmService.build` selects the Responses backend for new and restored chats from the current credentials. Codex requests omit `truncation`, which the subscription backend rejects with HTTP 400; platform requests retain `truncation: 'auto'`. Both keep `store: false` and encrypted reasoning. The backend is not persisted in the conversation, so reopening a chat after signing in or out follows the current route. Subscription requests send the full history or the saved compaction summary and retained items; Patch does not silently discard older items locally.

**OpenAI-compatible endpoints** (`openai.ts`, used when Settings → _OpenAI-compatible base URL_ is set, e.g. Ollama, OpenRouter, LM Studio): Chat Completions streaming with function tools, since most compatible servers only implement that API. With no server-side compaction, the oldest turns are left out of each request once the history passes ~100k tokens (estimated from the text, with images at a small fixed size rather than their base64 length); the first user message (the task) and the step in progress (the last assistant message with its tool results) are always kept, and a tool result is never sent without the call it answers (`trimHistory`). Only the copy that is sent is shortened, the stored history is not (chats saved by older versions were shortened when they were saved). Use **Compact chat** to keep the earlier work as a summary instead of losing it.

In both OpenAI paths, tool screenshots are sent as a follow-up user message because tool results cannot carry images. Saved chats record which API their history belongs to (`api: 'responses' | 'chat'`).

**Summary/title model** (`CompletionClient`): selected for the chat's pinned provider, not the current global model selection. Standard provider chats use Claude Haiku 5.5 or GPT-6 Luna according to available keys. The OpenAI `mid` subagent choice uses GPT-6.1 Sol; the Anthropic `small` choice and `finder` use Haiku 5.5. Custom Chat Completions chats use their own pinned model on the configured compatible endpoint, rather than assuming it serves GPT-6 Luna. Titles and Compact chat summaries require structured outputs (`output_config.format` / `response_format`) validated by Zod; compatible endpoints must support JSON-schema output. An unsupported summary request reports an error and leaves compaction state unchanged. Haiku 4.5 and GPT-6 Sol remain recognized for restored chats and retain their existing price estimates.

A chat keeps its model. The model picker in the composer (or Settings) sets the model for new chats through `settings:update`; it is locked once the chat has started.

Project skills are markdown files in `.patch/skills/` (`tools/skills.ts`). When a chat starts, `listSkills` reads the first 4 KB of each (up to 20; the prompt says how many more there are) and the system prompt lists their names and first non-heading lines. The skill list is frozen with the prompt: `load_skill` is offered exactly when the chat's prompt lists skills (`promptListsSkills`), so skills added or removed mid-chat change neither the prompt nor the tools, and the prompt cache stays warm. The model loads the text (up to 20,000 characters, `MAX_SKILL_CHARS`) on demand. The folder goes through `Workspace.resolve`, so a skills folder linked outside the project is ignored, linked files inside it are skipped, and skill names are restricted to file-name characters. The `task` subagent may load skills too.

Rules enforced in code, not only in the prompt:

- `Workspace.resolve` confines every path to the project root. Links are resolved first, also for a path that does not exist yet: its deepest existing part is resolved and the rest appended, so `link/new.txt` through a folder link to somewhere else is refused rather than created outside the project. A link that leads nowhere is refused. `.gitignore`, `.patchignore` and its older name `.ccignore` (read before it, so `.patchignore` wins; #38) are resolved through the same confinement check; external or dangling ignore-file links are ignored rather than read. Ignore rules are cached per folder and keyed on each ignore file's modification time and size, so changes from any tool, command, Undo or the user apply on the next lookup. Nested `.gitignore` files apply to their own folder with git's precedence, and `.git/info/exclude` is read when `.git` is a folder (#169).
- Existing files must be read in the current chat before `edit_file` or `write_file` may change them. The check runs both in `preview` (so an unread file is rejected before the user is asked to approve) and in `run`. The chat records the sha256 of each file's content when it is read (and after the assistant's own `write_file`, `edit_file` or `apply_patch`), and `write_file` refuses to overwrite a file whose content has changed since, again in both `preview` and `run`, so an edit made while the approval card is open is caught too. `edit_file` does not need the file unchanged since the read, since its search text must still match, but it refuses to run when the file changed after its preview (the hash of the previewed bytes is kept per call input, #255), so what runs is the diff that was approved. Chats saved by older versions store only paths; `write_file` asks for a new read of those files (#167).
- **Encoding.** `requireUtf8ForEdit` (`tools/text_files.ts`) validates the complete original buffer with Node's `isUtf8` before decoding. `edit_file` and existing-file `write_file` check in both preview and execution; `planPatch` checks updates, including moves, before any patch file is written. Non-UTF-8 files are refused without conversion; valid UTF-8 BOMs and literal replacement characters remain valid. New files are written as UTF-8; patch deletion does not re-encode a file.
- **Undo.** `edit_file`, `write_file` and `apply_patch` return `ToolOutput.undo` (`EditUndo`): the project-relative path, the exact previous bytes (`null` when the tool created the file) and the SHA-256 of what was written (`null` when it deleted the file). `apply_patch` lists its other files in `more` (`FileUndo`; a move is its new path plus its deleted old path), and Undo checks every file before writing any, then changes them in one helper batch, so a patch is undone as a whole or not at all (#197). It is never shown to the model. `Agent` passes it to `onEditApplied(toolId, edit)`, which `ChatManager` connects to `EditBackups.record` (`tools/edit_backups.ts`, one JSON file per edit in `userData/edit-backups/<chat id>/`, named by a hash of the application-generated tool-card id, newest 50 per chat, deleted with the chat). If that succeeds the `tool-end` event carries `undoable: true` and the card gets `undo: 'available'`. `edit:undo` (`ChatManager.undoEdit`) works only when the chat is idle and the card is `available`; `EditBackups.undo` resolves the path through `Workspace.resolve`, refuses unless the file's current bytes hash to `afterHash` (so later changes are never lost, and edits to one file are undone newest first), writes the bytes back or deletes the created file, and uses the backup up. `ChatSession.editUndone` then emits `tool-undone` (card `undo: 'undone'`), removes the file from `readFiles` so the model has to read it again, and queues a note that is put in front of the next message (or the resume instruction) sent to the model, so the conversation itself stays append-only. The note is saved with the chat until it is sent.
- **Protected files.** `isGuardedPath` (`tools/guard.ts`) lists paths whose edits always need approval (credentials and keys, `.git`, editor/agent folders and `.mcp.json`, the project's own `AGENTS.md`/`CLAUDE.md` and `.patch/` (they go into every new chat's system prompt, #236), files other programs run on their own (`.envrc`, `.husky/`), shell start-up files, databases, system folders; `.env.example`-style files are exempt). `write_file`, `edit_file` and `apply_patch` declare it with the optional `mustAsk(input, context)` of `AgentTool`, which asks in Auto mode too. A check that throws counts as "no".
- **Secret redaction** (best effort, not a boundary: a secret in a format none of the patterns knows is not caught). `redactSecrets` (`tools/redact.ts`) replaces private keys, AWS/GitHub/GitLab/npm/PyPI/Stripe/Twilio/DigitalOcean/Slack/Anthropic-style tokens, JWTs, passwords in URLs (`postgres://user:…@host`, keeping scheme, user and host; #123), quoted credential values and `.env`-style secret lines with `[REDACTED:_____]` in every tool result, summary and error. Command output is redacted before it is shortened, and a key with only its BEGIN or END line (cut by truncation or split between `command_output` reads) is masked to the end or from the start. `tool-progress` text goes through a per-call `streamRedactor`, which keeps masking after a BEGIN until the END arrives (#253). The patterns are bounded and anchored so a long line costs linear time on the main process. The file tools refuse input containing the placeholder, so a redacted value is never written back.
- **Permission rules.** `Settings.permissionRules` (`PermissionRule` in `src/shared/settings.ts`, validated by `parsePermissionRules`, edited as JSON in the dialog) are evaluated by `decidePermission` (`agent/permissions.ts`): the first rule whose `context`, `tool` glob and `matches` globs fit wins. `ChatManager` calls `decideCallPermission`, which checks the call with `path` made project-relative (case-insensitive on Windows and macOS) and, as separate parts, each file of an `apply_patch` (as `apply_patch` and as `edit_file` of that path) and each segment of a command between shell operators; any reject, then any ask wins, and allow needs the whole call or every part allowed (#237). `delegate` spawns the program in `to` (a string, never split, or `[program, ...args]`) without a shell (`delegateCommand`; on Windows `.cmd`/`.bat` go through `cmd.exe /d /s /c` with every part quoted, refusing `"`, `%`, `!` and line breaks, #178), sends `{tool,input,context}` on stdin and takes `allow`/`reject`/`ask` from stdout (15 s; any failure rejects). `ChatManager` passes the `thread` evaluator to the session and the `subagent` one to the subagent tools. `changesToConfirm` asks the user (native dialog) before a new or changed `allow` or `delegate` rule is saved. It also confirms any change to the ordered prefix through an existing `ask`, `reject` or `delegate` rule (#114, #251; a delegate may answer ask or reject): removals, field edits and preceding-rule reorders can bypass protection even when that rule stays at the same index. This conservative comparison uses serialized rule values, not glob containment; unchanged prefixes and new protective rules appended at the end stay quiet.
- Command output is capped (start and end kept) and decoded as a UTF-8 stream per pipe, so a character split across two reads stays intact; commands are killed with their whole process tree on stop or timeout.

To add a tool: create it with `defineTool` (name, description, Zod schema, `requiresApproval`, optional `preview`, `run`) and add it to `registry.ts` (`CORE_TOOLS`, or a configuration-gated entry in `availableTools`). Tools that need per-chat state (`search_code`, `task`, MCP tools) are passed to the agent as `extra` from `ChatManager`.

### macOS Service Boundary

`seatbeltProfile` uses exact `global-name` filters for Mach lookup: only `com.apple.system.opendirectoryd.libinfo` (CLI user/group lookup). Network-enabled commands additionally get the DNS/configuration and certificate-trust services `com.apple.SystemConfiguration.DNSConfiguration`, `com.apple.SystemConfiguration.configd`, `com.apple.networkd`, `com.apple.ocspd`, `com.apple.trustd.agent` and `com.apple.TrustEvaluationAgent` (DNS itself goes through the mDNSResponder socket, which `network*` covers). LaunchServices, URL-session and general background-execution daemons are not granted, regardless of network access, and an explicit trailing deny keeps LaunchServices and XPC services closed. The preferences daemon (`cfprefsd`) is not granted either: it would read preference files from the hidden home folder on the command's behalf. Tools that read user defaults (`defaults`, `xcodebuild`) therefore see built-in defaults, and notify/os_log calls fail silently.

With network access, the Seatbelt profile still denies connecting to local Unix sockets (`(deny network-outbound (remote unix-socket))` after `(allow network*)`), except the system DNS resolver socket `/private/var/run/mDNSResponder`, following the Codex and Chromium/WebKit profiles (#147). Shared memory is denied except libomp's `/__KMP_REGISTERED_LIB_<pid>` registration names (PyTorch), because a broader grant would let a command open a host process's named segment. Named semaphores are allowed for Python `multiprocessing` locks. Workloads that create arbitrary POSIX shared memory (`initdb` with `dynamic_shared_memory_type=posix`, `multiprocessing.shared_memory`) fail inside the sandbox. Direct `process-exec`/`process-fork` remain necessary for shells, compilers and toolchain subprocesses, which inherit the profile; they do not grant service-mediated application launches. `sysctl-read` is limited to named OS/hardware discovery entries (Codex's baseline plus `kern.boottime`, Rosetta/compat version checks and all `hw.optional.` CPU flags). `kern.procargs` (other processes' arguments and environment) is not granted. Seatbelt does not filter `kern.proc` process-table reads by sysctl name (macOS CI read a host process without the grant), so commands can list host processes and their owners; the `kern.proc.pid.`/`kern.proc.pgrp.` prefixes stay for parity with Codex. Writes are not granted.

The #99 LaunchServices escape is a static risk, not a claim of a demonstrated exploit. `sandbox_macos.integration.test.ts` exercises actual service lookup and a harmless app bundle with successful unsandboxed controls, shared-memory denial, a local HTTP endpoint that direct and Foundation (`NSURLSession`) requests must not reach with the network off, and representative CLI tools. Seatbelt's `.git` rule is path-based, so `sandbox_git.integration.test.ts` requires it to refuse creating a hard link to metadata, not only writes through one. Only a real Mac can establish enforcement and toolchain compatibility; off-platform skips do not count as successful isolation.

### Command Environment Boundary

`tools/env.ts` separates the legacy `scrubEnv` credential-name filter (it also drops any variable whose value holds a `scheme://user:password@` URL, and `KUBECONFIG`; unsandboxed agent commands and the host container-engine client) from `sandboxEnv`, the native command boundary. Native children inherit only `PATH`, `JAVA_HOME`, `GOROOT`, `GOPATH` and `RUSTUP_HOME`; Unix additionally inherits `LANG`, `LC_ALL`, `LC_CTYPE`, `LC_MESSAGES` and `TZ`, and gets `GIT_CONFIG_GLOBAL=/dev/null`: Seatbelt denies reading `~/.gitconfig` instead of hiding it, and Git aborts on a configuration file it cannot read. Windows additionally keeps OS/program-directory variables (`SYSTEMROOT`, `WINDIR`, `COMSPEC`, `PATHEXT`, Program Files/Common Program Files variants) and `LOCALAPPDATA`, which Windows rewrites for the AppContainer profile. Windows names are normalized case-insensitively; Unix names are exact.

Patch sets `HOME` to the policy's home (hidden except for approved toolchain locations), `TMPDIR` to the writable policy temp (`/tmp` for bubblewrap), and Windows `USERPROFILE`, `TMP` and `TEMP` deliberately from those locations. Agent commands also receive fixed `CI=1`, `FORCE_COLOR=0` and `NO_COLOR=1`. Native Unix shells run without login profiles. Arbitrary host values, agent/display handles and runtime injection/startup options are excluded, independently of tool-output secret redaction. This does not hide secrets stored in the writable project or make allow-listed toolchain paths writable.

Global `sandboxEnvAllowList` lists additional host variable names (one per line), and `sandboxPath` optionally overrides the native child's PATH. `changesToConfirm` requires native confirmation for added variable grants and changed nonempty PATH overrides; removing grants needs no confirmation. These grants can expose secret values, so the UI and confirmation warn without displaying values. Known runtime-startup/injection variables and agent/display handles cannot be granted, and home/temp values are still forced. No repository configuration or command-tool argument can supply a grant. GUI-launched Unix apps that discover toolchains through login profiles can set an explicit PATH instead of executing those profiles in the sandbox.

Container commands receive only the explicit environment in `containerArgs` and the image's defaults; the host Docker/Podman client needs its separate connection configuration, and native environment settings do not apply to it. The interactive terminal keeps its normal environment. An explicitly approved unsandboxed command still uses `scrubEnv` and can inherit private values with unrecognized names.

The Windows helper also journals a private per-command root under `%LOCALAPPDATA%\Patch\sandbox-temp`, grants only that root writable, and maps it to a temporary drive. It overrides `TEMP`, `TMP`, `TMPDIR`, `NPM_CONFIG_CACHE` and `NPM_CONFIG_USERCONFIG` case-insensitively, with an empty npm user config. Cleanup and abandoned-run recovery validate the deterministic root before deleting it and remove only exact-target drive mappings. Host temp, npm cache and profile config receive no new grants. Project PATH entries and directly launched project executables use the existing project drive mapping, avoiding inaccessible ancestor lookups. The helper compares long-form paths (`GetLongPathNameW`), so a PATH entry spelled with an 8.3 alias such as `C:\Users\RUNNER~1` still maps to the drive of the realpath project (#137). Sandboxed PowerShell applies `-ExecutionPolicy Bypass` only to its own process; filesystem/network controls remain AppContainer-enforced. libuv versions before 1.53 still lack the required `LOCAL` child-process pipe namespace, so ordinary Node test isolation remains an upstream blocker (#101): libuv retries the denied pipe name forever, so the command hangs until its timeout. No user command or Node test isolation flag is silently rewritten. Instead, `ShellRunner.run` records which sandbox ran a command (`CommandResult.sandbox`), and `formatResult` appends a fixed hint to AppContainer timeouts that names the explicit isolation flag and the `unsandboxed` request.

## Code search (`src/main/search/`)

`CodeIndex` walks the project (respecting ignore rules, up to _Maximum files to index_), skips credential files (`isSecretPath` in `tools/guard.ts`: `.env`, keys, `.npmrc`, `.ssh` and similar), splits text files into overlapping 60-line chunks, masks secrets in each chunk with `redactSecrets` (the reranker's documents too, #234), embeds them with Voyage `voyage-code-4` through OpenRouter's embeddings endpoint (`openRouterEmbedder`: `input_type` `document` for chunks and `query` for the search text, as Voyage recommends for retrieval; 1024 dimensions, the model's default) and stores Float32 vectors in `userData/indexes/<sha1 of path>.json`. Updates re-embed only files whose size or modification time changed, and each search refreshes the index once, reporting indexing progress to the tool card. A file is stored as soon as all its chunks are embedded, and the index file is saved every five batches and when the update ends, also after a failure or a stop, so a later run embeds only what is left. Concurrent searches share one update: each caller's stop ends only its own wait, and the update stops when every waiting caller has stopped. Cached indexes are dropped only when the OpenRouter key changes (#170); `CodeIndex.dispose()` then stops a running update after its current batch and keeps the dropped index from saving, so the old key is not used any more and the new index file is not overwritten (#248). The index is built on the first `search_code` call, never in the background. Search ranks by cosine similarity, at most two snippets per file. The best 30 of those go to Voyage `rerank-3` through OpenRouter's rerank endpoint (`openRouterReranker`, same key), which picks the final results; if reranking fails (anything but a stop), the results stay in embedding order and the tool output says why. Changing `INDEX_VERSION` or the embedding model rebuilds indexes. Settings shows the current project's index status (`index:status`: files and chunks, or why it is unavailable) and a Reindex button (`index:rebuild`, `CodeIndex.rebuild()`), which clears the index and embeds everything again.

## Chat list (`src/renderer/src/views/sidebar.ts`)

`Sidebar` lists the saved chats from `history:list`, newest first, grouped by day (Today, Yesterday, Previous 7 days, Older), and stays current through the `history:changed` push. `App` adds project navigation above it; New Chat sits above Sessions, and a header button collapses the sidebar with `aria-expanded`. Its footer sums the chats' `ChatSummary.tokens` and `cost`. Its filter narrows by title and project at once (`filterChats`) and then, after a short pause, shows `history:search` results, which also match message text (`ChatStore.search` reads each chat file once, yields to the event loop after each file so the window stays responsive, and keeps the text in memory until the chat changes). Deleting and clearing chats stay in the history dialog behind the header's history button. Its foot shows the open chat's `agentFile` and the code index state (`indexStatusLabel`, `src/shared/index_status.ts`), which `App` polls through `index:status` while an index is being built.

The main window follows an OpenCode Desktop-inspired layout: neutral theme tokens, a 48px header with session breadcrumbs, sidebar project navigation, a centered 768px conversation, and model/approval/plan controls mounted into `Composer.controls`. Inter, JetBrains Mono and Material Symbols are bundled with the app (`@fontsource-variable/*`, imported in `main.ts`), since the page's CSP loads nothing remote. `sym()` in `dom.ts` makes a Material Symbols icon, hidden from assistive technology. In the transcript every item is a row with an avatar column; the assistant's avatar is drawn on the first item of its turn (`leads` in `TranscriptView.render`). Tool rows show the tool name, a target and a result chip parsed from the summary (`toolLabel`), and `durationMs`, which `Agent.runTool` measures from the start of the tool's run (after approval) and sends with `tool-end`. The composer turns `@` into a file picker over `files:list` (`Workspace.listFiles`, ignore rules applied, at most 20,000 files) and sends mentions as `@path` at the start of the message (`messageWithMentions`). The status bar's context meter divides the last prompt size by the model's `contextWindow` (`src/shared/models.ts`; none for custom ids).

## Panels (`src/main/panels/`, `src/renderer/src/views/panels.ts`)

- **Terminal**: one interactive shell per project (`node-pty`), rendered with xterm.js. Separate from the agent's commands. The renderer starts it when the user presses Enter in the panel, and only when a project is open; without one the panel just says "Open a project to use the terminal." The main process still rejects `terminal:start` without a project as a safety net, and confirms the first start of each project in a session with a native dialog (concurrent starts share it; a cancelled one asks again), so a script in the renderer cannot open an unsandboxed shell on its own (#157).
- **Browser**: two `<webview>`s in the renderer: the user's (partition `persist:browser`) and the agent's (in-memory partition `agent-browser`, never written to disk; `AGENT_BROWSER_PARTITION` in `src/shared/panels.ts`). When the agent's guest attaches, the main process passes its `webContents` to `BrowserService`, which implements the `browser` tool on it (load, console capture, `capturePage` scaled to ≤1280 px); the user's guest is never handed to the agent. The panel shows the agent's page under an "Agent browser" banner while the agent drives it, and the user's page again when they type an address. A new chat, a reopened chat or a project switch empties the agent's page, history, cookies and storage (`BrowserService.reset`, #148).
- **Git**: `simple-git` — status, diff (untracked files shown as additions; a new link that resolves outside the project is left out, and a new file over 2 MB is shown without content), commit all, push, discard, discard all, init. Discard deletes the entry by its own path (`GitService.ownPath`, `removeEntry`): `Workspace.resolve` still confines it to the project, but its real path would turn a link into its target, so a link is removed itself and an entry inside a linked folder is refused (#111). `GitService.status` adds per-file line counts (`git diff --numstat --no-renames` against `HEAD`, or the index and working tree before the first commit, parsed by `parseNumstat` in `src/shared/panels.ts`; new files are counted by reading them, up to 2 MB, binary files not), the upstream with ahead/behind counts, and `canPush` (an upstream, or a remote named `origin`). `push` pushes to the upstream or runs `push --set-upstream origin <branch>`; it uses the user's git credentials but runs no hooks (`core.hooksPath=/dev/null`, see Security model), and since the app has no terminal git cannot prompt for a password. `git:suggest-message` sends the diff (cut at 30,000 characters, `MAX_COMMIT_DIFF_CHARS`) and the file list to the small model (`LlmService.smallModelForSettings`, preferring the provider of the model in Settings) and returns a Conventional Commit message (`panels/commit_message.ts`). The renderer shows one hunk of the diff at a time (`diffHunks`). Before the first commit, diffs include staged additions followed by any working-tree patches. Discarding a staged rename restores the original committed file and removes the renamed destination, including staged and unstaged edits to it. While the Git tab is open, it refreshes after each tool call and after an Undo. The status bar shows the current branch from `git:status` (with `*` when files changed) and the Git tab a badge with the number of changed files, refreshed when the project changes, after each run and whenever the Git tab reads a new status. A repository whose root is the home folder or a folder above it counts only when the project is that root (`isRepoAboveHome`); otherwise `git status` would scan the whole user profile. For a project inside a larger repository, `projectStatus` runs `git status -- .` and strips `git rev-parse --show-prefix` from the paths (`projectFiles`), so every path the panel uses is relative to the project folder; pathspecs are too, since Git runs there, and diffs use `--relative`. A rename across the project's edge is listed as an addition or a deletion of the project side only. Commit runs `git add -A -- .` and `git commit -- .`, so changes staged elsewhere stay staged and out of the commit (#174).

## Accessibility

- The transcript is re-rendered per streamed chunk, so it is not an `aria-live` region. `TranscriptView.announcer` is a hidden `role="status"` region fed by `newAnnouncements` (`src/shared/announce.ts`): a finished answer (first 300 characters), an approval request, a failed tool, an error or a notice, each once. Opening a saved chat announces nothing.
- Anything that carries meaning only through an icon or color needs a text alternative (`visually-hidden` text or `aria-label`). `h()` gives icon-only buttons their `title` as `aria-label`.
- Colors come from the `--patch-*` tokens at the top of `src/renderer/src/styles.css`, one set per theme; Bootstrap's `--bs-*` variables and button variables point at them. Change the palette there, not in individual rules. Keep `--patch-accent-rgb` comma-separated (Bootstrap uses it in `rgba(var(...), a)`).
- Use Bootstrap's `*-text-emphasis` colors for colored text, not the plain `--bs-info`/`--bs-warning`, which are too light on white.

## Security model

- **Renderer isolation**: `contextIsolation`, `sandbox`, no `nodeIntegration`. Strict CSP (`script-src 'self'`, no remote images or connections).
- **Preload**: exposes only `invoke`/`on` for allow-listed channels.
- **Setting changes that run programs, skip approvals or redirect a key**: before `settings:update` applies a switch to Auto mode (every time, #157), a changed `editorCommand`, a new or changed stdio MCP server (command, arguments, `cwd`, or a new `env` value; the dialog names the absolute program path the command resolves to, #142), a new or changed `allow` or `delegate` permission rule, changes to an existing `ask`, `reject` or `delegate` rule or its preceding rules (#251), new entries in the command or network allow-lists, or a changed Claude or OpenAI-compatible base URL, the main process shows a native confirmation (`changesToConfirm` in `settings_confirm.ts`). Removing protective rules requires confirmation even in Auto mode; cancelling aborts the whole patch before settings are stored or applied (#114). `project:update-settings` does the same for new entries in a project's own allow-lists and for new or changed project instructions, which go into every chat's system prompt; the dialog shows the first 600 characters (`projectChangesToConfirm`, #157). A compromised renderer therefore can't make these changes silently. The dialog names `env` keys, never their values. An HTTP MCP server asks only when it would keep stored headers (left out or empty in the save) while its URL is new or changed, because headers are stored by server name and would otherwise go to the new host (#110). The confirmation gets header names from `SettingsStore.mcpHeaderNames`, never values. Removing a server or allow-list entries, other HTTP server changes, clearing a base URL (back to the official API) and switching back to Ask mode don't ask (#29, #65).
- **Program lookup** (#141): Patch starts several programs by bare name (`git`, `powershell.exe`, `docker`/`podman`, `taskkill`), most with the project as working directory. Windows searches the working directory before PATH, and an empty or relative PATH entry does so on every platform, so a repository could supply its own `git.exe`. `hardenExecutableSearch` (`exec_search.ts`) runs before anything is spawned: it sets `NoDefaultCurrentDirectoryInExePath` on Windows and drops PATH entries that depend on the working directory (logging only how many). libuv reads both from the main process at every spawn, whatever environment the child gets. The interactive terminal and approved unsandboxed commands inherit them. MCP stdio servers are started through `cross-spawn`, which searches the working directory itself, so Patch never gives them the project as working directory and resolves their command to an absolute path first (#142, see MCP servers below). End-to-end test: `tests/e2e/planted_binaries.test.ts`.
- **IPC sender**: every handler (`handle` in `ipc.ts`) answers only calls from the app page's top frame: exactly the built page the window loads (`APP_PAGE_PATH`, compared as a file path with query and hash ignored, case-insensitively on Windows and macOS), or the dev server during development (`isAppPageUrl`, #66). Another file named `renderer/index.html` does not count. Calls from any other frame are refused and logged by channel name.
- **Navigation**: the app window cannot navigate; `http(s)` links and `window.open` go to the system browser. The app page always comes from the built files on disk in a packaged app: the dev server URL (`ELECTRON_RENDERER_URL`, set by `npm run dev`) is only used when the app is not packaged (`renderer_url.ts`).
- **DevTools** (#120): a console on the app page has the whole `window.api`, terminal panel included, so the packaged app has no View → Toggle Developer Tools item or its shortcut; development builds keep it. Chromium's `--remote-debugging-port` still works on the packaged app, which the packaged smoke test needs (`scripts/smoke-packaged.mjs`). It is an accepted local risk: using it means starting the app as the same user, who can already run anything.
- **Browser panel**: guests get no preload, no Node, sandboxed, in the `persist:browser` (user) or in-memory `agent-browser` (agent) session partition (`allowsWebviewAttach`); `will-attach-webview` rejects omitted or other partitions in the main process, so the renderer cannot attach a guest to the app's default session (#34). Guests always run with `webSecurity` on and insecure content off, and a `disablewebsecurity` attribute is dropped (#67). Every web contents the app creates gets a deny-all window-open handler and, for app windows, a block on navigating away from the loaded page (`guardNewWebContents`, `app.on('web-contents-created')`), so a future window is locked down by default. Popups are denied: the guest has no `allowpopups` attribute (any value would turn them on) and its window-open handler refuses every one. A guest can only be attached to `about:blank` or an `http(s)` URL. Both sessions deny every permission request (camera, microphone, location, notifications), and the agent never browses with the user's cookies or sign-ins (#148). Browser-tool top-level redirects and later page navigation stay on the approved hostname; cross-host destinations need a new tool call. Project `file://` URLs are preapproved only after `confineFileUrl` checks confinement. Once the agent has opened a page, both panel sessions' request filter (`BrowserService.allowsRequest`) also checks every `file://` request, frames and sub-resources included, which never fire `will-navigate`: a project page cannot show a file from outside the project in an `<iframe>` for a screenshot to pass on (#63). A project page opens without a card even in Ask mode, and with the `grantFileProtocolExtraPrivileges` fuse on (the app's own `file://` renderer needs it for its module scripts) it can `fetch()` other project files such as `.env`. So while the agent shows a `file://` page its session is offline (#229): `allowsRequest(url, fromAgentSession)` refuses `http(s)`, `ws(s)` and `ftp` requests from the agent partition only, and `BrowserService` sets the agent session's proxy to an unreachable one with `<-loopback>` (Chromium otherwise sends loopback past a proxy) and closes its connections, which also covers DNS prefetching. The agent's guest uses the `disable_non_proxied_udp` WebRTC policy, so WebRTC has no way around the proxy. Before a web page is opened after a file page, the file page is replaced with `about:blank` and only then is the network restored; `reset()` restores it too. While the agent's page is a web page on a public host, the filter also refuses its `http(s)` and `ws(s)` requests to local hostnames and address literals (`isLocalHostname`: loopback, private, link-local and metadata addresses), so frames and fetches cannot show a local service for a screenshot (#235); a page opened on a local address may still load from local addresses. `checkRequest` also resolves each host name once per page (`resolveDestination`) and refuses a public name that resolves to a local address (#260); Chromium resolves the name again itself, so an answer that changes in between (DNS rebinding) is not fully covered.
- **Model output**: rendered markdown and diffs pass through DOMPurify. Model Markdown uses `USE_PROFILES: { html: true }`, rejecting SVG (including `<image>` and `<feImage>`) and MathML in addition to the explicit image, embed, form and style exclusions (an image URL is a common data-exfiltration channel for prompt injection, #115). Model Markdown also loses `id`, `hidden` and every class except highlight.js's `hljs*` and `language-*` (an `uponSanitizeAttribute` hook added only for that call), so it cannot borrow the app's Bootstrap and layout classes to draw a fake Approve button or overlay, or hide text from the user (#254). Normal HTML Markdown and syntax highlighting remain available, and markup in code blocks stays literal text. `renderDiff` retains its separate sanitizer configuration for generated diff HTML. Generated UI never uses inline handlers.
- **Trusted Types** (#65): the app page's CSP adds `require-trusted-types-for 'script'; trusted-types dompurify`. `renderMarkdown` and `renderDiff` ask DOMPurify for a `TrustedHTML` (`RETURN_TRUSTED_TYPE`), made by DOMPurify's own policy, the only one allowed; `trustedHtml()` takes only that type. Any other HTML sink (an `innerHTML` with a plain string, `insertAdjacentHTML`, `document.write`) throws instead of parsing, so a sanitizer bypass or a stray sink in new code cannot inject markup. xterm, diff2html, highlight.js and marked write no HTML themselves. This matters because a compromised renderer amounts to code execution (the terminal panel types into a real shell): keeping the renderer free of XSS is the main control, and the settings confirmations only stop a settings-only exploit.
- **Secrets**: keys are encrypted at rest when system encryption is available and never sent to the renderer. Plaintext fallback and failed migration are flagged in Settings. API keys, the ChatGPT tokens and MCP servers' `env` and header values are all migrated together, in one staged write, once encryption becomes available, and all count toward that flag (`sealedSecretValues`, #113). On Linux, Electron's `basic_text` backend (no keyring, a fixed password) counts as unavailable (`fixedKey`, #258): new keys are stored as plaintext after confirmation, and Settings reports them as not encrypted.
- **Protected paths (#143)**: guard patterns match case-insensitively. `Workspace.resolve` uses `realpathSync.native` on the deepest existing ancestor before appending missing components, expanding Windows case and 8.3 aliases. A throwing `mustAsk` check requires approval; Auto mode and allow/delegate rules cannot turn that failure into permission to run.
- **Native file boundary (#144)**: `tools/file_operations.ts` sends one JSON request to the bundled `file-helper` (`native/sandbox-helper/src/file_helper.rs`), with project root, original relative paths and base64 byte snapshots. Workspace resolution still checks confinement, but never replaces below-root input components with their canonical targets: doing so would erase a link introduced after the protected-path check. Absolute aliases above the root remain supported. Unix walks use directory-relative `openat`/`mkdirat`/`unlinkat` and `O_NOFOLLOW`; writes use acquired regular-file descriptors and exclusive creation. Windows retains parent/target handles without write/delete sharing, refuses reparses and deletes through handle disposition. Hard-linked mutation targets are refused. Every existing batch target and expected byte snapshot is checked before the first mutation. Reads used by `read_file`, edit previews/snapshots, patch operations and Undo use the same helper, with no pathname-write fallback. Ordinary approvals, read-before-edit, UTF-8 validation and exact-byte Undo remain, including for `apply_patch` (#197). If a change fails while the batch is applied (an I/O error, a name the system refuses), `apply_all` undoes the changes already made in reverse order through the retained handles (#242): edited files get their old bytes back, created files and the folders made for them are removed, and deletions are taken back (on Windows a deletion is a delete-on-close mark until the request ends; on Unix the file is written again with its old bytes and mode). An existing file is replaced, not rewritten in place (#259): the new content goes to a `.patch-tmp-<pid>-<n>` file in the same held folder, is flushed, and is renamed over the target (`renameat` on Unix, `FileRenameInfo` with replace-if-exists on Windows), so a crash leaves the old file or the new one, never a short one; a crash before the rename can leave the temporary file behind. The replacement keeps the old mode and, where allowed, owner on Unix, and on Windows the old DACL (protected from inheritance when it was, so a file the sandbox protects during a command stays protected), creation time and hidden/system attributes. On Windows the target handle is closed just before the rename, and the immediate folder handle is swapped for one of the same folder (checked by file ID) that shares writing but not deletion, because a rename opens its folder for writing; the folder still cannot be renamed, and NTFS refuses a reparse point on a folder that is not empty. When no temporary file can be created, or another program holds the target open, the file is written in place as before, after checking it still has the expected bytes. Undo replaces the same way. Sandboxed background commands cannot relocate a retained descriptor outside the project: Linux/container host mounts expose only the project as writable, Seatbelt now has project-only host writes, and Windows sharing locks prevent relocation. Explicitly unsandboxed programs and host processes are outside that threat model.
- **Sandbox root validation (#145)**: `systemLaunchEnv` canonicalizes the project before Git preparation and refuses volume roots, home equality/ancestors and bidirectional overlap with Electron app-data/user-data and packaged installation trees. `index.ts` (`sandboxSensitivePaths`) supplies the application boundaries to `ShellRunner` through `ChatManager`, and to `McpHub` for sandboxed servers with project access (#256); development checkouts are not treated as app installations. Windows independently rejects profile, app-data, custom profile and installed-helper overlap at `run` entry, before locks, recovery, staging or ACL changes. Native and container commands share the TypeScript check; explicitly approved unsandboxed commands and sandbox-off remain intentional exceptions. Seatbelt host writes are limited to the project (plus narrow device paths), with per-command project-local temp, preventing an opened file from being relocated to another writable host tree (#144).
- **Agent**: path confinement, read-before-write, approval for edits and commands by default. Agent commands use the configured sandbox; **Auto** mode skips ordinary approvals, not sandbox boundaries. Commands on the "allowed without asking" list skip approval only when they contain no shell operator and nothing PowerShell would evaluate (`$`, parentheses, braces). Tools marked `alwaysAsk` (MCP tools and `propose_plan`; a `propose_plan` call while plan mode is off has no side effect and is answered without a card) ask even in Auto mode and are never covered by an allow-list; an explicit `allow` permission rule can override that flag. Per-call `mustAsk` checks (protected files and sandbox escalation) cannot be overridden by an `allow` rule or a delegate's allow decision; `reject` still blocks the call without asking. Tool results are redacted before the model sees them (best effort: known token formats and credential-named values).
- **MCP servers**: stdio servers are started with `cross-spawn` (no shell string) and `getDefaultEnvironment()` plus the server's own `env`, so the app's API keys are not passed on. They run in `userData/mcp`, never in the project (#142): there `npx` would prefer the project's `node_modules/.bin`, `python -m` would import from it, and cross-spawn looks for the program in the working directory first on Windows. `launchConfig` (`tools/mcp.ts`) sets that folder and replaces `${project}` in `args` and `env` with the open project's path, so only servers that ask for the project see it, and a project switch reconnects only those (the config `refreshMcp` compares contains the project path only for them). `resolveCommand` turns a bare command into an absolute path using only PATH folders that don't depend on the working directory, and refuses relative paths; the settings confirmation shows the path it found. A server's `env` values and HTTP `headers` are encrypted like API keys and only their names reach the renderer. A failed connection, a removed server and quitting close the client and kill the server's process tree, including what a wrapper such as `npx` or `uvx` started (#117): `closeClient` lists the tree (`listProcesses` and `processTree` in `tools/shell_leftovers.ts`; `ps` on POSIX, finished before the server can exit, because its children are re-parented once it does; a CIM listing on Windows, which keeps an orphan's parent pid, made while `close()` waits), then `killSurvivors` kills those still running with the same pid and start time. Asynchronous; `McpHub.stop()` and quitting wait for it. A stdio server with `sandbox: true` (#87) starts through `mcpSandboxLaunch` (`tools/mcp_sandbox.ts`). On Linux: `bwrapArgs` (in the limited systemd scope when available) with `cwd` and `HOME` set to `userData/mcp/sandboxed/<name>-<hash>`, the project mounted writable only when `launchConfig` set `projectAccess` (its `${project}` is used; never read from the stored settings), that project's root checked by `systemLaunchEnv` and its Git metadata read-only, `--share-net` only with `sandboxNetwork`, and `sandboxEnv` plus the server's `env`. The program runs as `/bin/sh -c 'exec "$0" "$@"'` so the shell substitution in `systemShell` never replaces it. On Windows: the same folder policy through `buildHelperRequest` (`workspace: true` so the helper accepts a working folder under userData; a server with `projectAccess` starts in the project's mapped drive instead, because Node cannot resolve a script under hidden parents, and its own folder stays writable as `HOME`), then `sandbox-helper.exe --stdio <request.json>`, which splices stdin/stdout/stderr to the AppContainer so JSON-RPC is not wrapped in helper events. Off those platforms, or without bubblewrap or the helper, connecting fails with the reason (`mcpSandboxUnavailable`); nothing starts unsandboxed. `stdioChange` confirms turning the sandbox off or the network on. Tool names are namespaced (`mcp_<server>_<tool>`) so a server cannot claim a built-in tool's name, and results are cut like other tool output.
- **Subagents (`task`, `finder`, `oracle`)**: can only run an allow-list of read-only tools (`read_file`, `list_directory`, `glob`, `grep`, `search_code`, `load_skill`), so they cannot edit, run commands, use the network, call MCP tools, propose a plan or start another subagent. A subagent on the chat's own model is sent the chat's exact system prompt and tool list, so its requests read the prefix the chat already cached instead of writing a new one (#77); its role goes into its first message, and every tool outside the allow-list is a stand-in with the same name, description and schema that only returns an error, so the real tool is never reachable. On another model it gets only the allow-listed tools and its role in the system prompt. Its reads go into its own set, so they do not satisfy the parent's read-before-edit check.
- **Project skills**: the `.patch/skills` folder is resolved through `Workspace.resolve`; a folder linked outside the project is ignored and linked files inside it are skipped. Skill text is prompt text, like `AGENTS.md`.
- **Electron fuses** (`build.electronFuses` in `package.json`, applied when packaging): the packaged app ignores `ELECTRON_RUN_AS_NODE`, `NODE_OPTIONS` and `--inspect` flags, so it can't be turned into a Node runtime or have code injected through them, and it only loads its code from `app.asar`, whose integrity is checked: a changed header stops the app at start, and a changed file stops it when that file is read. Cookies of the browser panel are encrypted on disk. `GrantFileProtocolExtraPrivileges` stays on, because the UI loads ES-module scripts from `file://`.
- **API endpoints** (`src/main/llm/endpoints.ts`, #64): keys and ChatGPT tokens only go to the official endpoints or the base URL set in Settings. The clients always get an explicit base URL (Settings → Claude base URL or OpenAI-compatible base URL, else the official one; the Anthropic client gets no `authToken`), so `ANTHROPIC_BASE_URL`, `OPENAI_BASE_URL`, `ANTHROPIC_AUTH_TOKEN` or an `ant auth login` profile cannot redirect them or add a credential. The `PATCH_TEST_*` hooks the tests use to reach local stand-ins only work in development builds: the main process calls `setPackagedBuild(app.isPackaged)` at start, and until it does the hooks are off, so a missed call fails closed. The same rule covers `ELECTRON_RENDERER_URL` (`renderer_url.ts`, #27). Setting or changing the Claude base URL needs a native confirmation (`settings_confirm.ts`), since the Anthropic key goes there; it and the OpenAI-compatible base URL must be http(s) URLs, and a bad saved value falls back to the official API.
- **macOS hardened runtime**: the app and helper entitlement files grant only `allow-jit` for V8, not DYLD environment-variable injection or unsigned executable memory. A signed packaged launch on Intel and Apple Silicon remains to be verified (#22, #28).
- **Git panel**: a repository's own `.git/config` can name commands git runs by itself. `GitService` (`panels/git.ts`) runs every call with `core.fsmonitor=false` and `core.hooksPath=/dev/null`, neutralizes the clean, smudge and process commands of the filter drivers the repository defines in its local config (`hardenedConfig`), and diffs use `--no-ext-diff --no-textconv`. The main process keeps one `GitService` per open project (#199), which reads that filter list once (`git config --local --includes --show-origin`) and again whenever one of the files it depends on changes: the local and worktree config, each file an entry came from and each file an include names, missing ones too (`parseConfigListing`, compared by size, times and inode). The files are checked before the list is read, so a change made meanwhile triggers another read. Filters the user configured globally keep working, but hooks (including Git LFS pre-push hooks) require running Git explicitly in the terminal. Disabling hooks at this host boundary stops a sandboxed command from redirecting hooks to any writable project folder, including when `.git/hooks` was absent at launch. Covered by real commit/push tests with executable default and redirected hooks in `panels/git.test.ts`.

### Known limits (reviewed 2026-10-01)

These are accepted limits of the unreleased Patch baseline; each is a trade-off, not an oversight.

- **Toolchain grants.** Cargo opens only `bin`, `registry` and `git`; Maven opens `repository`; Gradle opens `caches` and `wrapper`. Their parent directories and global Git configuration are not granted, keeping standard credential/config files hidden. Windows PATH grants reject these private paths and their ancestors as well, even before the files exist. `exceedsEntryLimit` uses native filesystem paths, with threshold-boundary tests on all platforms. Secrets deliberately stored inside the project or exposed tool/cache directories remain accessible; this is not secret detection. Commands needing private home configuration require explicit unsandboxed approval.
- **Command sandbox (#76).** `tools/sandbox.ts` plans how `ShellRunner` launches `run_command` (not the terminal panel; MCP servers only with `"sandbox": true`, below). `decideSandbox` picks bubblewrap (Linux), Seatbelt (macOS), the AppContainer helper (Windows) or a Docker/Podman container from the `sandboxMode` setting and what `detectSandboxSupport` finds. That call never blocks: it reads the results of `refreshSandboxSupport`, which `ShellRunner.prepare` awaits before the approval preview and before starting a command. It runs only the probes the mode needs (bwrap for `auto` on Linux, `docker version`/`podman version` only for `container`) as asynchronous child processes, caches them for 30 s, shares a probe that is still running and keeps the last result while refreshing (#112); `bwrapArgs`, `seatbeltProfile`, `containerArgs` and, for Windows, `windowsPolicy`/`buildHelperRequest` (`tools/sandbox_windows.ts`) are pure and unit-tested. Policy: project folder writable (the entire root `.git` read-only), temp writable, system and toolchain folders read-only, the rest of the home folder hidden, no network unless `sandboxNetwork: on` or a one-time approval grants it. `allow-list` is enforced on Linux when bubblewrap and the `net-bridge` helper are there, and on Windows when the AppContainer helper is there (`filtersNetwork`, #97): the decision is `{ network: false, filtered: true }`. On Linux the command keeps its own network namespace (loopback only, no resolver). `ShellRunner` starts a `FilteringProxy` (`tools/net_proxy.ts`) on a Unix socket in a private temp folder (a named pipe on Windows) for that command and closes it when the command ends; `bwrapArgs` mounts the socket and the bridge on the sandbox's /tmp, sets the proxy variables and runs `net-bridge 3128 <socket> -- <shell>` (`native/sandbox-helper/src/net_bridge.rs`), which forwards 127.0.0.1:3128 to the socket. On Windows the helper copies `net-bridge.exe` into the command's private temp folder, starts it in the same AppContainer (no `internetClient` capability) and relays the bridge's named-pipe connections to Patch's proxy; only that AppContainer may open the relay. `checkDestination` allows an exact allow-listed hostname on 80/443, resolves it with `resolveDestination` and refuses a local result, then the proxy dials only that address; plain HTTP is forwarded with its absolute URL, HTTPS goes through CONNECT. After the `200`, the proxy reads the client's TLS ClientHello (`clientHelloServerName`, across handshake records, up to 64 KB and 10 s) and relays nothing unless its SNI is the checked hostname (no SNI only for an IP literal); non-TLS data on a tunnel is cut, so a CDN-hosted allowed name cannot front another site (#239). Filtered commands need no approval (`mustAsk`). On macOS and in container mode `allow-list` requests unrestricted network if every URL written in the command is on the allowed hosts; `ShellRunner.mustAsk` requires approval because URL matching cannot filter a program's connections. Limits (#104): `DEFAULT_LIMITS` (`tools/sandbox_windows.ts`: 512 processes, 8192 MB) apply to the Windows job, to containers (`--pids-limit`, `--memory`, `--memory-swap`) and, on Linux, to a transient systemd user scope: when the `systemd-run --user --scope` probe succeeds, `buildLaunch` runs `systemd-run ... -p TasksMax -p MemoryMax -p MemorySwapMax=0 -- bwrap --unsetenv XDG_RUNTIME_DIR ...`. systemd-run execs bubblewrap in its own process, so stopping still signals the process group; only `XDG_RUNTIME_DIR` (`Launch.launcherEnv`) is passed to it, and bubblewrap unsets it for the command. setrlimit is not a fallback: its process limit counts all of the user's processes and an address-space limit breaks V8 and the JVM, so without a user manager the command runs unlimited and `appLog` warns. Seatbelt commands have no limits yet. Container mode mounts only the project at `/workspace`, drops capabilities and passes no host environment; stopping a command also runs `<engine> rm -f`. Both `auto` without a native backend and `container` without a running engine fail closed (foreground and background commands are not run). The model can set `network` or `unsandboxed` on a call; either makes it ask even in Auto mode or with an `allow` permission rule (allow once). Turning the sandbox off or network on needs a native confirmation. `tools/env.ts` (`scrubEnv`) drops credential-named variables. `npm run test:sandbox` runs policy tests plus real Unix/container probes (`sandbox.integration.test.ts`) and Windows helper probes (`sandbox_windows.integration.test.ts`). The Unix/container suite uses a fake home and local TCP control, asserts the probe actually executed, and never falls back to unsandboxed execution. Missing backends/images skip explicitly; CI requires its native backend.
- **Git metadata boundary (#98, #109).** `tools/sandbox_git.ts` prepares the selected root before sandbox launch and returns the protected top-level paths. The check is asynchronous (`fs.promises` walk, `execFile` for `git config`) and `ShellRunner` awaits it before spawning. A successful result is cached per project root while a fingerprint (device, inode, mode, link count, size, mtime and ctime) of `.git`, `HEAD`, the Git directories and their `config`, `config.worktree`, `commondir` and `hooks`, every config file read and the protected top-level entries is unchanged; failures are never cached, and paths changed in the last 2 s or an unreadable fingerprint force a full check. Changes deeper inside a protected tree are seen on the next check that misses the cache; sandboxed commands cannot make them because every protected path is read-only in the sandbox (#112). Missing `.git` is reserved as a protected file (`GIT_RESERVATION`), not initialized Git, and persists across all command lifetimes to avoid overlap/cleanup races. The file is not a valid gitfile, so Git stops at the project with "invalid gitfile format"; an empty folder would let discovery fall through to a bare repository planted in the writable project root (#129). A project below another repository (not one at or above the home folder) keeps an empty folder, because the file would hide the enclosing repository. Git then checks the project folder itself for a bare repository, which requires a readable `HEAD`, so `reserveHead` creates a protected empty `HEAD` folder and returns it with `.git` (#132). Git ignores empty folders, so the enclosing repository does not list it. An existing `HEAD` is protected if it is a folder or a file that is not a valid Git `HEAD`; links, hard-linked files and a `HEAD` that starts with `ref:` or an object id refuse execution. A nested project with its own metadata needs no `HEAD` reservation. Protection is applied when each sandboxed process starts, so the `git:init` handler first stops the project's background commands (`ChatManager.stopBackgroundCommands`, then `commandStopsSettled`) and takes sandboxed MCP servers with `projectAccess` out of the server list until `GitService.init` has run (#231): on Windows the new `.git` would inherit the project grant a running process already holds, and on Linux unlinking the read-only reservation file detaches its bind mount. Empty folders from earlier versions are converted, and the Git panel's init turns the file back into an empty folder (`releaseGitReservation`) immediately before `git init`. Regular metadata, active hooks and existing command overrides are accepted. In-project gitfiles and `commondir` redirects protect the pointer plus entire top-level metadata ancestors, so renaming a writable ancestor cannot replace a target. External, linked or special metadata still refuse execution. On Linux and macOS a pointer may name the project through a link above it (macOS `/tmp` → `/private/tmp`) when every such link sits in a root-owned directory that group and others cannot write, so no command can retarget it (#131); links inside the project are always refused; the tree-size limit is removed. Git parses configuration with `--git-dir=/dev/null`, `--file` and `--no-includes`, suppressing repository discovery and startup config loading; include targets must stay within protected trees and are recursively checked without following writable includes. Bubblewrap and containers mount each protected entry read-only, including absent control names; `--mount` fails on disappearing sources instead of creating host directories, and comma-containing mount paths are refused. Seatbelt denies writes to protected entries and unlink/rename of the project's ancestor chain. Windows revalidates regular protected entries under the permission lock, protects inheritance and grants read-only access. The Git panel applies `safe.bareRepository=explicit` before even its local-config query to prevent discovery of bare metadata planted outside an empty reservation. Git writes still require the panel or explicitly approved unsandboxed access; approval text describes loss of file confinement and unrestricted networking. Before push and commit, the panel also reads the repository's local credential helpers, `core.sshCommand`, `core.askPass`, `core.gitProxy`, `remote.*.receivepack`/`uploadpack`, `gpg.*program` and `gpg.ssh.defaultKeyCommand` (#156); if one runs a file inside the project (`projectCommands`: a path or bare name that leads into the project, or shell substitution), it refuses instead of running it (#130). This does not make nested repositories, arbitrary later terminal Git commands or existing host/global integrations that execute writable project code safe: hooks that run project scripts (Husky running `npm test`) run whatever the agent left, like running those scripts yourself.
- **Project configuration boundary (#127).** `tools/sandbox_config.ts` lists the top-level entries editors, agents, Git hook managers and CI read or run outside the sandbox (`.vscode`, `.idea`, `.claude`, `.agents`, `.patch`, `.husky`, `.github`, `.mcp.json`, `AGENTS.md`, `CLAUDE.md`, `.envrc` and others). `systemLaunchEnv` adds the ones that exist (`protectedConfigPaths`, one `readdir` of the root, names matched case-insensitively, links left out) to the Git paths in `LaunchEnv.protectedPaths`, so every backend protects them the way it protects `.git`: bwrap `--ro-bind`, a Seatbelt `file-write*` deny, container read-only mounts and Windows `denyWrite` (`protect_acl`, restored by the last overlapping run). Whole entries are protected, never files inside them, so renaming a writable parent cannot swap one in. The direct edit tools ask about the same names (`guard.ts`), except `.github`. Absent entries, links and nested copies are not covered (#262).
- **Windows sandbox helper.** `native/sandbox-helper` is a Rust program (`npm run build:sandbox`). `ShellRunner` starts it once per command and writes a JSON request line on stdin (`HelperRequest`: shell, cwd, env, `network`, optional `proxy` named pipe for filtered allow-list network, optional `workspace` for an MCP server's folder under userData, `readWrite`, `readOnly`, `denyWrite`, limits). `sandbox-helper.exe --stdio <request.json>` starts one process and splices stdin/stdout/stderr to it so an MCP JSON-RPC stream is not wrapped in helper events (#87). It answers with JSON events (`started`, `stdout`, `stderr`, `exit`, `error`, and `log`, which Patch writes to `app.log.jsonl` as a `sandbox-helper` warning without failing the command) and stops the command on `{id, kill: true}` or end of input. `started` is sent before the command's first instruction runs, so no output precedes it; a command that is still running 5 s after its job was terminated is reported as `exit` with `exitCode: -1` and `timedOut: true` instead of Windows' `STILL_ACTIVE` (259). `revokeProject` runs on a worker thread like a command, so a kill message is never queued behind it (#195, #206). Each run creates a temporary AppContainer profile and grants only the listed paths. The project's own write grant is the exception (#103): it goes to a capability SID that `DeriveCapabilitySidsFromName` derives from `patch.project.<lowercased project path>` (SHA-256 inside Windows, so a folder name cannot be chosen to collide with another project's), and every command for that project carries the capability in its token. The grant is propagated through the project once, under the permission lock, with a record in `%LOCALAPPDATA%\Patch\sandbox-projects` flushed as unfinished before and finished after; later commands only check the record and the root's DACL, so they rewrite no project permissions. A helper killed half-way leaves an unfinished record and the next command repeats the grant. In a large project that first propagation can take minutes, so other helpers wait for the permission lock with no fixed limit while its holder lives (a holder that dies abandons the mutex and the next waiter takes it), a stopped command ends its wait, and a command still waiting after 5 s writes a line to its output saying why (#176). `revokeProjectGrant` keeps its 15 s timeout and is retried on the next close. Closing or removing the project in Patch sends the helper a `revokeProject` message (`releaseProjectGrant` in `tools/sandbox_windows.ts`, retried while a stopped command's helper finishes); the helper keeps the grant while a recovery record shows a live run in that project. Quitting keeps it for the next session. Windows system paths keep their built-in package access, but Program Files installers can remove inherited package permissions (#106). Individual Program Files PATH entries travel separately as `toolchains`, and the helper checks effective package read/execute rights before changing anything. A folder whose own entries are already readable (Git, Python) gets no grant, and the rest of the install is not walked. Otherwise the whole tree is inspected. An inaccessible install uses a read-only copy, kept across commands in `%LOCALAPPDATA%\Patch\sandbox-toolchains\cache` (#108). The shared install folder is never granted to the run's SID, even when its permissions would allow it: a grant there would expose the whole install while the command runs and could outlive a forced kill until the next helper start (#207). Inspection first lists the install cheaply (names, sizes, write times, reparse flags, no per-entry security queries) and names the copy `<install hash>-<contents hash>` (FNV-1a). If that copy exists, the command uses it and the per-entry link and package-rights checks are skipped, because the source is never read; a repeat `node --version` with the official Node install takes about 0.3 s instead of about 4 s. Otherwise the helper copies into the run's private staging folder after the lock is released, with read/execute for the `patch.toolchains` capability inherited from that folder (never write), and publishes the copy by an atomic directory rename, so a partial copy never appears in the cache; if another run published the same name first, its copy is used. The cache root is readable only through the `patch.toolchains` capability (derived like the project capability; runs that map the cache carry it), not by ALL APPLICATION PACKAGES, which every AppContainer on the machine has; a cache an earlier version granted to them loses that entry once (#151). It is mapped for each run to its own journaled drive letter, removed by exact letter like the project drive. Publishing also removes, under the permission lock, older copies of the same install and copies unused for 30 days (each use stamps the entry's write time), except those a recovery record lists in `cached`, so a live run's copy is never removed. PATH entries and directly launched executables are redirected with case-insensitive path boundaries; absolute paths written in shell text are not rewritten. No administrator prompt is used. Toolchain inspection rejects reparse points and escaping paths, and is limited to 32 candidates, 100,000 inspected entries and 15 seconds per tree (30 seconds across inspection). Inaccessible toolchains are limited to 5,000 entries per command, and copies to 256 MiB and 30 seconds. A toolchain that is too large, or that cannot be inspected, granted or copied, stays unreadable, as before #106; the command still runs and its output names the folder and the reason. Skipping one never widens access. Cancellation during inspection or copying prevents the process from starting. The project appears at a temporary drive root (a free letter from `Z:` down to `D:`; a run holds two or three, and `P:`–`Z:` alone ran out at about four concurrent commands, #177) so relative paths work without exposing parent folders (#88). The entire `.git` temporarily stops inheriting the project grant, and the copy of its permissions made then leaves out the project capability's entries (`protect_acl`), so the lasting grant never makes it writable; the last overlapping run restores the original inheritance. The command runs in a job object with `KILL_ON_JOB_CLOSE`, an active-process limit, a memory limit for the whole job as well as per process, and a hard CPU-rate cap (`cpuPercent`, 90% of all processors by default, `WINDOWS_CPU_PERCENT`; #150); the `internetClient` capability is added only for unrestricted network, and a filtered command gets none (it reaches Patch's proxy only through `net-bridge` and the helper's relay pipe). Toolchain folders with more than 5000 entries are replaced by a small `bin` folder or skipped to bound recursive ACL work (#89). `HelperProcess` wraps the protocol; Entries moved into a granted project keep their old permissions (#140): `AddedEntries` (`tools/added_entries.ts`) keeps the names a recursive `fs.watch` reports as added (`rename` events only, at most 1000) per project from its first sandboxed command, and `ShellRunner` sends the outermost ones that still exist as `refresh`. Under the permission lock, after the project grant, `refresh_inheritance` skips entries outside the project, under a reparse point, under a `denyWrite` path or already allowed for the project capability, and otherwise sets the entry's own entries with inheritance turned on, so it and its subtree inherit the grant; a move can leave the old inherited entries as protected explicit ones, so protection is not taken as intent, but explicit denies stay and win. `findHelper` checks packaged resources then Cargo output. A packaged build runs `sandbox-helper.exe` and `file-helper.exe` only when they match the digests `electron.vite.config.ts` took from the helpers `npm run build` compiled just before the bundle (`__PATCH_NATIVE_DIGESTS__`; `trustedHelper` in `tools/native_integrity.ts`, #149). The digest (`peDigest`) is a SHA-256 of the executable without its header checksum, its certificate table entry, the certificate and trailing zero padding, the parts Authenticode signing writes, so signing a release later does not break it. A mismatch counts as a missing helper (no sandbox; file tools refuse) and logs the helper's name. The check is cached per size and file times; it does not stop someone who can also rewrite `app.asar` in the same per-user install folder, which needs a signed build with ASAR integrity (#26). The installer ships the helper and `net-bridge.exe`, and CI builds both. A missing or failed helper never falls back to an unsandboxed command. Real Windows coverage lives in `sandbox_windows.integration.test.ts`, including protected and readable installs, a copy instead of a grant for installs that could take one (#207), source-ACL preservation, staging write denial, cancellation and forced recovery.
- **Windows permission recovery (#91).** Before creating a profile or editing permissions, the helper flushes a cleanup record in `%LOCALAPPDATA%\Patch\sandbox-recovery`, locked against other writers but readable by other helpers. A named OS mutex serializes setup/recovery/cleanup, never command execution. Overlapping runs copy the original inheritance snapshot into their records; cleanup restores it only when no other record owns that path, so ending or recovering one command cannot expose metadata to another (#100). Normal and failed runs revoke their own grants and delete their profile and record. Forced termination bypasses destructors: the job still kills descendants, and the next helper startup recovers unlocked records before accepting commands. Live helpers retain their locks and grants. Recovery derives the exact SID from the recorded profile name, even if the profile was already deleted; it preserves unrelated container grants and retains records for retry if cleanup fails. Each record is recovered on its own: one whose cleanup fails is skipped so the helper still starts, its failures are counted in a `<name>.failures` file beside it, and after five failed starts it moves to `sandbox-recovery\quarantine` and is no longer retried. A record that can't be parsed, or whose file name doesn't match the profile it names, moves there at once (#152); no live run can own one, because records are published complete (written as `.pending`, then renamed), so other readers of the records skip it until then. Each failed attempt and each quarantined record is reported as a `log` event with a code (`recovery-failed`, `recovery-quarantined`, `record-unreadable`, `quarantine-failed`), the record name and its failure count, never paths or error text. Revoking a grant on a path whose permissions the user can't read (`ERROR_ACCESS_DENIED`) counts as done, because such a grant could not have been applied (#163). Entries from older helpers without a record cannot safely be distinguished from other deleted containers, so they are not automatically removed. Staged toolchain copies are journaled before they are created or exposed. Cleanup removes only exact-target mappings to that run's private staging root and its copied files, so live helpers and unrelated mappings are kept; old records default to no staging. Cleanup and recovery never remove cached toolchain copies; only publishing a new copy does. A cleanup failure after the command ran is reported in its output, its exit code is still sent, and the record stays for the next helper start to retry. Project drive mappings also record the exact letter and target before creation (#94). Letter selection, record publication and mapping creation run under the same permission mutex, including serialization with staging/temp mapping selection. The journal alone owns project mapping cleanup, preventing a late destructor from deleting a newer mapping for the same project. Recovery removes only that letter/target pair, never project files or another live run's mapping to the same project; exact-target removal preserves letters reused for different folders. Missing mappings make repeated recovery harmless, while other removal errors retain the record for retry. Older records default to no project mapping and cannot safely identify historical abandoned drives.
- **Network approvals are not a sandbox.** In Ask mode, `fetch_url` and `browser` require approval unless the exact URL hostname matches `allowedNetworkHosts` (empty by default, all ports, subdomains listed separately). Auto mode skips approvals, except that a call whose host is `localhost`/`*.localhost` or resolves to a loopback, private (RFC 1918, fc00::/7, fec0::/10), link-local (169.254/16 including cloud metadata, fe80::/10), carrier-grade NAT (100.64/10), 0/8, 192.0.0/24, 198.18/15, multicast, reserved (240/4) or unspecified address, or an IPv4-mapped, NAT64 (64:ff9b::/96, 64:ff9b:1::/48), 6to4 (2002::/16) or IPv4-compatible address carrying one of these (#252) always asks unless the host is in `allowedNetworkHosts` (`tools/net_address.ts`, #146). `fetch_url` resolves the host once and connects only to the checked addresses, so DNS rebinding cannot switch them; Chromium resolves names itself, so the browser cannot be pinned. Fetch redirects and the agent's browser navigation must keep the whole origin (scheme, host and port), even in Auto mode; the model must request another origin separately. Before the agent opens a page, and for addresses typed in the panel's address bar, browser navigation is not filtered; after the agent opens a page, link clicks and redirects in the panel stay on that page's origin. Browser subresources are not filtered by this policy, except that a public page in the agent's browser cannot load from local addresses or names that resolve to them (see Browser panel); Google `web_search` is not filtered. Approved hosts and search queries can still receive private data. Keep projects with secrets out of chats that read untrusted pages.
- **Editor command.** `editorCommand` is run through a shell with the file path quoted. File names with a double quote or line break are refused, and on macOS and Linux also names with `$`, a backtick or a backslash, which `sh` would still expand inside the quotes. The command itself is the user's own setting; changing it needs a native confirmation, though a compromised renderer can already write to the terminal panel.
- **Tool card ids are the app's own.** `Agent.runTool` gives every tool call a fresh UUID for its card, approval and edit backup. The provider's tool-call id is used only to pair the call with its result in the API request, since some OpenAI-compatible servers reuse ids across turns.
- **Undo is locked against sending.** `ChatManager.undoEdit` counts as busy until the file is restored and the note for the model is queued and saved, so a message, resume, compact or chat/project switch cannot start in between. The pending note is saved with the chat (`SavedChat.pendingNotes`) and survives a restart; it is sent, and cleared, with the next message or resume.
- **Log redaction is pattern-based.** Recognized `sk-`, `gsk_`, `xai-` and `AIza` keys, bearer tokens and named API-key/authorization fields are redacted; unrecognized secret formats can still appear in error messages. Review logs before sharing.
- **IPC handlers trust the renderer's arguments.** The renderer is sandboxed, has a strict CSP and only shows sanitized model output, and pages in the browser panel have no preload, so they cannot call IPC. Handlers that take paths (`git:*`, file tools) still confine them to the project with `Workspace.resolve`. The renderer's IPC surface is powerful by design: the terminal panel types into a real shell, so a compromised renderer still amounts to code execution. Settings that choose MCP commands, the editor command, Auto mode, allow `allow`/`delegate` rules, add allow-list entries or change a base URL need a native confirmation (see Security model), as do new entries in a project's allow-lists, and handlers only answer the app page's top frame.
- **Retries repeat the whole request.** A failure in the middle of a long answer discards the streamed text and asks again, so the tokens of the failed attempt may be billed. On the Anthropic path, this also repeats any server-side compaction or `pause_turn` continuations from the failed attempt; their responses are not left in saved model history. Only errors that usually pass are retried; a wrongly classified error costs at most 4 extra requests (about 30 seconds) before it is shown.
- **A compaction is a lossy summary written by the small model.** Details can be missed or wrong, and the model then works from the summary as if it were what happened; the unedited history stays in the chat file but is no longer sent. The summarizing request is not included in the token and cost totals (`CompletionClient` reports no usage). The first request after a compaction misses the prompt cache. Context size is only known after a request, and the 150k suggestion is one value for every model, not a limit of the model in use (custom endpoints can have far smaller windows).
- **Undo covers the edit tools only.** Changes made by commands the assistant ran, or by anything else, have no backup. A backup is a plaintext copy of the file on disk in the app's data folder (until the chat is deleted or 50 newer edits push it out), which matters for projects with secrets. The pending model notification is saved with the chat and delivered on the next Send or Resume, including after a restart.
- **Local logs can name paths.** `logs/app.log.jsonl` never holds chat history or API keys (keys and tokens are redacted), but error messages such as "Folder not found: …" can contain file paths. The files stay on the machine and rotate at 512 KB; nothing is sent anywhere.
- **Project instructions, `AGENTS.md` and project skills** are prompt text, not trusted configuration: they are added to the system prompt (skills when loaded), so a malicious repository can steer the model. Approvals still apply to edits and commands.
- **MCP servers run with the user's permissions.** A stdio server is a program the user configured; approval covers each tool call, not what the server does on its own. Stdio servers start in a private folder (`mcp` in user data); one that names `${project}` gets the open project and reconnects when the project changes, including through History (#241), and a server that stops on its own is started again (#243). Stored `env` and header secrets are keyed by server name; renaming a server carries them over only when exactly one old and one new server share the same endpoint (URL, or command and arguments), so a rename never sends a saved header to another host (#23).
- **Git panel commits and pushes use the repository's remote and identity, but not its hooks.** Every panel call runs with `core.hooksPath=/dev/null` (see the Git panel entry above), so **Commit** and **Push** do not run commit or pre-push hooks; tools like husky only run from your own terminal, where they also run whatever the agent left in the project. A push goes to whatever URL the repository's `origin` or upstream names, with the user's credentials. **Generate** sends the uncommitted diff to the configured model provider, like a chat would. A repository whose filter drivers are defined in its local config (for example `git lfs install --local`) is shown and committed without those filters in the Git panel.
- **Release signing**: Windows releases require signing credentials and valid Authenticode signatures on both the app and installer before publishing; checksums accompany the installer. Local development builds may remain unsigned. Signing credentials have not been provisioned, so releases are blocked (#26); macOS entitlement changes still need signed packaged testing (#28, #22).

## Tests

- `npm run test:unit` — Vitest unit tests next to the code (`*.test.ts`). The provider tests run the real SDKs against a local mock HTTP server (`llm/test_server.ts`).
- `npm run test:e2e` — builds the app and drives it with Playwright's Electron support, using a throwaway profile and mock APIs: Claude (`tests/e2e/mock_claude.ts`, enabled by `PATCH_TEST_ANTHROPIC_URL`) and OpenAI (`tests/e2e/mock_openai.ts`, enabled by `PATCH_TEST_OPENAI_URL`, used only when no custom base URL is set so the Responses API path runs). These hooks, and `PATCH_TEST_CODEX_URL` / `PATCH_TEST_CODEX_TOKEN_URL` for ChatGPT sign-in, only work when the app is not packaged; unit tests that use them call `setPackagedBuild(false)`. Covers window security, settings, a full tool-using chat with approval on both providers (including the encrypted reasoning round trip), the UI, the panels, Git panel Initialize stopping the project's background commands first (`git_init.test.ts`), a project `file://` page having no network (#229), MCP `${project}` servers reconnecting when History opens another project's chat (#241), retries of rate limits and overloads (the Claude mock can script failures with `Retry-After`), the local error log and Help menu, stopping and resuming long runs (the mock can hold an answer open until Stop, and `launchApp({}, { userData })` restarts on the same profile), killing the app mid-run and resuming from whatever it had saved (`RunningApp.kill()` ends the whole process tree, as a crash would), switching between open projects, very large tool results, a catastrophically backtracking grep pattern that must not freeze the app, the transcript view (opening a long chat at its end, a tall approval card staying in view, focus after Undo), undoing approved edits, Compact chat, image attachments, MCP tools, plan mode, per-project allow-lists, project skills, the `task` subagent, the single-instance lock, the terminal without a project, and the documentation screenshots with text contrast checks. The chat list, the composer's model picker and approval/Plan switches, and the status-bar branch are covered by `chat_controls.test.ts` (#62). Closing the app or a mock server fails with a clear error after 20 s and 5 s instead of hanging until the hook timeout. The harness also captures the main process's stderr, so tests can assert that no IPC handler errors were logged.

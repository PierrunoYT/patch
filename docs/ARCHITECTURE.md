# Architecture

Patch is an Electron app written in TypeScript and built with electron-vite. All logic that touches the file system, the network, API keys or child processes runs in the **main process**. The **renderer** is a sandboxed page without Node.js access that talks to the main process only through a typed IPC contract.

```
┌──────────────────────── main process (Node) ─────────────────────────┐
│ index.ts          wiring, IPC handlers                                │
│ settings.ts       settings, keys, ChatGPT session (safeStorage)       │
│ projects.ts       recent projects, per-project instructions           │
│ chat_manager.ts   active chat, autosave  ──▶ chat_store.ts            │
│ agent/            agent loop, chat session, system prompt             │
│ llm/              Anthropic + OpenAI conversations, small-model calls │
│ tools/            read/edit/write/grep/list, run_command, web, browser│
│ search/           embeddings index for search_code                    │
│ panels/           terminal (node-pty), git (simple-git), browser      │
└───────────────▲──────────────────────────────────────────────────────┘
                │ typed IPC (src/shared/ipc.ts)
┌───────────────┴── preload (sandboxed) ──┐   ┌── <webview> guest ──────┐
│ window.api.invoke / window.api.on,       │   │ pages opened in the     │
│ allow-listed channels only               │   │ browser panel; no Node, │
└───────────────▲──────────────────────────┘   │ no preload             │
┌───────────────┴── renderer (no Node) ────┐   └─────────────────────────┘
│ app.ts, views/ (transcript, composer,     │
│ sidebar, dialogs, panels), markdown.ts    │
│ (DOMPurify)                               │
└──────────────────────────────────────────┘
```

## IPC contract

`src/shared/ipc.ts` declares every channel:

- `InvokeApi` — renderer → main request/response (`window.api.invoke('settings:get')`).
- `EventMap` — main → renderer pushes (`window.api.on('chat:event', …)`).

Handlers (`src/main/ipc.ts`, `handle` / `send`) and the preload bridge are typed from these maps, so a renamed channel or changed payload fails to compile. The preload forwards only channels listed in `INVOKE` / `EVENTS`; those lists are `Record<Channel, true>` so forgetting a new channel is also a compile error.

## Chats and the agent loop

1. The renderer calls `chat:send`. `ChatManager` creates a `ChatSession` on the first message, fixing the chat's project, model and system prompt, and returns as soon as the session starts. Setup errors (no project, missing key) come back immediately.
2. `Agent.send` (`src/main/agent/agent.ts`) adds the user message and runs turns:
   - The tool list is rebuilt at the start of every turn (`ChatManager` passes `tools: () => …`), so a tool that becomes available while a chat is open, such as `search_code` after an OpenRouter key is saved, is offered from the next turn on. The system prompt is not rebuilt; it stays byte-identical for prompt caching and tells the model to use optional tools only when currently offered. When the chat starts, `agent/agent_file.ts` reads `AGENTS.md` (else `CLAUDE.md`, capped at 20,000 characters) from the project root into the prompt, before the per-project instructions. `ChatSnapshot.agentFile` carries its name so the status bar can show that it is loaded; a saved chat keeps the file it started with.
   - `conversation.runTurn` streams the model's answer (text and summarized thinking are forwarded as `chat:event`s).
   - A request that fails for a reason that usually passes is repeated by the agent loop (`runTurnWithRetries`), not by the provider SDKs: their clients are created with `maxRetries: 0` for conversations (the small-model clients for titles and compaction summaries get 3 silent SDK retries, `BACKGROUND_RETRIES`). `agent/retry.ts` decides from the error's shape, so it covers Anthropic, OpenAI and compatible endpoints: HTTP 408, 429 and 5xx (including Anthropic's 529), errors sent inside a stream after a 200 response (`overloaded_error`, `api_error`, `rate_limit_error`, `server_error`, read from the most specific type or code the SDK puts on the error, since the outer type is just `error`) and connection problems (`ECONNRESET`, timeouts, DNS failures, SDK connection errors). Not retried: 501 and 505, other 4xx, an out-of-quota 429, a refused connection (nothing is listening, e.g. Ollama not started), aborts and anything else. Up to 4 retries wait about 2, 4, 8 and 16 seconds (±25%), or the provider's `Retry-After` / `retry-after-ms` when given; a request to wait more than 60 seconds is not retried. Each retry adds a notice to the chat ("Rate limited (429). Retrying in 2 s (retry 1 of 4)…"), discards the text the failed attempt had streamed, and can be stopped during the wait. A conversation only records a turn once it has succeeded, so repeating a request cannot duplicate history; the last error is shown as before once the retries are used up.
   - For each tool call: validate the input against the tool's Zod schema (a failure names the missing fields and the fields received, and is returned to the model as an error result) → ask the permission rules (`decidePermission`, `agent/permissions.ts`; `reject` answers the model without running, `allow` skips ordinary approval but not a per-call `mustAsk` safety check, `ask` forces approval) → build a preview (diff, command, or URL) → if the tool needs approval (`mustAsk` for this call, or, absent a rule, `alwaysAsk` or `requiresApproval` in **Ask** mode when the call is not pre-approved), wait for `chat:decide` → run it. Consecutive calls to `parallelSafe` tools run with `Promise.all`; every other call runs alone after them, and results keep the order of the calls. The result text, summary and errors pass through `redactSecrets` (`tools/redact.ts`) before they are returned to the model or emitted. The `isPreApproved` callback that `ChatManager` passes to each session checks shell commands against `allowedCommands` (the global list in Settings plus the chat's project's own list from `projects.json`, `mergeAllowLists`, both read on every call so changes apply to open chats) (whole-word prefix match; never for a command containing `; & | < >`, a backtick, `$`, `(`, `)`, `{`, `}` or a line break, because PowerShell runs `(...)` and `{...}` even inside a program's arguments), fetch/browser hostnames against `allowedNetworkHosts` (global plus project, the same way), and local browser files against workspace confinement. File edits always ask in Ask mode.
   - All results of a turn go back to the model together, then the next turn starts. The loop ends when the model answers without tool calls (or after 200 turns).
3. Declining **with** feedback sends the feedback to the model as the tool result and continues; declining **without** feedback stops the task. Stopping (`chat:stop`) aborts the request and running commands. Every tool call always gets a result, even when skipped or stopped, or when it came with a refusal, so the history stays valid for the API. Tool calls from a response cut off by the output limit or by a full context window are not run, since their input may be cut off too.
4. Every event goes through `applyChatEvent` (`src/shared/chat.ts`) in both processes: the main process keeps the transcript for saving, the renderer for display. Streaming deltas are applied in batches once per animation frame. `TranscriptView` re-renders only items whose object changed and updates their element in place, moving keyboard focus back to the same control (`data-focus-key`); items are grouped in chunks of 50 (`CHUNK_SIZE`), and off-screen chunks and items skip layout (`content-visibility: auto`), so a frame at the bottom of a long chat lays out a few dozen chunks rather than every item; finished tool cards and Thinking build their body when first expanded (measurements in `docs/PERFORMANCE.md`). Because off-screen items count at a placeholder height until laid out, the view jumps to the bottom again for a few frames after a chat is opened or an item is added, and stays at the bottom when the scroll area shrinks; the user's own scrolling ends this. The reducer also caps what a tool card keeps (`TRANSCRIPT_LIMITS`): the last 20,000 characters of output (`outputOmittedChars` counts what was left out, over all streamed chunks), the first 2,000 lines and at most 200,000 characters of a diff (`diffOmittedLines`), the first 20,000 characters of a command (`commandOmittedChars`), and the first 20,000 characters of a plan (`textOmittedChars`). The card says what was left out; on an approval card that is a warning that approving applies the whole change. This limits only what is shown and saved in the chat; the tools' results for the model and the change that is applied are not affected, and exports say where content was left out.
5. The chat is saved (debounced 500 ms, immediately after every tool-result batch, and when a task finishes) to `userData/chats/<id>.json`, including the provider-native conversation, so reopened chats continue exactly where they stopped.
6. A short title is generated by the small model after the first message.
7. **Compact chat** (`chat:compact`, `ChatSession.compact`) shortens what is sent without touching what is stored, so the history stays append-only. `conversation.planCompaction()` picks a cut (`llm/compaction.ts`): the latest place that still leaves about 40k characters after it and where the history may start without separating a tool call from its result, which is provider-specific (Anthropic: before an assistant message or a user message that is not a tool result; Chat Completions: anywhere but before a `tool` message; Responses: before a message or a reasoning item, never before a function call or its output, and never right after a reasoning item, whose message or call would otherwise be sent without it). The text before the cut (tool results cut to 1,500 characters, inputs to 600, at most 300k characters in all) goes to the small model, which returns a summary. `applyCompaction(summary, keepFrom)` then stores a `CompactionState { summary, keepFrom }` next to the messages in the saved conversation. From then on each request is built from the summary followed by the messages from `keepFrom`: a separate user message in front of an assistant message, or joined to the first block of a user message (a copy; stored messages are never edited). The Responses path always sends it as a separate user item. A later compaction starts at the previous `keepFrom` and hands the previous summary to the summarizer. `UsageTotals.contextTokens` (input plus cache reads and writes of the last request) drives the status-bar hint; `COMPACT_SUGGESTED_TOKENS` in `src/shared/models.ts` sets when it turns into a suggestion. This is separate from the server-side compaction Claude models do on their own (`compact-2026-01-12`), which the API applies to the request and returns as blocks in the history.

A crash mid-run is survivable the same way. A run saves the chat immediately when it starts (with its new user message) and after each tool batch, and while a run is in progress the saved `resumable` flag is true, so a chat reopened after a crash offers Resume wherever the crash happened: during a model request, while tools ran, or in the 500 ms save debounce before the latest tool calls were written. The save after a tool batch is a checkpoint: it writes only the chat file, not the chat index, and sends no `history:changed`, unless the chat is not in the index yet. A checkpoint serializes the chat at once and writes the file in the background (`writeJsonLater` in `storage/json_file.ts`: one write per chat at a time, in order, through a temporary file and a rename); the regular saves are synchronous and replace a checkpoint that has not landed. A crash in the few milliseconds before a checkpoint lands resumes from the save before it. The history list (title, time, cost) catches up with the next regular save, at the latest when the run ends. The flag is cleared by the save when the run ends, unless the user stopped it. A conversation that ends with unanswered tool calls is also marked resumable; resuming appends a synthetic failed result for each of them, saying the action may or may not have run, since a result is only recorded once the whole batch finishes and earlier calls in that batch may already have taken effect. Loading also closes tool rows left running or awaiting approval, and stops the typing indicator on an assistant row saved mid-stream. Stopping a run marks it resumable only after its abort handling settles and tool results are paired. `chat:resume` appends a continuation instruction to the model history (not a duplicate visible user request), warning the model to inspect state before retrying interrupted side effects. The `resumable` flag is saved and restored; declining an approval without feedback does not set it. This continues the task from conversation history, not from an exact execution checkpoint, and cannot guarantee that the model never repeats an action.

`ProjectStore.opened()` tracks tabs separately from recent projects. `ChatManager` retains each inactive project's idle session, workspace and shell runner; switching back restores its chat, including stopped-run state. The renderer keeps unsent text and attachments per project in memory and drops them when a tab closes. Switching or closing projects and starting another chat requires the current run to settle first, preventing approvals from crossing workspaces. The interactive terminal restarts on switches. Agent-started background commands survive normal turn completion and project switching, but Stop cancels the active project's background jobs as well as its current foreground command; closing their chat/tab also stops them. Other projects' jobs and the interactive terminal are not cancelled by Stop. Tabs and drafts are not restored after app restart; saved chats remain accessible through history. `project:opened` and `project:close` are part of the typed IPC contract.

Project-change side effects compare the stored active paths before and after opening, closing or removing a project. The main process stops the interactive terminal only when that path changes; the renderer likewise resets terminal/Git state only on a real project change. `ChatManager.projectChanged` does not republish an unchanged project's snapshot, so clicking the active tab, reopening its current chat, or closing another tab preserves expanded transcript sections and scroll position. Opening a different chat within that project changes the transcript but keeps the terminal and commit draft. Closing the last project publishes the empty snapshot after its session is discarded.

`ChatManager.open` resolves the saved chat's target workspace and prepares its provider conversation, session and workspace-bound shell without changing the active or parked state. Existing retained sessions are reused; newly restored sessions enter `liveSessions` only after they are installed. A missing provider key or a session-construction error therefore leaves the current project and chat untouched. Session factories accept explicit target resources so restoring a different project's chat cannot accidentally bind its tools to the current project's workspace. The `history:open` handler sends the current project in `finally`, resetting the terminal only if the active project actually changed.

## Model providers (`src/main/llm/`)

`Conversation` is the provider-neutral interface: `addUserMessage`, `addToolResults`, `runTurn`, `serialize`. Each implementation stores history in its API's native format, and only records an assistant turn once the request has succeeded, which is what makes it safe for the agent loop to repeat a failed request.

The SDK clients for conversations are created with `maxRetries: 0` (`createAnthropicClient` / `createOpenAIClient`); retries of transient errors are done by the agent loop so they can be shown in the chat (see [Chats and the agent loop](#chats-and-the-agent-loop)). Clients for the small model (chat titles, compaction summaries) are created with 3 silent SDK retries (`BACKGROUND_RETRIES`).

The built-in catalog gives Claude Haiku 5.5 and Claude Fable 5.1 1M-token context windows and GPT-6.1 Sol a 1.05M-token context window. Legacy Claude Haiku 4.5 and GPT-6 Sol remain recognized so existing settings and saved chats continue to work.

**Anthropic** (`anthropic.ts`, official SDK, `client.beta.messages.stream`):

- History is **append-only**: assistant turns are stored exactly as returned, including thinking, compaction and fallback blocks, because current Claude models reject or ignore edited history.
- Server-side `pause_turn` and `compaction` responses are staged within `runTurn` and included in continuation requests, but not in serialized history until `runTurn` returns successfully. A failed or aborted continuation discards the staged messages, so an agent retry starts from the original history. Successful responses are appended together without rewriting their blocks; the existing five-continuation limit still applies.
- Billable usage accumulates across successful continuation requests, but the reported context size comes only from the final request. A server compaction can therefore reduce the displayed context without subtracting previously billed tokens.
- Features are enabled per model (`claudeCapabilities` in `src/shared/models.ts`) because unsupported parameters are rejected:
  - Fable 5.1, Opus 5.5, Sonnet 5.5 and Haiku 5.5: adaptive thinking with summarized display, `output_config.effort` (Settings → Effort) and server-side threshold compaction (`compact-2026-01-12`). Anthropic's compatibility list explicitly includes Haiku 5.5.
  - Fable 5.1, Opus 5.5 and Sonnet 5.5: refusal fallback (`fallbacks: "default"`, `server-side-fallback-2026-07-01`). Haiku 5.5 does not enable refusal fallback.
  - Haiku 4.5 and unknown ids: a plain request.
  - Image input (`images`): Fable 5.1, Opus 5.5, Sonnet 5.5, Haiku 5.5, Haiku 4.5 and the other known current ids; not unknown ids, since an image the model cannot take is a 400. `acceptsImages(model)` applies it (and allows every OpenAI or compatible id, as before). `ChatManager.send` refuses a message with images for a chat whose model does not accept them, before a chat is created or anything is sent; the composer disables the paperclip and paste with the same message (`imagesNotSupportedMessage`). Images in tool results (browser screenshots) are not gated.
- Prompt caching via top-level `cache_control`, plus an ephemeral breakpoint on the system text and on the last tool, so that prefix can stay cached while the conversation tail moves. The system prompt is built once per chat and includes a project map two levels deep (file counts per folder, and entry points from `package.json`, `pyproject.toml`, `Cargo.toml`, and `go.mod`), capped at 2,500 characters. It is built on the main process, so the walk that counts files below the two shown levels stops after 20,000 entries and shows the counts as lower bounds (`(19028+ files)`); a home folder or a folder of many repositories then takes about 0.2 s instead of minutes. Each completed Anthropic turn appends one local log line (`llm` / `anthropic request`) with cache reads, cache writes, token counts, tool count, system length, and whether the tool-name hash or the system hash changed. Extra tools are sorted by name so MCP tools do not shuffle the prefix. With Settings → Prompt cache on, an idle Claude chat re-sends its last request about every 4 minutes for up to an hour (`ChatSession.scheduleKeepAlive`, `AnthropicConversation.keepCacheWarm`): `max_tokens: 0`, not streamed, the same tools, system, thinking, effort and betas, a placeholder user message at the end (the API rejects a request that ends with the assistant's reply) and the breakpoint on the reply's last block instead of the top-level automatic one. It only reads the cache, which refreshes the entry's 5-minute timer; the next real request then reads it. Its usage is added to the chat, and it stops on the next run, compaction, dispose or a failure.
- `edit_file` opts into `strictInput`: for Claude models with `claudeCapabilities.strictTools` (Fable 5.1, Opus 5.5, Sonnet 5.5, Haiku 5.5, the other known current generation and Haiku 4.5), its definition uses `strict: true` and omits `eager_input_streaming`. The API enforces required fields and types, including in batched calls, without forcing tool use or disabling parallel calls. The SDK's `zodOutputFormat` schema transformation moves unsupported constraints such as `minLength` into descriptions; the agent still validates the original Zod schema before preview or execution. Same-model subagent stand-ins retain the flag to keep the tool prefix identical. MCP JSON Schemas never opt in. See [strict tool use](https://platform.claude.com/docs/en/agents-and-tools/tool-use/strict-tool-use) and [schema limitations](https://platform.claude.com/docs/en/build-with-claude/structured-outputs#json-schema-limitations).
- Other tools and unknown Claude ids keep `eager_input_streaming`, so large inputs (file contents) stream as generated without API validation. The agent validates every input itself, regardless of provider strict mode. A turn whose streamed tool input cannot be parsed is re-issued (up to twice).
- No `temperature` and no forced `tool_choice` (both rejected by current models).

**OpenAI** (`openai_responses.ts`, used when no custom base URL is set and no ChatGPT session is the credential): the Responses API, because GPT-6 models only support function calling in Chat Completions with reasoning turned off (and GPT-6 Astra cannot turn it off); GPT-6.1 Sol likewise uses Responses for tool calling. Requests are stateless (`store: false`); reasoning items come back encrypted (`include: ['reasoning.encrypted_content']`) and are sent back unchanged so the model keeps its reasoning across tool calls. The output items are stored as the API returned them, minus the fields the SDK's stream helper adds (`parsed_arguments` on function calls, `parsed` on message text): the API rejects those as input (`toInputItem`, applied when a turn is stored and again when history is sent, so older saved chats are repaired). Reasoning effort follows Settings → Effort, reasoning summaries are shown as "Thinking", and `truncation: 'auto'` drops the oldest items when the context fills up.

**Sign in with ChatGPT** (`codex_auth.ts`, `openai_route.ts`): Settings can sign in with a ChatGPT account for official models. `chatgpt:sign-in` opens `https://auth.openai.com/oauth/authorize` with the public PKCE client and the loopback redirect `http://localhost:1455/auth/callback`. The code is exchanged only when the callback `state` matches that login. A callback with a different state is answered and ignored, so the login keeps waiting. A timeout, a sign-in replaced by a newer attempt, or a failure to bind port 1455 stores nothing. The access token, refresh token, and ChatGPT account id are stored on `settings.json` under `chatgpt`. The two tokens use the same `safeStorage` sealing as API keys. `chatgpt:sign-out` removes the session. The renderer receives `{ signedIn, accountLabel }` and never the tokens.

With no custom base URL, `chooseOpenAIRoute` sends an official chat to the Codex responses backend (`https://chatgpt.com/backend-api/codex`) when the session has an access token and an account id. That includes the case where an API key is also stored. The request sends `Authorization: Bearer` from the session and a `ChatGPT-Account-ID` header. `CodexAuthedConversation` refreshes an access token that expires within 60 seconds, once, before the turn. Turns that need a refresh of the same token share that request. The new tokens are stored only if that refresh token is still the one saved, and a permanent failure clears the session only in that same case. `invalid_grant` and the other permanent refresh failures then fail the turn with `ChatGptSignInRequiredError`. The agent loop does not retry that error. With no session, an API key still uses the Responses API. A non-empty OpenAI-compatible base URL still uses that URL, the API key, and Chat Completions, and does not send the ChatGPT session. Embeddings and the small model (titles, compaction, commit messages) still require the OpenAI API key. A Codex request that the backend rejects is shown as that error. The app does not fall back to the API key for the same turn.

`LlmService.build` selects the Responses backend for new and restored chats from the current credentials. Codex requests omit `truncation`, which the subscription backend rejects with HTTP 400; platform requests retain `truncation: 'auto'`. Both keep `store: false` and encrypted reasoning. The backend is not persisted in the conversation, so reopening a chat after signing in or out follows the current route. Subscription requests send the full history or the saved compaction summary and retained items; Patch does not silently discard older items locally.

**OpenAI-compatible endpoints** (`openai.ts`, used when Settings → _OpenAI-compatible base URL_ is set, e.g. Ollama, OpenRouter, LM Studio): Chat Completions streaming with function tools, since most compatible servers only implement that API. With no server-side compaction, the oldest turns are left out of each request once the history passes ~100k tokens (estimated from the text, with images at a small fixed size rather than their base64 length); the first user message (the task) and the step in progress (the last assistant message with its tool results) are always kept, and a tool result is never sent without the call it answers (`trimHistory`). Only the copy that is sent is shortened, the stored history is not (chats saved by older versions were shortened when they were saved). Use **Compact chat** to keep the earlier work as a summary instead of losing it.

In both OpenAI paths, tool screenshots are sent as a follow-up user message because tool results cannot carry images. Saved chats record which API their history belongs to (`api: 'responses' | 'chat'`).

**Summary/title model** (`CompletionClient`): selected for the chat's pinned provider, not the current global model selection. Standard provider chats use Claude Haiku 5.5 or GPT-6 Luna according to available keys. The OpenAI `mid` subagent choice uses GPT-6.1 Sol; the Anthropic `small` choice and `finder` use Haiku 5.5. Custom Chat Completions chats use their own pinned model on the configured compatible endpoint, rather than assuming it serves GPT-6 Luna. Titles and Compact chat summaries require structured outputs (`output_config.format` / `response_format`) validated by Zod; compatible endpoints must support JSON-schema output. An unsupported summary request reports an error and leaves compaction state unchanged. Haiku 4.5 and GPT-6 Sol remain recognized for restored chats and retain their existing price estimates.

A chat keeps its model. The model picker in the composer (or Settings) sets the model for new chats through `settings:update`; it is locked once the chat has started.

MCP servers are configured in Settings as JSON (`mcpServers`). The `McpHub` connects in the background (stdio child processes or Streamable HTTP), caches each server's tools for the synchronous per-turn tool callback, reconnects when the setting changes, and reports per-server status via `mcp:status` for the settings dialog. Names are namespaced and sanitized (`mcp_<server>_<tool>`) so servers cannot collide or forge the name of a built-in tool; a failed server shows its error and the rest keep working.

Project skills are markdown files in `.patch/skills/` (`tools/skills.ts`). When a chat starts, `listSkills` reads the first 4 KB of each (up to 20; the prompt says how many more there are) and the system prompt lists their names and first non-heading lines. The skill list is frozen with the prompt: `load_skill` is offered exactly when the chat's prompt lists skills (`promptListsSkills`), so skills added or removed mid-chat change neither the prompt nor the tools, and the prompt cache stays warm. The model loads the text (up to 20,000 characters, `MAX_SKILL_CHARS`) on demand. The folder goes through `Workspace.resolve`, so a skills folder linked outside the project is ignored, linked files inside it are skipped, and skill names are restricted to file-name characters. The `task` subagent may load skills too.

Rules enforced in code, not only in the prompt:

- `Workspace.resolve` confines every path to the project root. Links are resolved first, also for a path that does not exist yet: its deepest existing part is resolved and the rest appended, so `link/new.txt` through a folder link to somewhere else is refused rather than created outside the project. A link that leads nowhere is refused. `.gitignore` and `.ccignore` are resolved through the same confinement check; external or dangling ignore-file links are ignored rather than read.
- Existing files must be read in the current chat before `edit_file` or `write_file` may change them. The check runs both in `preview` (so an unread file is rejected before the user is asked to approve) and in `run`.
- **Encoding.** `requireUtf8ForEdit` (`tools/text_files.ts`) validates the complete original buffer with Node's `isUtf8` before decoding. `edit_file` and existing-file `write_file` check in both preview and execution; `planPatch` checks updates, including moves, before any patch file is written. Non-UTF-8 files are refused without conversion; valid UTF-8 BOMs and literal replacement characters remain valid. New files are written as UTF-8; patch deletion does not re-encode a file.
- **Undo.** `edit_file` and `write_file` return `ToolOutput.undo` (`EditUndo`): the project-relative path, the exact previous bytes (`null` when the tool created the file) and the SHA-256 of what was written. It is never shown to the model. `Agent` passes it to `onEditApplied(toolId, edit)`, which `ChatManager` connects to `EditBackups.record` (`tools/edit_backups.ts`, one JSON file per edit in `userData/edit-backups/<chat id>/`, named by a hash of the application-generated tool-card id, newest 50 per chat, deleted with the chat). If that succeeds the `tool-end` event carries `undoable: true` and the card gets `undo: 'available'`. `edit:undo` (`ChatManager.undoEdit`) works only when the chat is idle and the card is `available`; `EditBackups.undo` resolves the path through `Workspace.resolve`, refuses unless the file's current bytes hash to `afterHash` (so later changes are never lost, and edits to one file are undone newest first), writes the bytes back or deletes the created file, and uses the backup up. `ChatSession.editUndone` then emits `tool-undone` (card `undo: 'undone'`), removes the file from `readFiles` so the model has to read it again, and queues a note that is put in front of the next message (or the resume instruction) sent to the model, so the conversation itself stays append-only. The note is saved with the chat until it is sent.
- **Protected files.** `isGuardedPath` (`tools/guard.ts`) lists paths whose edits always need approval (credentials and keys, `.git`, editor/agent folders, shell start-up files, databases, system folders; `.env.example`-style files are exempt). `write_file`, `edit_file` and `apply_patch` declare it with the optional `mustAsk(input, context)` of `AgentTool`, which asks in Auto mode too. A check that throws counts as "no".
- **Secret redaction.** `redactSecrets` (`tools/redact.ts`) replaces private keys, AWS/GitHub/Slack/Anthropic-style tokens, JWTs, passwords in URLs (`postgres://user:…@host`, keeping scheme, user and host; #123), quoted credential values and `.env`-style secret lines with `[REDACTED:_____]` in every tool result, summary and error. The patterns are bounded and anchored so a long line costs linear time on the main process. The file tools refuse input containing the placeholder, so a redacted value is never written back.
- **Permission rules.** `Settings.permissionRules` (`PermissionRule` in `src/shared/settings.ts`, validated by `parsePermissionRules`, edited as JSON in the dialog) are evaluated by `decidePermission` (`agent/permissions.ts`): the first rule whose `context`, `tool` glob and `matches` globs fit wins. `delegate` spawns the named program without a shell, sends `{tool,input,context}` on stdin and takes `allow`/`reject`/`ask` from stdout (15 s; any failure rejects). `ChatManager` passes the `thread` evaluator to the session and the `subagent` one to the subagent tools. `changesToConfirm` asks the user (native dialog) before a new or changed `allow` or `delegate` rule is saved. It also confirms any change to the ordered prefix through an existing `ask` or `reject` rule (#114): removals, field edits and preceding-rule reorders can bypass protection even when that rule stays at the same index. This conservative comparison uses serialized rule values, not glob containment; unchanged prefixes and new protective rules appended at the end stay quiet.
- Command output is capped (start and end kept) and decoded as a UTF-8 stream per pipe, so a character split across two reads stays intact; commands are killed with their whole process tree on stop or timeout.

To add a tool: create it with `defineTool` (name, description, Zod schema, `requiresApproval`, optional `preview`, `run`) and add it to `registry.ts` (`CORE_TOOLS`, or a configuration-gated entry in `availableTools`). Tools that need per-chat state (`search_code`, `task`, MCP tools) are passed to the agent as `extra` from `ChatManager`.

### macOS Service Boundary

`seatbeltProfile` uses exact `global-name` filters for Mach lookup: only `com.apple.system.opendirectoryd.libinfo` (CLI user/group lookup). Network-enabled commands additionally get the DNS/configuration and certificate-trust services `com.apple.SystemConfiguration.DNSConfiguration`, `com.apple.SystemConfiguration.configd`, `com.apple.networkd`, `com.apple.ocspd`, `com.apple.trustd.agent` and `com.apple.TrustEvaluationAgent` (DNS itself goes through the mDNSResponder socket, which `network*` covers). LaunchServices, URL-session and general background-execution daemons are not granted, regardless of network access, and an explicit trailing deny keeps LaunchServices and XPC services closed. The preferences daemon (`cfprefsd`) is not granted either: it would read preference files from the hidden home folder on the command's behalf. Tools that read user defaults (`defaults`, `xcodebuild`) therefore see built-in defaults, and notify/os_log calls fail silently.

Shared memory is denied except libomp's `/__KMP_REGISTERED_LIB_<pid>` registration names (PyTorch), because a broader grant would let a command open a host process's named segment. Named semaphores are allowed for Python `multiprocessing` locks. Workloads that create arbitrary POSIX shared memory (`initdb` with `dynamic_shared_memory_type=posix`, `multiprocessing.shared_memory`) fail inside the sandbox. Direct `process-exec`/`process-fork` remain necessary for shells, compilers and toolchain subprocesses, which inherit the profile; they do not grant service-mediated application launches. `sysctl-read` is limited to named OS/hardware discovery entries (Codex's baseline plus `kern.boottime`, Rosetta/compat version checks and all `hw.optional.` CPU flags). `kern.procargs` (other processes' arguments and environment) is not granted. Seatbelt does not filter `kern.proc` process-table reads by sysctl name (macOS CI read a host process without the grant), so commands can list host processes and their owners; the `kern.proc.pid.`/`kern.proc.pgrp.` prefixes stay for parity with Codex. Writes are not granted.

The #99 LaunchServices escape is a static risk, not a claim of a demonstrated exploit. `sandbox_macos.integration.test.ts` exercises actual service lookup and a harmless app bundle with successful unsandboxed controls, shared-memory denial, a local HTTP endpoint that direct and Foundation (`NSURLSession`) requests must not reach with the network off, and representative CLI tools. Seatbelt's `.git` rule is path-based, so `sandbox_git.integration.test.ts` requires it to refuse creating a hard link to metadata, not only writes through one. Only a real Mac can establish enforcement and toolchain compatibility; off-platform skips do not count as successful isolation.

### Command Environment Boundary

`tools/env.ts` separates the legacy `scrubEnv` credential-name filter (unsandboxed agent commands and the host container-engine client) from `sandboxEnv`, the native command boundary. Native children inherit only `PATH`, `JAVA_HOME`, `GOROOT`, `GOPATH` and `RUSTUP_HOME`; Unix additionally inherits `LANG`, `LC_ALL`, `LC_CTYPE`, `LC_MESSAGES` and `TZ`, and gets `GIT_CONFIG_GLOBAL=/dev/null`: Seatbelt denies reading `~/.gitconfig` instead of hiding it, and Git aborts on a configuration file it cannot read. Windows additionally keeps OS/program-directory variables (`SYSTEMROOT`, `WINDIR`, `COMSPEC`, `PATHEXT`, Program Files/Common Program Files variants) and `LOCALAPPDATA`, which Windows rewrites for the AppContainer profile. Windows names are normalized case-insensitively; Unix names are exact.

Patch sets `HOME` to the policy's home (hidden except for approved toolchain locations), `TMPDIR` to the writable policy temp (`/tmp` for bubblewrap), and Windows `USERPROFILE`, `TMP` and `TEMP` deliberately from those locations. Agent commands also receive fixed `CI=1`, `FORCE_COLOR=0` and `NO_COLOR=1`. Native Unix shells run without login profiles. Arbitrary host values, agent/display handles and runtime injection/startup options are excluded, independently of tool-output secret redaction. This does not hide secrets stored in the writable project or make allow-listed toolchain paths writable.

Global `sandboxEnvAllowList` lists additional host variable names (one per line), and `sandboxPath` optionally overrides the native child's PATH. `changesToConfirm` requires native confirmation for added variable grants and changed nonempty PATH overrides; removing grants needs no confirmation. These grants can expose secret values, so the UI and confirmation warn without displaying values. Known runtime-startup/injection variables and agent/display handles cannot be granted, and home/temp values are still forced. No repository configuration or command-tool argument can supply a grant. GUI-launched Unix apps that discover toolchains through login profiles can set an explicit PATH instead of executing those profiles in the sandbox.

Container commands receive only the explicit environment in `containerArgs` and the image's defaults; the host Docker/Podman client needs its separate connection configuration, and native environment settings do not apply to it. The interactive terminal keeps its normal environment. An explicitly approved unsandboxed command still uses `scrubEnv` and can inherit private values with unrecognized names.

The Windows helper also journals a private per-command root under `%LOCALAPPDATA%\Patch\sandbox-temp`, grants only that root writable, and maps it to a temporary drive. It overrides `TEMP`, `TMP`, `TMPDIR`, `NPM_CONFIG_CACHE` and `NPM_CONFIG_USERCONFIG` case-insensitively, with an empty npm user config. Cleanup and abandoned-run recovery validate the deterministic root before deleting it and remove only exact-target drive mappings. Host temp, npm cache and profile config receive no new grants. Project PATH entries and directly launched project executables use the existing project drive mapping, avoiding inaccessible ancestor lookups. The helper compares long-form paths (`GetLongPathNameW`), so a PATH entry spelled with an 8.3 alias such as `C:\Users\RUNNER~1` still maps to the drive of the realpath project (#137). Sandboxed PowerShell applies `-ExecutionPolicy Bypass` only to its own process; filesystem/network controls remain AppContainer-enforced. libuv versions before 1.53 still lack the required `LOCAL` child-process pipe namespace, so ordinary Node test isolation remains an upstream blocker (#101): libuv retries the denied pipe name forever, so the command hangs until its timeout. No user command or Node test isolation flag is silently rewritten. Instead, `ShellRunner.run` records which sandbox ran a command (`CommandResult.sandbox`), and `formatResult` appends a fixed hint to AppContainer timeouts that names the explicit isolation flag and the `unsandboxed` request.

## Code search (`src/main/search/`)

`CodeIndex` walks the project (respecting ignore rules, up to _Maximum files to index_), splits text files into overlapping 60-line chunks, embeds them with Voyage `voyage-code-4` through OpenRouter's embeddings endpoint (`openRouterEmbedder`: `input_type` `document` for chunks and `query` for the search text, as Voyage recommends for retrieval; 1024 dimensions, the model's default) and stores Float32 vectors in `userData/indexes/<sha1 of path>.json`. Updates re-embed only files whose size or modification time changed, and each search refreshes the index once, reporting indexing progress to the tool card. The index is built on the first `search_code` call, never in the background. Search ranks by cosine similarity, at most two snippets per file. The best 30 of those go to Voyage `rerank-3` through OpenRouter's rerank endpoint (`openRouterReranker`, same key), which picks the final results; if reranking fails (anything but a stop), the results stay in embedding order and the tool output says why. Changing `INDEX_VERSION` or the embedding model rebuilds indexes. Settings shows the current project's index status (`index:status`: files and chunks, or why it is unavailable) and a Reindex button (`index:rebuild`, `CodeIndex.rebuild()`), which clears the index and embeds everything again.

## Chat list (`src/renderer/src/views/sidebar.ts`)

`Sidebar` lists the saved chats from `history:list`, newest first, grouped by day (Today, Yesterday, Previous 7 days, Older), and stays current through the `history:changed` push. `App` adds project navigation above it; New Chat sits above Sessions, and a header button collapses the sidebar with `aria-expanded`. Deleting and clearing chats stay in the history dialog behind the header's history button. Its foot shows the open chat's `agentFile` and the code index state (`indexStatusLabel`, `src/shared/index_status.ts`), which `App` polls through `index:status` while an index is being built.

The main window follows an OpenCode Desktop-inspired layout: neutral theme tokens, a 48px header with session breadcrumbs, sidebar project navigation, a centered 768px conversation, and model/approval/plan controls mounted into `Composer.controls`. ## Panels (`src/main/panels/`, `src/renderer/src/views/panels.ts`)

- **Terminal**: one interactive shell per project (`node-pty`), rendered with xterm.js. Separate from the agent's commands. The renderer starts it only when a project is open; without one the panel just says "Open a project to use the terminal." The main process still rejects `terminal:start` without a project as a safety net.
- **Browser**: a `<webview>` in the renderer (partition `persist:browser`). When it attaches, the main process receives its `webContents`; `BrowserService` implements the `browser` tool on it (load, console capture, `capturePage` scaled to ≤1280 px).
- **Git**: `simple-git` — status, diff (untracked files shown as additions), commit all, push, discard, discard all, init. Discard deletes the entry by its own path (`GitService.ownPath`, `removeEntry`): `Workspace.resolve` still confines it to the project, but its real path would turn a link into its target, so a link is removed itself and an entry inside a linked folder is refused (#111). `GitService.status` adds per-file line counts (`git diff --numstat --no-renames` against `HEAD`, or the index and working tree before the first commit, parsed by `parseNumstat` in `src/shared/panels.ts`; new files are counted by reading them, up to 2 MB, binary files not), the upstream with ahead/behind counts, and `canPush` (an upstream, or a remote named `origin`). `push` pushes to the upstream or runs `push --set-upstream origin <branch>`; it uses the user's git credentials and runs pre-push hooks, and since the app has no terminal git cannot prompt for a password. `git:suggest-message` sends the diff (cut at 30,000 characters, `MAX_COMMIT_DIFF_CHARS`) and the file list to the small model (`LlmService.smallModelForSettings`, preferring the provider of the model in Settings) and returns a Conventional Commit message (`panels/commit_message.ts`). Discarding a staged rename restores the original committed file and removes the renamed destination, including staged and unstaged edits to it. While the Git tab is open, it refreshes after each tool call and after an Undo. The status bar shows the current branch from `git:status` (with `*` when files changed) and the Git tab a badge with the number of changed files, refreshed when the project changes, after each run and whenever the Git tab reads a new status. A repository whose root is the home folder or a folder above it counts only when the project is that root (`isRepoAboveHome`); otherwise `git status` would scan the whole user profile.

## Accessibility

- The transcript is re-rendered per streamed chunk, so it is not an `aria-live` region. `TranscriptView.announcer` is a hidden `role="status"` region fed by `newAnnouncements` (`src/shared/announce.ts`): a finished answer (first 300 characters), an approval request, a failed tool, an error or a notice, each once. Opening a saved chat announces nothing.
- Anything that carries meaning only through an icon or color needs a text alternative (`visually-hidden` text or `aria-label`). `h()` gives icon-only buttons their `title` as `aria-label`.
- Colors come from the `--patch-*` tokens at the top of `src/renderer/src/styles.css`, one set per theme; Bootstrap's `--bs-*` variables and button variables point at them. Change the palette there, not in individual rules. Keep `--patch-accent-rgb` comma-separated (Bootstrap uses it in `rgba(var(...), a)`).
- Use Bootstrap's `*-text-emphasis` colors for colored text, not the plain `--bs-info`/`--bs-warning`, which are too light on white.

## Security model

- **Renderer isolation**: `contextIsolation`, `sandbox`, no `nodeIntegration`. Strict CSP (`script-src 'self'`, no remote images or connections).
- **Preload**: exposes only `invoke`/`on` for allow-listed channels.
- **Setting changes that run programs, skip approvals or redirect a key**: before `settings:update` applies a switch to Auto mode (once per app session), a changed `editorCommand`, a new or changed stdio MCP server (command, arguments, `cwd`, or a new `env` value), a new or changed `allow` or `delegate` permission rule, changes to an existing `ask` or `reject` rule or its preceding rules, new entries in the command or network allow-lists, or a changed Claude or OpenAI-compatible base URL, the main process shows a native confirmation (`changesToConfirm` in `settings_confirm.ts`). Removing protective rules requires confirmation even after Auto was confirmed; cancelling aborts the whole patch before settings are stored or applied (#114). `project:update-settings` does the same for new entries in a project's own allow-lists (`projectChangesToConfirm`). A compromised renderer therefore can't make these changes silently. The dialog names `env` keys, never their values. An HTTP MCP server asks only when it would keep stored headers (left out or empty in the save) while its URL is new or changed, because headers are stored by server name and would otherwise go to the new host (#110). The confirmation gets header names from `SettingsStore.mcpHeaderNames`, never values. Removing a server or allow-list entries, other HTTP server changes, clearing a base URL (back to the official API) and switching back to Ask mode don't ask (#29, #65).
- **Program lookup** (#141): Patch starts several programs by bare name (`git`, `powershell.exe`, `docker`/`podman`, `taskkill`), most with the project as working directory. Windows searches the working directory before PATH, and an empty or relative PATH entry does so on every platform, so a repository could supply its own `git.exe`. `hardenExecutableSearch` (`exec_search.ts`) runs before anything is spawned: it sets `NoDefaultCurrentDirectoryInExePath` on Windows and drops PATH entries that depend on the working directory (logging only how many). libuv reads both from the main process at every spawn, whatever environment the child gets. The interactive terminal and approved unsandboxed commands inherit them. MCP stdio servers resolve their command through `cross-spawn`, which searches the working directory itself (#142). End-to-end test: `tests/e2e/planted_binaries.test.ts`.
- **IPC sender**: every handler (`handle` in `ipc.ts`) answers only calls from the app page's top frame: the built `renderer/index.html` from disk, or the dev server during development (`isAppPageUrl`). Calls from any other frame are refused and logged by channel name.
- **Navigation**: the app window cannot navigate; `http(s)` links and `window.open` go to the system browser. The app page always comes from the built files on disk in a packaged app: the dev server URL (`ELECTRON_RENDERER_URL`, set by `npm run dev`) is only used when the app is not packaged (`renderer_url.ts`).
- **Browser panel**: guests get no preload, no Node, sandboxed, in the `persist:browser` session partition; `will-attach-webview` rejects omitted or different partitions in the main process, so the renderer cannot attach a guest to the app's default session (#34). Popups are denied. A guest can only be attached to `about:blank` or an `http(s)` URL. Every permission request (camera, microphone, location, notifications) is denied. Browser-tool top-level redirects and later page navigation stay on the approved hostname; cross-host destinations need a new tool call. Project `file://` URLs are preapproved only after `confineFileUrl` checks confinement. Once the agent has opened a page, the `persist:browser` session's request filter (`BrowserService.allowsRequest`) also checks every `file://` request, frames and sub-resources included, which never fire `will-navigate`: a project page cannot show a file from outside the project in an `<iframe>` for a screenshot to pass on (#63).
- **Model output**: rendered markdown and diffs pass through DOMPurify. Model Markdown uses `USE_PROFILES: { html: true }`, rejecting SVG (including `<image>` and `<feImage>`) and MathML in addition to the explicit image, embed, form and style exclusions (an image URL is a common data-exfiltration channel for prompt injection, #115). Normal HTML Markdown and syntax highlighting remain available, and markup in code blocks stays literal text. `renderDiff` retains its separate sanitizer configuration for generated diff HTML. Generated UI never uses inline handlers.
- **Trusted Types** (#65): the app page's CSP adds `require-trusted-types-for 'script'; trusted-types dompurify`. `renderMarkdown` and `renderDiff` ask DOMPurify for a `TrustedHTML` (`RETURN_TRUSTED_TYPE`), made by DOMPurify's own policy, the only one allowed; `trustedHtml()` takes only that type. Any other HTML sink (an `innerHTML` with a plain string, `insertAdjacentHTML`, `document.write`) throws instead of parsing, so a sanitizer bypass or a stray sink in new code cannot inject markup. xterm, diff2html, highlight.js and marked write no HTML themselves. This matters because a compromised renderer amounts to code execution (the terminal panel types into a real shell): keeping the renderer free of XSS is the main control, and the settings confirmations only stop a settings-only exploit.
- **Secrets**: keys are encrypted at rest when system encryption is available and never sent to the renderer. Plaintext fallback and failed migration are flagged in Settings. API keys, the ChatGPT tokens and MCP servers' `env` and header values are all migrated together, in one staged write, once encryption becomes available, and all count toward that flag (`sealedSecretValues`, #113).
- **Agent**: path confinement, read-before-write, approval for edits and commands by default. Agent commands use the configured sandbox; **Auto** mode skips ordinary approvals, not sandbox boundaries. Commands on the "allowed without asking" list skip approval only when they contain no shell operator and nothing PowerShell would evaluate (`$`, parentheses, braces). Tools marked `alwaysAsk` (MCP tools and `propose_plan`; a `propose_plan` call while plan mode is off has no side effect and is answered without a card) ask even in Auto mode and are never covered by an allow-list; an explicit `allow` permission rule can override that flag. Per-call `mustAsk` checks (protected files and sandbox escalation) cannot be overridden by an `allow` rule or a delegate's allow decision; `reject` still blocks the call without asking. Tool results are redacted before the model sees them (best effort: known token formats and credential-named values).
- **MCP servers**: stdio servers are started with `cross-spawn` (no shell string) and `getDefaultEnvironment()` plus the server's own `env`, so the app's API keys are not passed on. A server's `env` values and HTTP `headers` are encrypted like API keys and only their names reach the renderer. A failed connection, a removed server and quitting close the client and kill the server's process tree (`taskkill /T` on Windows). Tool names are namespaced (`mcp_<server>_<tool>`) so a server cannot claim a built-in tool's name, and results are cut like other tool output.
- **Subagents (`task`, `finder`, `oracle`)**: can only run an allow-list of read-only tools (`read_file`, `list_directory`, `glob`, `grep`, `search_code`, `load_skill`), so they cannot edit, run commands, use the network, call MCP tools, propose a plan or start another subagent. A subagent on the chat's own model is sent the chat's exact system prompt and tool list, so its requests read the prefix the chat already cached instead of writing a new one (#77); its role goes into its first message, and every tool outside the allow-list is a stand-in with the same name, description and schema that only returns an error, so the real tool is never reachable. On another model it gets only the allow-listed tools and its role in the system prompt. Its reads go into its own set, so they do not satisfy the parent's read-before-edit check.
- **Project skills**: the `.patch/skills` folder is resolved through `Workspace.resolve`; a folder linked outside the project is ignored and linked files inside it are skipped. Skill text is prompt text, like `AGENTS.md`.
- **Electron fuses** (`build.electronFuses` in `package.json`, applied when packaging): the packaged app ignores `ELECTRON_RUN_AS_NODE`, `NODE_OPTIONS` and `--inspect` flags, so it can't be turned into a Node runtime or have code injected through them, and it only loads its code from `app.asar`, whose integrity is checked: a changed header stops the app at start, and a changed file stops it when that file is read. Cookies of the browser panel are encrypted on disk. `GrantFileProtocolExtraPrivileges` stays on, because the UI loads ES-module scripts from `file://`.
- **API endpoints** (`src/main/llm/endpoints.ts`, #64): keys and ChatGPT tokens only go to the official endpoints or the base URL set in Settings. The clients always get an explicit base URL (Settings → Claude base URL or OpenAI-compatible base URL, else the official one; the Anthropic client gets no `authToken`), so `ANTHROPIC_BASE_URL`, `OPENAI_BASE_URL`, `ANTHROPIC_AUTH_TOKEN` or an `ant auth login` profile cannot redirect them or add a credential. The `PATCH_TEST_*` hooks the tests use to reach local stand-ins only work in development builds: the main process calls `setPackagedBuild(app.isPackaged)` at start, and until it does the hooks are off, so a missed call fails closed. The same rule covers `ELECTRON_RENDERER_URL` (`renderer_url.ts`, #27). Setting or changing the Claude base URL needs a native confirmation (`settings_confirm.ts`), since the Anthropic key goes there; it must be an http(s) URL, and a bad saved value falls back to the official API.
- **macOS hardened runtime**: the app and helper entitlement files grant only `allow-jit` for V8, not DYLD environment-variable injection or unsigned executable memory. A signed packaged launch on Intel and Apple Silicon remains to be verified (#22, #28).
- **Git panel**: a repository's own `.git/config` can name commands git runs by itself. `GitService` (`panels/git.ts`) runs every call with `core.fsmonitor=false` and `core.hooksPath=/dev/null`, neutralizes the clean, smudge and process commands of the filter drivers the repository defines in its local config (`hardenedConfig`), and diffs use `--no-ext-diff --no-textconv`. Filters the user configured globally keep working, but hooks (including Git LFS pre-push hooks) require running Git explicitly in the terminal. Disabling hooks at this host boundary stops a sandboxed command from redirecting hooks to any writable project folder, including when `.git/hooks` was absent at launch. Covered by real commit/push tests with executable default and redirected hooks in `panels/git.test.ts`.

### Known limits (reviewed 2026-10-01)

These are accepted limits of the unreleased Patch baseline; each is a trade-off, not an oversight.

- **Toolchain grants.** Cargo opens only `bin`, `registry` and `git`; Maven opens `repository`; Gradle opens `caches` and `wrapper`. Their parent directories and global Git configuration are not granted, keeping standard credential/config files hidden. Windows PATH grants reject these private paths and their ancestors as well, even before the files exist. `exceedsEntryLimit` uses native filesystem paths, with threshold-boundary tests on all platforms. Secrets deliberately stored inside the project or exposed tool/cache directories remain accessible; this is not secret detection. Commands needing private home configuration require explicit unsandboxed approval.
- **Command sandbox (#76).** `tools/sandbox.ts` plans how `ShellRunner` launches `run_command` (not the terminal panel, not MCP servers). `decideSandbox` picks bubblewrap (Linux), Seatbelt (macOS), the AppContainer helper (Windows) or a Docker/Podman container from the `sandboxMode` setting and what `detectSandboxSupport` finds. That call never blocks: it reads the results of `refreshSandboxSupport`, which `ShellRunner.prepare` awaits before the approval preview and before starting a command. It runs only the probes the mode needs (bwrap for `auto` on Linux, `docker version`/`podman version` only for `container`) as asynchronous child processes, caches them for 30 s, shares a probe that is still running and keeps the last result while refreshing (#112); `bwrapArgs`, `seatbeltProfile`, `containerArgs` and, for Windows, `windowsPolicy`/`buildHelperRequest` (`tools/sandbox_windows.ts`) are pure and unit-tested. Policy: project folder writable (the entire root `.git` read-only), temp writable, system and toolchain folders read-only, the rest of the home folder hidden, no network unless `sandboxNetwork: on` or a one-time approval grants it. `allow-list` requests unrestricted network if every URL written in the command is on the allowed hosts; `ShellRunner.mustAsk` requires approval because URL matching cannot filter a program's connections. Container mode mounts only the project at `/workspace`, drops capabilities and passes no host environment; stopping a command also runs `<engine> rm -f`. Both `auto` without a native backend and `container` without a running engine fail closed (foreground and background commands are not run). The model can set `network` or `unsandboxed` on a call; either makes it ask even in Auto mode or with an `allow` permission rule (allow once). Turning the sandbox off or network on needs a native confirmation. `tools/env.ts` (`scrubEnv`) drops credential-named variables. `npm run test:sandbox` runs policy tests plus real Unix/container probes (`sandbox.integration.test.ts`) and Windows helper probes (`sandbox_windows.integration.test.ts`). The Unix/container suite uses a fake home and local TCP control, asserts the probe actually executed, and never falls back to unsandboxed execution. Missing backends/images skip explicitly; CI requires its native backend.
- **Git metadata boundary (#98, #109).** `tools/sandbox_git.ts` prepares the selected root before sandbox launch and returns the protected top-level paths. Missing `.git` is reserved as a protected file (`GIT_RESERVATION`), not initialized Git, and persists across all command lifetimes to avoid overlap/cleanup races. The file is not a valid gitfile, so Git stops at the project with "invalid gitfile format"; an empty folder would let discovery fall through to a bare repository planted in the writable project root (#129). A project below another repository (not one at or above the home folder) keeps an empty folder, because the file would hide the enclosing repository. Git then checks the project folder itself for a bare repository, which requires a readable `HEAD`, so `reserveHead` creates a protected empty `HEAD` folder and returns it with `.git` (#132). Git ignores empty folders, so the enclosing repository does not list it. An existing `HEAD` is protected if it is a folder or a file that is not a valid Git `HEAD`; links, hard-linked files and a `HEAD` that starts with `ref:` or an object id refuse execution. A nested project with its own metadata needs no `HEAD` reservation. Empty folders from earlier versions are converted, and the Git panel's init turns the file back into an empty folder (`releaseGitReservation`) immediately before `git init`. Regular metadata, active hooks and existing command overrides are accepted. In-project gitfiles and `commondir` redirects protect the pointer plus entire top-level metadata ancestors, so renaming a writable ancestor cannot replace a target. External, linked or special metadata still refuse execution. On Linux and macOS a pointer may name the project through a link above it (macOS `/tmp` → `/private/tmp`) when every such link sits in a root-owned directory that group and others cannot write, so no command can retarget it (#131); links inside the project are always refused; the tree-size limit is removed. Git parses configuration with `--git-dir=/dev/null`, `--file` and `--no-includes`, suppressing repository discovery and startup config loading; include targets must stay within protected trees and are recursively checked without following writable includes. Bubblewrap and containers mount each protected entry read-only, including absent control names; `--mount` fails on disappearing sources instead of creating host directories, and comma-containing mount paths are refused. Seatbelt denies writes to protected entries and unlink/rename of the project's ancestor chain. Windows revalidates regular protected entries under the permission lock, protects inheritance and grants read-only access. The Git panel applies `safe.bareRepository=explicit` before even its local-config query to prevent discovery of bare metadata planted outside an empty reservation. Git writes still require the panel or explicitly approved unsandboxed access; approval text describes loss of file confinement and unrestricted networking. Before push and commit, the panel also reads the repository's local credential helpers, `core.sshCommand`, `core.askPass`, `core.gitProxy`, `remote.*.receivepack`/`uploadpack` and `gpg.*program`; if one runs a file inside the project (`projectCommands`: a path or bare name that leads into the project, or shell substitution), it refuses instead of running it (#130). This does not make nested repositories, arbitrary later terminal Git commands or existing host/global integrations that execute writable project code safe: hooks that run project scripts (Husky running `npm test`) run whatever the agent left, like running those scripts yourself.
- **Windows sandbox helper.** `native/sandbox-helper` is a Rust program (`npm run build:sandbox`). `ShellRunner` starts it once per command and writes a JSON request line on stdin (`HelperRequest`: shell, cwd, env, `network`, `readWrite`, `readOnly`, `denyWrite`, limits). It answers with JSON events (`started`, `stdout`, `stderr`, `exit`, `error`) and stops the command on `{id, kill: true}` or end of input. Each run creates a temporary AppContainer profile and grants only the listed paths. The project's own write grant is the exception (#103): it goes to a capability SID that `DeriveCapabilitySidsFromName` derives from `patch.project.<lowercased project path>` (SHA-256 inside Windows, so a folder name cannot be chosen to collide with another project's), and every command for that project carries the capability in its token. The grant is propagated through the project once, under the permission lock, with a record in `%LOCALAPPDATA%\Patch\sandbox-projects` flushed as unfinished before and finished after; later commands only check the record and the root's DACL, so they rewrite no project permissions. A helper killed half-way leaves an unfinished record and the next command repeats the grant. Closing or removing the project in Patch sends the helper a `revokeProject` message (`releaseProjectGrant` in `tools/sandbox_windows.ts`, retried while a stopped command's helper finishes); the helper keeps the grant while a recovery record shows a live run in that project. Quitting keeps it for the next session. Windows system paths keep their built-in package access, but Program Files installers can remove inherited package permissions (#106). Individual Program Files PATH entries travel separately as `toolchains`, and the helper checks effective package read/execute rights before changing anything. A folder whose own entries are already readable (Git, Python) gets no grant, and the rest of the install is not walked. Otherwise the whole tree is inspected. An inaccessible, inheritable install gets a temporary read/execute grant on that folder when the helper is allowed to add one, under the permission lock. A protected ACL, or a grant the helper may not make, uses a read-only copy instead, kept across commands in `%LOCALAPPDATA%\Patch\sandbox-toolchains\cache` (#108). Inspection first lists the install cheaply (names, sizes, write times, reparse flags, no per-entry security queries) and names the copy `<install hash>-<contents hash>` (FNV-1a). If that copy exists, the command uses it and the per-entry link and package-rights checks are skipped, because the source is never read; a repeat `node --version` with the official Node install takes about 0.3 s instead of about 4 s. Otherwise the helper copies into the run's private staging folder after the lock is released, with ALL APPLICATION PACKAGES read/execute inherited from that folder (never write), and publishes the copy by an atomic directory rename, so a partial copy never appears in the cache; if another run published the same name first, its copy is used. The cache root is readable for packages and mapped for each run to its own journaled drive letter, removed by exact letter like the project drive. Publishing also removes, under the permission lock, older copies of the same install and copies unused for 30 days (each use stamps the entry's write time), except those a recovery record lists in `cached`, so a live run's copy is never removed. PATH entries and directly launched executables are redirected with case-insensitive path boundaries; absolute paths written in shell text are not rewritten. No administrator prompt is used. Toolchain inspection rejects reparse points and escaping paths, and is limited to 32 candidates, 100,000 inspected entries and 15 seconds per tree (30 seconds across inspection). Inaccessible toolchains are limited to 5,000 entries per command, and copies to 256 MiB and 30 seconds. A toolchain that is too large, or that cannot be inspected, granted or copied, stays unreadable, as before #106; the command still runs and its output names the folder and the reason. Skipping one never widens access. Cancellation during inspection or copying prevents the process from starting. The project appears at a temporary drive root (`P:`–`Z:`) so relative paths work without exposing parent folders (#88). The entire `.git` temporarily stops inheriting the project grant, and the copy of its permissions made then leaves out the project capability's entries (`protect_acl`), so the lasting grant never makes it writable; the last overlapping run restores the original inheritance. The command runs in a job object with `KILL_ON_JOB_CLOSE`, process and memory limits; network capabilities are added only when requested. Toolchain folders with more than 5000 entries are replaced by a small `bin` folder or skipped to bound recursive ACL work (#89). `HelperProcess` wraps the protocol; `findHelper` checks packaged resources then Cargo output. The installer ships the helper and CI builds it. A missing or failed helper never falls back to an unsandboxed command. Real Windows coverage lives in `sandbox_windows.integration.test.ts`, including protected and readable installs, temporary grants, source-ACL preservation, staging write denial, cancellation and forced recovery.
- **Windows permission recovery (#91).** Before creating a profile or editing permissions, the helper flushes a cleanup record in `%LOCALAPPDATA%\Patch\sandbox-recovery`, locked against other writers but readable by other helpers. A named OS mutex serializes setup/recovery/cleanup, never command execution. Overlapping runs copy the original inheritance snapshot into their records; cleanup restores it only when no other record owns that path, so ending or recovering one command cannot expose metadata to another (#100). Normal and failed runs revoke their own grants and delete their profile and record. Forced termination bypasses destructors: the job still kills descendants, and the next helper startup recovers unlocked records before accepting commands. Live helpers retain their locks and grants. Recovery derives the exact SID from the recorded profile name, even if the profile was already deleted; it preserves unrelated container grants and retains records for retry if cleanup fails. Entries from older helpers without a record cannot safely be distinguished from other deleted containers, so they are not automatically removed. Staged toolchain copies are journaled before they are created or exposed. Cleanup removes only exact-target mappings to that run's private staging root and its copied files, so live helpers and unrelated mappings are kept; old records default to no staging. Cleanup and recovery never remove cached toolchain copies; only publishing a new copy does. A cleanup failure after the command ran is reported in its output, its exit code is still sent, and the record stays for the next helper start to retry. Project drive mappings also record the exact letter and target before creation (#94). Letter selection, record publication and mapping creation run under the same permission mutex, including serialization with staging/temp mapping selection. The journal alone owns project mapping cleanup, preventing a late destructor from deleting a newer mapping for the same project. Recovery removes only that letter/target pair, never project files or another live run's mapping to the same project; exact-target removal preserves letters reused for different folders. Missing mappings make repeated recovery harmless, while other removal errors retain the record for retry. Older records default to no project mapping and cannot safely identify historical abandoned drives.
- **Network approvals are not a sandbox.** In Ask mode, `fetch_url` and `browser` require approval unless the exact URL hostname matches `allowedNetworkHosts` (empty by default, all ports, subdomains listed separately). Auto mode skips approvals. Fetch and browser top-level cross-host redirects are blocked even in Auto mode; the model must request the destination separately. Before the agent opens a page, and for addresses typed in the panel's address bar, browser navigation is not filtered; after the agent opens a page, link clicks and redirects in the panel stay on that page's host. Browser subresources and Google `web_search` are not filtered by this policy. Approved hosts and search queries can still receive private data. Keep projects with secrets out of chats that read untrusted pages.
- **Editor command.** `editorCommand` is run through a shell with the file path quoted. File names with a double quote or line break are refused, and on macOS and Linux also names with `$`, a backtick or a backslash, which `sh` would still expand inside the quotes. The command itself is the user's own setting; changing it needs a native confirmation, though a compromised renderer can already write to the terminal panel.
- **Tool card ids are the app's own.** `Agent.runTool` gives every tool call a fresh UUID for its card, approval and edit backup. The provider's tool-call id is used only to pair the call with its result in the API request, since some OpenAI-compatible servers reuse ids across turns.
- **Undo is locked against sending.** `ChatManager.undoEdit` counts as busy until the file is restored and the note for the model is queued and saved, so a message, resume, compact or chat/project switch cannot start in between. The pending note is saved with the chat (`SavedChat.pendingNotes`) and survives a restart; it is sent, and cleared, with the next message or resume.
- **Log redaction is pattern-based.** Recognized `sk-`, `gsk_`, `xai-` and `AIza` keys, bearer tokens and named API-key/authorization fields are redacted; unrecognized secret formats can still appear in error messages. Review logs before sharing.
- **IPC handlers trust the renderer's arguments.** The renderer is sandboxed, has a strict CSP and only shows sanitized model output, and pages in the browser panel have no preload, so they cannot call IPC. Handlers that take paths (`git:*`, file tools) still confine them to the project with `Workspace.resolve`. The renderer's IPC surface is powerful by design: the terminal panel types into a real shell, so a compromised renderer still amounts to code execution. Settings that choose MCP commands, the editor command, Auto mode, allow `allow`/`delegate` rules, add allow-list entries or change a base URL need a native confirmation (see Security model), as do new entries in a project's allow-lists, and handlers only answer the app page's top frame; runtime payload validation (#32) is open.
- **Retries repeat the whole request.** A failure in the middle of a long answer discards the streamed text and asks again, so the tokens of the failed attempt may be billed. On the Anthropic path, this also repeats any server-side compaction or `pause_turn` continuations from the failed attempt; their responses are not left in saved model history. Only errors that usually pass are retried; a wrongly classified error costs at most 4 extra requests (about 30 seconds) before it is shown.
- **A compaction is a lossy summary written by the small model.** Details can be missed or wrong, and the model then works from the summary as if it were what happened; the unedited history stays in the chat file but is no longer sent. The summarizing request is not included in the token and cost totals (`CompletionClient` reports no usage). The first request after a compaction misses the prompt cache. Context size is only known after a request, and the 150k suggestion is one value for every model, not a limit of the model in use (custom endpoints can have far smaller windows).
- **Undo covers the edit tools only.** Changes made by commands the assistant ran, or by anything else, have no backup. A backup is a plaintext copy of the file on disk in the app's data folder (until the chat is deleted or 50 newer edits push it out), which matters for projects with secrets. The pending model notification is saved with the chat and delivered on the next Send or Resume, including after a restart.
- **Local logs can name paths.** `logs/app.log.jsonl` never holds chat history or API keys (keys and tokens are redacted), but error messages such as "Folder not found: …" can contain file paths. The files stay on the machine and rotate at 512 KB; nothing is sent anywhere.
- **Project instructions, `AGENTS.md` and project skills** are prompt text, not trusted configuration: they are added to the system prompt (skills when loaded), so a malicious repository can steer the model. Approvals still apply to edits and commands.
- **MCP servers run with the user's permissions.** A stdio server is a program the user configured; approval covers each tool call, not what the server does on its own. Stdio servers start in the project that was open when they connected and are not restarted on a project switch. Stored `env` and header secrets are keyed by server name; renaming a server carries them over only when exactly one old and one new server share the same endpoint (URL, or command and arguments), so a rename never sends a saved header to another host (#23).
- **Git panel commits and pushes run the repository's hooks.** Viewing status and diffs or discarding a file runs nothing the repository's config names, but **Commit** runs its commit hooks and **Push** its pre-push hook (including a local `core.hooksPath`), as any git client does; tools like husky depend on that. A push goes to whatever URL the repository's `origin` or upstream names, with the user's credentials. **Generate** sends the uncommitted diff to the configured model provider, like a chat would. A repository whose filter drivers are defined in its local config (for example `git lfs install --local`) is shown and committed without those filters in the Git panel.
- **Release signing**: Windows releases require signing credentials and valid Authenticode signatures on both the app and installer before publishing; checksums accompany the installer. Local development builds may remain unsigned. Signing credentials have not been provisioned, so releases are blocked (#26); macOS entitlement changes still need signed packaged testing (#28, #22).

## Tests

- `npm run test:unit` — Vitest unit tests next to the code (`*.test.ts`). The provider tests run the real SDKs against a local mock HTTP server (`llm/test_server.ts`).
- `npm run test:e2e` — builds the app and drives it with Playwright's Electron support, using a throwaway profile and mock APIs: Claude (`tests/e2e/mock_claude.ts`, enabled by `PATCH_TEST_ANTHROPIC_URL`) and OpenAI (`tests/e2e/mock_openai.ts`, enabled by `PATCH_TEST_OPENAI_URL`, used only when no custom base URL is set so the Responses API path runs). These hooks, and `PATCH_TEST_CODEX_URL` / `PATCH_TEST_CODEX_TOKEN_URL` for ChatGPT sign-in, only work when the app is not packaged; unit tests that use them call `setPackagedBuild(false)`. Covers window security, settings, a full tool-using chat with approval on both providers (including the encrypted reasoning round trip), the UI, the panels, retries of rate limits and overloads (the Claude mock can script failures with `Retry-After`), the local error log and Help menu, stopping and resuming long runs (the mock can hold an answer open until Stop, and `launchApp({}, { userData })` restarts on the same profile), killing the app mid-run and resuming from whatever it had saved (`RunningApp.kill()` ends the whole process tree, as a crash would), switching between open projects, very large tool results, a catastrophically backtracking grep pattern that must not freeze the app, the transcript view (opening a long chat at its end, a tall approval card staying in view, focus after Undo), undoing approved edits, Compact chat, image attachments, MCP tools, plan mode, per-project allow-lists, project skills, the `task` subagent, the single-instance lock, the terminal without a project, and the documentation screenshots with text contrast checks. The chat list, the header model picker and the status-bar branch have no e2e tests yet. Closing the app or a mock server fails with a clear error after 20 s and 5 s instead of hanging until the hook timeout. The harness also captures the main process's stderr, so tests can assert that no IPC handler errors were logged.
